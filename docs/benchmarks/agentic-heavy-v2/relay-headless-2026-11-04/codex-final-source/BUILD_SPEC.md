# Relay Directory

Build one local, durable roster-import service with a usable JSON CLI and a typed JavaScript SDK. There is no graphical interface in this task. Use only local synthetic data and no remote dependencies or services. Both runtime arms receive the identical empty seed. The evaluator and reference implementation are independent instruments; do not inspect or modify them.

## Deliverables and execution contract

Provide `app.mjs`, `cli.mjs`, `sdk.mjs`, `sdk.d.mts`, and `package.json`. JavaScript must run with both current Node and Bun without installation or downloaded packages. Start the service using `<runtime> app.mjs --data ABSOLUTE_DIRECTORY --port NUMBER`. Bind only `127.0.0.1`; port 0 selects a free port. The first stdout line must be one JSON object `{ "ready": true, "port": ACTUAL_PORT }` after recovery and exclusive ownership are complete. Read the initial administrator capability from `RELAY_BOOTSTRAP_TOKEN`. Do not write capabilities or lease tokens in plaintext to disk, stdout, stderr, events, or error bodies. Store data only under the supplied data directory. Expose `GET /health` as `{ "ok": true }`. Errors have JSON `{ "error": { "code": STRING, "message": STRING } }` with a suitable non-2xx status. No request may escape as an uncaught exception or corrupt subsequent requests.

Use `Authorization: Bearer TOKEN` for protected endpoints and JSON request/response bodies. Mutation bodies are limited to 262,144 UTF-8 bytes and must be valid UTF-8. Missing, malformed, unknown or revoked capabilities return 401. A valid capability for another workspace returns 403. An authenticated caller requesting an absent import within its own workspace receives 404. Enforce authorization on every operation, including idempotent replays, rather than relying on the token's original admission. Use 403 for a disallowed role, 409 for state/version/idempotency/lease conflicts, 400 for malformed input, 413 for oversized input, and 415 for non-JSON mutation bodies. Query parameters must be bounded integers; malformed values return 400. All successful mutations described below return 200, except new workspace/import creation which returns 201; an exact creation replay returns 200. When the owning process writes `shutdown` followed by a newline to stdin, drain accepted writes, close the listener, release owned process-lock resources and exit 0.

## Workspaces and capabilities

`POST /v1/workspaces` requires the bootstrap capability and accepts `{ "id": "name", "name": "Display name" }`. IDs match `[a-z][a-z0-9-]{2,23}`; names are trimmed, nonempty and at most 80 characters. Workspace IDs are unique. Return `{ "workspace": { "id", "name", "version": 0 }, "ownerToken": TOKEN }`; the owner capability's subject is `owner`. The bootstrap capability cannot access workspace business endpoints.

The owner can `POST /v1/workspaces/:workspace/tokens` with `{ "subject": STRING, "role": ROLE }`, where subject matches `[a-zA-Z0-9_-]{1,32}` and role is exactly `editor`, `approver`, `worker` or `viewer`. Return `{ "id", "subject", "role", "token" }`. Capabilities have independent opaque IDs and secret tokens. The owner can `POST /v1/workspaces/:workspace/tokens/:id/revoke` with `{}`. Revocation is durable and an exact repeated revocation succeeds without a second event. Other roles cannot issue or revoke capabilities. Every workspace role may read its own workspace, members, imports and events. `GET /v1/workspaces/:workspace` returns `{ "workspace": { "id", "name", "version" } }`.

## Imports and directory state

`GET /v1/workspaces/:workspace/members` returns `{ "version": INTEGER, "members": [...] }`. Members are sorted by `externalId` in ascending codepoint order and contain `{ "externalId", "name", "email", "revision" }`. Initial state is version 0 and an empty member list.

Owner or editor can `POST /v1/workspaces/:workspace/imports` with `{ "baseVersion": INTEGER, "csv": STRING }` and an `Idempotency-Key` header matching `[a-zA-Z0-9_-]{1,80}`. The supplied base version must equal the current directory version. CSV has exactly the header `op,external_id,name,email`, followed by 1–500 data rows, with at most 65,536 UTF-8 bytes. Support LF, CRLF, a leading UTF-8 BOM, quoted commas and doubled quotes. Reject malformed quoting, extra/missing columns, interior empty rows, duplicate external IDs, unsupported operations or unsafe field values as one atomic failure. One optional final line ending is allowed. `op` is `upsert` or `delete`; external IDs match `[a-zA-Z0-9_-]{1,32}`. Upserts require a trimmed 1–80-character name without control characters and an email with one `@`, nonempty local part and a dotted domain, no whitespace and at most 120 characters. Normalize emails to lowercase. Deletes require empty name and email. No directory data is changed by staging. Return `{ "import": IMPORT }`.

An IMPORT has `{ "id", "workspaceId", "creator", "baseVersion", "state", "rowCount", "digest", "leaseEpoch", "approvedBy" }`; `digest` is the lowercase SHA256 of the exact submitted CSV UTF-8 bytes, and `state` is `staged`, `approved`, `leased`, `committed`, `rejected` or `cancelled`. `approvedBy` is null before approval. Do not expose capability hashes, lease-token hashes or raw stored CSV/rows in import responses. `GET /v1/workspaces/:workspace/imports/:id` returns `{ "import": IMPORT }`; `GET .../imports` returns `{ "imports": [...] }` sorted by import ID.

An exact staging replay, scoped to workspace plus subject plus idempotency key, returns the original import without another event. Reusing that key with another request body returns 409. A different subject has an independent key namespace. Keys must survive restart. Comparison is based on canonical JSON (object property order is insignificant) and the exact CSV string. Replays still require current valid authorization and an appropriate role.

## Approval and worker fencing

Owner or approver can `POST .../imports/:id/approve` with `{}` only for a staged import. The approver subject must differ from the creator, including when the caller is owner. Persist the subject as `approvedBy` and state as `approved`. The same approver's repeat approval succeeds without a second event; another subject's repeat is a conflict. Owner or approver can instead `POST .../imports/:id/reject` with `{ "reason": STRING }`, requiring a trimmed 1–160-character reason and staged state. Owner or the original creator (with current editor authority) can `POST .../imports/:id/cancel` with `{}` while staged, approved or leased. Cancellation invalidates any lease and is terminal. A viewer, unrelated editor or worker cannot cancel. Rejected/cancelled/committed imports cannot be claimed or otherwise reactivated.

Worker role can `POST .../imports/:id/claim` with `{ "leaseMs": INTEGER }`, 100–5000 inclusive. Claim only approved imports or a leased import whose old lease has expired. Return `{ "import": IMPORT, "leaseToken": TOKEN, "expiresAt": UNIX_MILLISECONDS }`. Each successful claim increases `leaseEpoch` by exactly 1. Two simultaneous claims have exactly one winner. A nonexpired lease cannot be stolen, even by the same subject. A lease is bound to the claiming subject, its precise capability ID, import and epoch. A new claim fences the old token. Revoking the worker capability invalidates its outstanding lease even if another valid worker capability has the same subject.

`POST .../imports/:id/commit` requires worker authority, `{ "leaseToken": STRING }`, and a valid `Idempotency-Key`. Validate current capability, lease ownership, token, epoch, expiry, state and base version inside the atomic write boundary. A stale/revoked/expired/wrong-worker lease must not apply anything or advance directory version. Apply every row or none. Deleting a nonexistent member conflicts. Final email values must be unique across the whole workspace; atomic email swaps are valid. Existing external IDs increment revision by 1 on upsert; new IDs start at 1. Deletes remove a member. A successful batch increments directory version exactly once, sets the import to committed, and returns `{ "import": IMPORT, "version": INTEGER, "applied": INTEGER }`. Persist its result with the directory data and event in the same transaction. Exact commit replay by the same currently authorized capability returns the original result without another event/version increment, even after lease expiry. A changed body/key conflict or another worker must not receive a successful replay. Never partially apply a failed batch. Two imports staged against the same version may both be approved, but at most one can commit; the other is a stale-version conflict.

## Durable transactions and audit

All successful mutations are durable before responding. Serialize competing writes. Data, import transitions, capability issuance/revocation, replay outcomes and audit events must commit atomically. Reopen the same data directory after graceful stop or abrupt process death without resetting data, revisions, roles, revocations, epochs or replay outcomes. Refuse a second live writer for the same data directory before announcing readiness. Recover a dead owner's process lock safely; do not delete unrelated files or terminate any other process. Use a UTF-8 JSONL transaction journal with a checked monotonic sequence and a checksum/hash chain. A malformed, truncated, checksum-invalid, reordered or sequence-gapped durable journal must fail closed at startup, never reset to empty or silently repair. Document its filename on a line `Journal: filename.jsonl` in `STORAGE.md` (one safe basename under DATA_DIR), followed by its format. The evaluator injects a partial trailing line and a valid-JSON changed transaction. Do not store an entire reference implementation or evaluator workaround in the app.

Every successful state-changing operation appends exactly one per-workspace event in the same transaction; exact replays/repeated revocation/repeated approval append none. Events are `{ "cursor", "type", "subject", "importId" }`, with `importId` null when inapplicable. Types are `workspace.created`, `capability.issued`, `capability.revoked`, `import.staged`, `import.approved`, `import.rejected`, `import.cancelled`, `import.claimed`, `import.committed`. Per-workspace cursors start at 1, are contiguous, and remain stable after restart. Rejected operations append no event. `GET /v1/workspaces/:workspace/events?after=N&limit=N` returns `{ "events": [...], "nextCursor": INTEGER }`, selecting cursors greater than `after` (default 0), in order, with limit 1–100 (default 50). `nextCursor` is the last returned cursor or the supplied `after` for an empty page. Capabilities, raw CSV and lease secrets are excluded from events and routine logs.

## CLI and SDK

`<runtime> cli.mjs --help` exits 0 with useful command names. Commands use `RELAY_URL` and `RELAY_TOKEN`, emit a single JSON success value on stdout, and exit nonzero with a JSON error on stderr for failures. Never echo either environment value or secret flags on failure. Support `status WORKSPACE`, `members WORKSPACE`, `stage WORKSPACE --file PATH --base-version N --key KEY`, `approve WORKSPACE IMPORT`, `claim WORKSPACE IMPORT --lease-ms N`, `commit WORKSPACE IMPORT --lease-token TOKEN --key KEY`, `cancel WORKSPACE IMPORT`, and `events WORKSPACE --after N --limit N`. Commands must call the running service and reflect durable shared state, rather than maintaining separate state. The server must remain healthy after CLI errors.

`sdk.mjs` exports `createClient({ baseUrl, token })` and `RelayError`. Its methods are `workspace(id)`, `members(id)`, `stage(id, {baseVersion,csv}, key)`, `approve(id, importId)`, `claim(id, importId, leaseMs)`, `commit(id, importId, leaseToken, key)`, `cancel(id, importId)` and `events(id, {after?,limit?})`. They return the JSON shapes described above, and non-2xx responses reject with `new RelayError(status, code, message)` containing numeric `status` and string `code`. Declare accurate argument and return types in `sdk.d.mts`, export `Role`, `ImportState`, `Member`, `ImportRecord`, and avoid `any`. `Role` is the exact five workspace roles including owner; `ImportState` is the exact six states. No secret or network URL should be hardcoded in the SDK.

Preserve complete verification and report limitations honestly. The acceptance groups cover the connected workflows, input boundaries, tenant/role isolation, idempotency, concurrency, fencing/revocation, atomicity, restart/corruption, CLI and SDK. Meeting only happy paths is insufficient.
