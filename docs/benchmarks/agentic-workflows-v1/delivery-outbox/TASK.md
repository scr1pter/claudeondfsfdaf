# Upgrade the existing support dashboard with a durable delivery outbox

The application is a small customer-support dashboard with three synthetic tickets, persistent reply drafts, and a local fake delivery provider. Keep the existing ticket browsing and draft workflow working. Replace its fragile direct-send path with a durable transactional outbox. Complete storage, HTTP and browser behavior; a static mockup is insufficient.

Use the installed pinned dependencies (Bun 1.3.14, Node 24.22.0, TypeScript 5.8.2). Run with `bun server/index.ts`, bind only `127.0.0.1`, use `PORT` (default 4123), and keep every mutable database/cache under the supplied absolute `DATA_DIR` outside the application directory. Use Bun SQLite. Preserve `package.json`, `bun.lock`, `.bun-version`, `.node-version`, `fixtures/provider.ts`, `fixtures/tickets.json` and this task. Do not read or change independent benchmark instrumentation. Do not use external services, accounts, authentication, real recipients or personal data.

The protected `startProvider(DATA_DIR)` function starts an HTTP fake provider on loopback port zero in the same application process. Call it once at startup and return its `origin` as `providerOrigin` from `GET /api/health`. The fixture has a separate durable SQLite database and may not be replaced, bypassed or edited. All real delivery effects must go through its HTTP `/deliver` endpoint. The frontend talks only to the application origin. Provider `/control/*` routes are for local verification; application delivery logic must not use them.

Deliveries are at least once on the wire and exactly once in provider effect. A message gets one durable, nonempty provider idempotency key, retained across retries, crashes, cancellation races and repeated admission requests. The immutable delivery envelope is `{idempotencyKey,messageId,ticketId,body}`. The provider atomically records a receipt or cancellation for a key. Replaying the same envelope returns the same receipt without another effect. Reusing an accepted key with different content returns 409. A 503, a lost connection, or process death can occur after acceptance, so absence of a receipt response never proves non-delivery.

Admission must commit the queued message's immutable body and its recoverable outbox work in one SQLite transaction before returning success. Nothing may be transmitted by admission alone. Processing is explicit: a user presses **Process queue**, or an HTTP client invokes the drain endpoint. No timer or automatic retry is required. Each drain attempts each currently eligible message at most once, and concurrent drains/admission requests must be safe. Failed/unknown attempts become `retryable` with a useful error, never `delivered` without a provider receipt. **Retry** makes the same message eligible again; it must not create a second logical delivery or new key. A later drain must recover unfinished work after a hard process stop. Receipt reconciliation must also repair a crash after provider acceptance but before the app commits that receipt.

Cancellation is a durable terminal outcome only when non-acceptance is established. Cancelling an untransmitted queued message prevents future transmission. For a potentially transmitted message, use provider `POST /cancel` with its key: the provider atomically returns either `cancelled` (a tombstone prevents later acceptance), or `accepted` with its committed receipt. In the latter case the app must converge to `delivered`, show the receipt, and retain a nonempty human-readable `delivery.lastError` explaining that cancellation was too late. A transient cancellation failure must remain unresolved/retryable, never claim a successful cancellation. A late send response must not overwrite an already-established terminal outcome or its cancellation explanation. Repeated cancellation/retry/drain calls and page refreshes must retain truthful state.

Keep these HTTP contracts. JSON responses and error bodies must use `application/json`; error bodies include a nonempty human-readable `error` string that is stable for identical validation failures. Request IDs or timing metadata, if desired, belong in additional fields. Invalid JSON, unsupported values, whitespace-only bodies, bodies over 2000 Unicode code points, and malformed admission IDs return 400 without mutating delivery state. An astral character such as 🙂 counts as one code point, not two UTF-16 code units. Preserve every accepted body verbatim, including leading/trailing spaces and newlines; trimming for validation must not normalize stored or transmitted text. Unknown resource IDs return 404. Valid IDs are nonempty strings of at most 80 ASCII letters, digits, `_` or `-`. Extra object properties may be ignored. Exact response formatting and internal database schema are your choice.

| Route | Required behavior |
| --- | --- |
| `GET /api/health` | `{ok:true,providerOrigin}`; readiness only after SQLite and provider are ready. |
| `GET /api/tickets` | `{tickets:[{id,subject,customer, ...}]}` containing the protected fixture tickets. |
| `GET /api/tickets/:id` | `{ticket,messages:[Message]}`, ordered by durable creation order. |
| `POST /api/tickets/:id/messages` | `{body}` → 201 `{message}` in `draft`, with returned ID. |
| `GET /api/messages/:id` | `{message}`. |
| `PATCH /api/messages/:id` | `{body}` edits a draft; 409 for admitted/terminal messages. |
| `POST /api/messages/:id/send` | `{requestId}` → 202 `{message}`. Exact repeat on the same message/request returns the same logical admission and may return its current message state (including delivered); it need not repeat the original queued response bytes. A different request ID for an already admitted message, or reuse of a request ID for a different message, returns 409. |
| `GET /api/outbox` | `{items:[Message]}` for all admitted messages, including terminal history; no duplicates. |
| `POST /api/outbox/drain` | `{}` → `{processed:[messageId,...]}` when that drain's attempts have settled. Retrying a terminal message is prohibited. Concurrent drains may coalesce; provider effect must remain exactly once. |
| `POST /api/messages/:id/retry` | `{}` → `{message}`; `retryable` becomes `queued` with the existing envelope/key. A draft or cancelled/delivered message returns 409. Repeating retry while queued is harmless. |
| `POST /api/messages/:id/cancel` | `{}` → `{message}` after settling cancellation. A draft can become cancelled. Repeated cancelled/delivered cancellation is harmless and truthful. |

`Message` has `{id,ticketId,body,status,delivery}`. `status` is one of `draft`, `queued`, `sending`, `retryable`, `delivered`, `cancelled`. A draft has `delivery:null`; an admitted message has `{idempotencyKey,attempts,receiptId,lastError,cancelRequested}`. `attempts` is a durable nonnegative integer counting outbound `/deliver` attempts, `receiptId` is null unless accepted, and `lastError` is null or human-readable text. `cancelRequested` records whether cancellation has been requested. A locally cancelled draft may have null delivery. On recovery, unresolved work can remain `sending`, become `queued`, or become `retryable` until the next explicit drain; it may not silently become terminal. A provider receipt always wins over a late cancellation request. Never modify the admitted body.

Browser requirements: retain an accessible page headed **Support desk**, a ticket control named for each subject, a labelled **Reply** text area, and a **Save draft** button. Selecting a ticket shows its replies. Saved replies show their body, a visible status, and applicable controls. Use these accessible names so users can operate the application consistently: `Edit <messageId>`, `Queue <messageId>`, `Retry <messageId>`, `Cancel <messageId>` and `Details <messageId>`. Provide a **Process queue** button and **Refresh** button. Details must expose message ID, status, attempt count, provider receipt (when known), and the current `lastError` text verbatim when nonempty. Show an invalid save's API `error` string visibly and verbatim; you may add explanatory copy. The wording of these error strings is your choice. Queued/sending/retryable states must not look delivered; successful cancellation and too-late cancellation must be distinguishable. Do not erase draft text on a failed save. A refresh/restart must show the same committed messages, keys, attempts and receipt. At a 390px viewport the workflow controls and details must remain reachable. No exact color, font, layout, animation or ornamental style is graded.

The local provider protocol is intentionally small. `POST /deliver` accepts the envelope above, returning `{status:'accepted',receipt:{id,idempotencyKey,messageId,ticketId,body}}`, or `{status:'cancelled',idempotencyKey}` for a tombstoned key. `POST /cancel` accepts `{idempotencyKey}`, returning `{status:'cancelled',idempotencyKey}` or `{status:'accepted',receipt}`. Check status codes and shapes. For verification, `GET /control/state` exposes synthetic receipts, cancellations, attempts, plans and held requests; `POST /control/plan` accepts `{messageId,mode}` where mode is `accept`, `reject`, `fail_once`, `before_accept`, or `after_accept`; `POST /control/release` accepts `{messageId,response:'receipt'|'lost'}`. The last two modes hold a request before or after durable acceptance until released, cancelled, or process termination. `lost` returns a 503 instead of the receipt even when acceptance committed. `POST /control/cancel-plan` accepts `{idempotencyKey,mode:'fail_once'|'accept'}` to make the next cancellation return 503 without establishing either terminal outcome. Provider plans and effects persist across restart, while held HTTP connections do not. You can change a persisted plan to `accept` after restart. Do not infer correctness from a fixed sleep; poll observable state with a deadline and use explicit release controls.
