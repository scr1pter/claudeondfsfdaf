# Harbor — local release and incident operations

Build a polished, complete **Harbor** operations console from the empty React/TypeScript/Bun scaffold. Harbor connects projects, environments, versioned runbooks, approval of immutable release plans, a real durable dependency-job queue, artifacts, rollback, incidents and audit history. This is one cohesive application with working UI and HTTP behavior, not mock screens. All application implementation must be written during this task.

Everything is synthetic and local. Jobs simulate work with timers and generated text artifacts; they never run shell commands, deploy software, read arbitrary files or call external APIs. No accounts, cloud, Docker, SMTP, telemetry, external fonts/assets or additional dependencies. Do not inspect other applications or benchmark evaluators. Use only the supplied common browser client for browser verification.

Read the accompanying `UI_CONTRACT.md` for the public semantic control names used by independent browser verification. Visual design and component structure remain your choice.

## Delivery and HTTP conventions

Use the pinned dependencies, Bun HTTP and `bun:sqlite`. `bun run typecheck` checks actual frontend and backend; `bun run build` creates the frontend in `dist`; `bun run start` serves both from one origin on `127.0.0.1:$PORT` (default 3000). Direct frontend links work after reload. Store the database **harbor.sqlite** and any owned artifact files only under `DATA_DIR` (default `.harbor-data`). Everything described as durable survives process termination and restart. Stop your verification servers before finishing.

`GET /api/health` → 200 `{ok:true}`. Unknown `/api` routes return JSON 404. Singular bodies use `{project}`, `{environment}`, `{runbook}`, `{release}`, `{incident}`; collections use plural arrays. Create returns 201, reads/updates/actions 200, delete/logout 204. All errors use `{error:{code,message}}` with nonempty strings: malformed/invalid input 400; no session 401; insufficient role 403; missing/cross-project reference 404; state, version, uniqueness or idempotency conflict 409. IDs are opaque strings and dates ISO 8601 UTC. Do not silently coerce enums, integers, empty required strings or malformed JSON. Preserve partial patch semantics. Timestamps, IDs, status, revision counters and ownership are server-controlled. Lists may be bounded at 200 but must include all supplied small fixtures. Search is case-insensitive.

## Local actor sessions and permissions

Harbor is a local simulator, not an authentication product. On first boot persist exactly three synthetic actors: `{id:"admin",name:"Avery Admin",role:"admin"}`, `{id:"operator",name:"Owen Operator",role:"operator"}`, `{id:"viewer",name:"Val Viewer",role:"viewer"}`. `GET /api/actors` is public. `POST /api/session {actorId}` selects one of those actors, returns `{actor}` and sets a random server-side `harbor_session` cookie, at least 32 characters, HttpOnly, SameSite=Lax, Path=/. `GET /api/session` returns `{actor}` or 401. `DELETE /api/session` revokes it on the server. A restarted server recognizes still-valid durable sessions. No client-supplied role or actor header grants permissions.

All authenticated actors can read. Admin and operator can edit projects, environments, runbooks, release drafts, submit/run/cancel/retry releases, create/update incidents and add notes. Only admin can approve/reject or rollback. A release author cannot approve their own submission, even if admin. Viewer writes return 403. Invalid protected-field overrides return 400 or are safely ignored; the server must never apply them.

## Projects and environments

Project fields `{id,name,slug,description,createdAt,updatedAt}`. Name and slug required; slug is lowercase letters/digits/hyphens, 2–40 characters, globally unique. `GET /api/projects?q=`, `POST /api/projects {name,slug,description?}`, `GET/PATCH/DELETE /api/projects/:id`. Delete is 409 while environments, runbooks, releases or incidents reference the project.

Environment fields `{id,projectId,name,protected,activeReleaseId,createdAt,updatedAt}`. Name required and unique case-insensitively within its project. `GET/POST /api/projects/:projectId/environments` and `GET/PATCH/DELETE /api/projects/:projectId/environments/:id`; create accepts `{name,protected?}` (default false). Do not permit client writes to activeReleaseId. Delete is 409 when releases reference it. Protected environments require approval; unprotected ones do not.

## Versioned runbooks and immutable release plans

A **step** is `{key,name,kind,dependsOn,durationMs,failureMode}`. Key is 1–32 lowercase letters/digits/hyphens, unique within a plan; name nonempty; kind is `check`, `build` or `deploy`; dependsOn is an array of distinct other step keys; durationMs is an integer 100–5000; failureMode is `never`, `once` or `always`. A plan has 1–12 steps. Reject unknown references, self-dependency, cycles and duplicate keys atomically. Steps are local simulation parameters, never executable code.

Runbook fields `{id,projectId,name,description,version,steps,createdAt,updatedAt}`. `GET/POST /api/projects/:projectId/runbooks`; create accepts `{name,description?,steps}` and starts version 1. `GET/PATCH/DELETE /api/projects/:projectId/runbooks/:id`; patch requires `{expectedVersion,...changedFields}`, increments version exactly once on success, and returns 409 for a stale expectedVersion. Rejected updates change nothing. Deletion is allowed because releases retain snapshots.

Release fields `{id,projectId,environmentId,title,versionLabel,notes,authorId,status,revision,runbookId,runbookVersion,steps,approvals,createdAt,updatedAt,submittedAt,startedAt,finishedAt,previousReleaseId}`. Status is `draft`, `awaiting_approval`, `ready`, `running`, `succeeded`, `failed`, `cancelled` or `rolled_back`. `GET /api/projects/:projectId/releases?status=&q=&environmentId=` filters; `POST` accepts `{environmentId,title,versionLabel,notes?,runbookId? ,steps?}`. Specify exactly one of runbookId or steps. The server copies the current runbook version and steps at creation; later runbook edits cannot alter any release. Version label is nonempty and unique within environment. New release starts draft, revision 1, author from session, approvals empty. `GET/PATCH /api/projects/:projectId/releases/:id`; patch requires expectedRevision and may change title, versionLabel, notes, steps only while draft; it increments revision. A step change clears runbookId/runbookVersion. Cross-project environment/runbook references are 404 with no partial write.

`POST .../releases/:id/submit {expectedRevision}` freezes the plan and increments revision. Protected environment → awaiting_approval; other → ready. `POST .../:id/approve {expectedRevision,decision:"approve"|"reject",comment}` is admin-only, requires awaiting_approval and a nonempty comment. Self approval/rejection is 409. Record immutable `{actorId,decision,comment,createdAt,revision}`. Approve → ready; reject → draft, increment revision, retaining the decision history. Submitted/running/completed plans cannot be edited. A rejected draft can be edited and submitted again.

## Durable jobs, idempotency and bounded workers

`POST .../releases/:id/run {}` requires ready and an **Idempotency-Key** header (1–100 printable characters). Atomically persist one job per snapshot step and set release running. Return `{release,jobs}`. An exact retry with the same actor, key, path and JSON returns 200 with the original run response, even after completion/restart; no duplicate jobs, artifacts or audit records. Reusing a key for a different path/body is 409. Persist the idempotency receipt. A different key cannot run an already-started release. Concurrent identical requests must admit only one run.

Job fields `{id,releaseId,stepKey,name,kind,dependsOn,status,attempts,recoveryCount,startedAt,finishedAt,error}`. Status `queued`, `running`, `succeeded`, `failed`, `blocked`, `cancelled`. `GET .../releases/:id/jobs` returns `{jobs}`; `GET /api/jobs?status=&projectId=` returns `{jobs}`; `GET /api/jobs/:id` returns `{job}`. Job steps use job IDs in dependsOn. A job starts only after all dependencies succeeded. `WORKER_LIMIT` (default 2, valid 1–4) globally bounds running jobs across every release. Execute the requested delay asynchronously, no busy wait. Attempts increments when a job starts. `never` succeeds; `once` fails its first attempt only; `always` fails every attempt. Success writes exactly one artifact for that job's successful attempt. A failed dependency eventually makes descendants blocked, never executed. Once no queued/running jobs remain, release succeeds only if all jobs succeeded; otherwise failed unless explicitly cancelled. On success set environment.activeReleaseId and capture its previous active release in previousReleaseId.

On startup recover persisted running jobs by changing them to queued, increment recoveryCount, preserve prior attempts, append a `recovered` log and audit event, and resume scheduling. Queued jobs also resume. Completed jobs/artifacts must not rerun or duplicate. Lost timers must not strand a running release. State transitions and job admission must be atomic enough that concurrent requests cannot exceed capacity, start a job twice or create duplicate artifacts.

`POST .../:id/cancel {reason}` requires running and a nonempty reason. Cancel queued/running jobs and the release; preserve succeeded jobs and artifacts. A delayed worker completion cannot overwrite cancellation. `POST .../:id/retry {}` requires failed; requeue failed and blocked jobs, preserving successful jobs, attempts and artifacts, set release running. Retried fail-once steps then succeed. Cancelled/succeeded releases cannot retry.

`GET /api/jobs/:id/logs` → `{logs:[{id,jobId,sequence,event,message,createdAt}]}` ordered by contiguous per-job sequence starting 1. Events include queued, started, succeeded, failed, blocked, cancelled, recovered as applicable; logs are append-only. `GET .../releases/:id/artifacts` → `{artifacts:[{id,jobId,releaseId,name,size,sha256,createdAt}]}`. `GET /api/artifacts/:id/content` returns plain text bytes, with `Content-Disposition: attachment; filename="..."`. Each generated artifact contains release versionLabel and step key; size and SHA-256 match exact downloaded bytes. Names are safe basenames. Unknown resources 404; no arbitrary file path parameter.

## Rollback, incidents and history

`POST .../releases/:id/rollback {reason}` is admin-only, requires nonempty reason, succeeded status, this release currently active in its environment, and a previously succeeded release in that environment. Atomically restore activeReleaseId to previousReleaseId, mark this release rolled_back and retain all jobs/artifacts/history. Repeat or non-active rollback is 409. No jobs are actually deployed.

Incident fields `{id,projectId,environmentId,releaseId,title,severity,status,summary,resolution,version,createdBy,createdAt,updatedAt,resolvedAt}`. Severity `sev1`, `sev2`, `sev3`; status `open`, `mitigated`, `resolved`; initial open/version 1. `GET/POST /api/projects/:projectId/incidents`, filter GET by status, severity, q. Create accepts `{environmentId,releaseId?,title,severity,summary?}`; release must belong to the same project and environment. `GET/PATCH .../incidents/:id`; patch requires expectedVersion and supports title, severity, summary, status, resolution. Allowed transitions open→mitigated/resolved, mitigated→open/resolved, resolved→open. Resolving requires nonempty resolution in that request, sets resolvedAt; reopening clears resolvedAt. Stale version is 409 and atomic. `GET/POST .../incidents/:id/notes`; create `{body}` nonempty, max 4000; return `{note:{id,incidentId,actorId,body,createdAt}}`. Notes are immutable and durable. Include incident creation/status changes and notes in its chronological timeline: `GET .../incidents/:id/timeline` → `{events:[{id,type,actorId,message,createdAt}]}`.

`GET /api/audit?projectId=&type=&after=` → `{events:[{id,sequence,projectId,actorId,type,entityId,details,createdAt}]}` ordered ascending by globally increasing durable sequence; `after` is an exclusive sequence cursor. Record successful project/environment/runbook/release changes, approval decisions, each job transition/recovery, rollback, incident transitions and notes. Details must be structured JSON. Rejected requests and exact idempotent replays create no success events. `GET /api/dashboard` → `{counts:{projects,environments,activeReleases,runningJobs,openIncidents,failedReleases},recentEvents:[...]}` reflecting actual persisted state; activeReleases counts environments with non-null activeReleaseId, openIncidents counts open+mitigated. `GET /api/projects/:projectId/export` returns JSON `{project,environments,runbooks,releases,incidents}` with snapshots and no sessions/internal database fields.

## Complete browser product

Provide a coherent responsive console with persistent navigation **Overview**, **Projects**, **Runbooks**, **Releases**, **Jobs**, **Incidents**, **Audit** and an accessible actor selector labelled **Actor**. Show current actor/role and useful permissions. Every required workflow must be usable without hand-written HTTP, pasted JSON or developer tools. Use meaningful labels, native inputs/selects or equivalent accessible controls, visible focus, keyboard activation, dialog/form error feedback, loading/empty states, and prevent accidental double submission. User-entered text is rendered as text, never HTML. Inline error feedback must preserve entered form values. At 390px viewport there is no page-wide horizontal overflow, primary navigation/actions remain reachable, and job/release details remain readable. All data and refresh/polling come from the real API.

- **Overview**: live counts, recent audit, links to active work.
- **Projects**: searchable list, project create/edit/detail, environment create/edit including protected flag, project export download. Select a project for scoped screens; preserve it on reload/deep links.
- **Runbooks**: list, create/edit with version display, structured step editor (key/name/kind/dependencies/duration/failure mode), visible validation of invalid DAG, optimistic conflict feedback.
- **Releases**: project/environment/status/search filters, draft create from runbook or structured steps, detail with immutable step graph/dependency labels, snapshot/version/revision, notes and approval history, draft editing, submit, approve/reject with comment, run, cancel with reason, retry, rollback with reason, current active indicator and useful unavailable-action explanations. Jobs appear with live states, attempts/recovery counts, ordered logs and artifact download links. Link a release to its incidents.
- **Jobs**: global project/status filters, live queue and worker usage, job details/logs linking back to release; completed artifacts are discoverable.
- **Incidents**: searchable/filterable list, create with project environment/optional matching release, detail edit and status transitions, resolution/reopen, add notes, chronological timeline and release link.
- **Audit**: project/type filter and readable chronological event details; no fabricated fixture events.
