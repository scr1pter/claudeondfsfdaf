# Harbor accessible interaction contract

This public contract makes browser verification reproducible without requiring a particular component library, CSS selector or layout. Include this file with `BUILD_SPEC.md` in every participant workspace. The independent verifier uses accessible roles, labels and text; equivalent visual design remains open.

- The persistent navigation has links named exactly `Overview`, `Projects`, `Runbooks`, `Releases`, `Jobs`, `Incidents`, `Audit`. The native actor selector is labelled `Actor`, with values `admin`, `operator`, `viewer`. A native project selector labelled `Project` chooses the project on scoped screens. Selecting an actor immediately establishes the corresponding session.
- Create/edit forms may be inline or dialogs. Buttons opening create forms are `New project`, `New environment`, `New runbook`, `New release`, `New incident`. Form submission buttons are `Save project`, `Save environment`, `Save runbook`, `Save release`, `Save incident`.
- Project inputs: `Project name`, `Project slug`, `Project description`. Environment inputs: `Environment name`, checkbox `Protected environment`. Project details open through a link with the project's name; an environment editor opens through a button `Edit environment <name>`. A project editor opens through `Edit project`.
- Runbook inputs: `Runbook name`, `Runbook description`. The structured step editor starts with one step. `Add step` adds one. For step N (one based), labels are `Step N key`, `Step N name`, `Step N kind`, `Step N dependencies`, `Step N duration`, `Step N failure mode`. Dependencies are a text field containing comma-separated step keys. Native kind values are `check`, `build`, `deploy`; failure values `never`, `once`, `always`. The runbook name links to its detail/editor. `Edit runbook` opens its editor.
- Release inputs: `Release title`, `Version label`, `Release notes`, native `Environment`, native `Runbook` with an empty/custom choice. An empty runbook enables the same structured step editor. Release titles link to detail. `Edit release` opens the draft editor. Actions are buttons `Submit for approval` (also used for unprotected submission), `Approve release`, `Reject release`, `Run release`, `Cancel release`, `Retry release`, `Rollback release`. Approval/rejection accepts `Approval comment`; cancellation/rollback accepts `Action reason`. A confirmation form may appear after action selection; its final button is `Confirm approve`, `Confirm reject`, `Confirm cancel`, or `Confirm rollback` respectively. Details visibly display status, version label, revision, step keys, job state, attempts, recovery count and history. Successful artifact downloads are links named `Download <artifact name>`.
- Incident inputs: `Incident title`, native `Incident environment`, native `Related release` with empty choice, native `Severity` values `sev1`, `sev2`, `sev3`, `Incident summary`. Incident titles link to detail. `Edit incident` opens an edit form, whose native `Incident status` values are `open`, `mitigated`, `resolved`; `Resolution` accepts resolution text. Notes use `Incident note` and `Add note`. Details visibly show timeline notes and current status.
- List filters are labelled `Search projects`, `Search releases`, `Release status`, `Search incidents`, `Incident status filter`, `Severity filter`, `Job status`, `Audit type` as applicable. Text filters may submit on input or with a `Search` button. Native status filters include an empty/all choice. Audit entries include their type in visible text.
- Project detail offers a link `Export project`. Release details have a `View jobs` link to its jobs section or screen. Individual jobs have a link using their step name and a detail view that displays log events. Every entity detail must survive browser reload at its current URL.
- Every validation/error message is exposed in a visible `role="alert"` region. Do not use a browser-native JavaScript alert/confirm for operational actions. Current entity status may appear in ordinary visible text; an accessible status region for live updates is encouraged.

The verifier will create fresh synthetic data through these controls. API setup may create additional isolated fixtures, but browser workflow checks must themselves use UI interactions for their labelled mutations. No request interception, direct application state mutation or injected UI is used to make those checks pass.
