# cx-linear-authority-batch: one atomic read for each installation authority check

Branch `linear-authority-batch` (PR #124, worked locally as `cx-linear-authority-batch`). Codex opened it as a draft on 2026-11-24 and left it idle. For the Saturday 2026-11-28 v2 deadline this run took it over to finish and merge it. Vector everywhere stays dormant: `VECTOR_EVERYWHERE_ENABLED` stays off and no switch changes.

Files: `api/_lib/everywhere/identity.ts`, `packages/web/test/everywhere-authority.test.ts`, `packages/web/test/everywhere-journey-laptop-tracker.test.ts` and the test FakeStore in `packages/web/test/lib/everywhere-store.ts`.

## 2026-11-26, Linear's first thought came after 44 slow store commands

**Bug.** `checkInstallAuthority` read each guard with its own GET: the account-closed key, the Codium account tombstone, the exact install record and the install hold. The Linear adapter runs this check before every Linear API call (`assertAuthority` in `linear/adapter.ts`) and again in `linear/credentials.ts`. The Slack and Jira adapters use the same check. At the E12 model's 100 ms per store command, Linear's first thought after `created` came after 44 store commands, so 4,400 ms. That is past the adapter's declared `ackMs` of 4,000 ms. The everywhere deviations log recorded this as EV-20 deviation (e), a finding left for the lead. The separate reads also checked the four guards at four different moments, not as one state.

**Fix.** `checkInstallAuthority` passes the same guards to the existing read-only guard wrapper `authorizedScript` with a fixed program, `CHECK_INSTALL_AUTHORITY_SCRIPT` (`return 'current'`). The wrapper GETs every guard key in one atomic Lua run and answers `EVERYWHERE_AUTHORITY_CHANGED` when any guard moved. Any reply other than the exact string `current` fails closed with `PERSISTENT_STORE_UNAVAILABLE`. So does an unavailable store, and so does a guard key of the wrong type, because Lua's GET errors on it. The pre-check in `accountGuards` (the account-closed GET and the account-authority lookup) is unchanged. The test FakeStore answers the fixed program with `current` after its existing guard emulation.

**Tests.**
- web `test/everywhere-authority.test.ts`, "the read-only installation authority check sees changes to each guard at the store boundary": a live installation passes and writes nothing. Then, for the install record, the hold, the account-closed key and the tombstone in turn, a concurrent write lands as the check's EVAL is sent, and the check rejects with `EVERYWHERE_AUTHORITY_CHANGED`. A tombstone stored as a set fails closed with `PERSISTENT_STORE_UNAVAILABLE`.
- Same file, "the read-only installation authority check requires the fixed success reply": the replies `null`, `true`, `1`, `["current"]`, `"current "` and an object, and a store that goes down during the EVAL, all reject with `PERSISTENT_STORE_UNAVAILABLE`.
- web `test/everywhere-journey-laptop-tracker.test.ts` (L1 and L2): Linear's first thought now comes after at most 29 store commands. It must land within `min(10 s, ackMs)` on the server's clock, with every store command before it slow.

**Red before.** `identity.ts` was put back to origin/main, keeping only the exported constant so the FakeStore import resolves. Both authority cases fail, because the old reads send no EVAL. L1 and L2 fail with "Expected: <= 29, Received: 44". With the fix restored all of them pass.

**Mutation check.** With the `verdict !== "current"` check removed, "requires the fixed success reply" fails (1 pass, 1 fail). Restored, both pass.

**Lead ruling (EV-20 deviation (e)).** Of the options in the deviations log, the safest one that fully closes the finding is to make `ackMs` hold, not to keep the looser 10 s bound. After batching, the first thought takes 29 modeled commands (2.9 s), inside the adapter's 4 s `ackMs`. The journey test now asserts the stricter bound and a 29-command ceiling, so a regression in the number of authority reads fails. The modeled latency stays 100 ms per command. The open question about `prompted` events (198 commands in a probe, same log) is not part of this item and stays with the lead. The historical entry in `vector-everywhere-deviations.md` is left as written; this entry records how it was closed.
