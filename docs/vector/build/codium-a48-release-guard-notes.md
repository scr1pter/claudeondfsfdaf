# A48 Release Guard and incidents: implementation record

A48 builds on A47 (the webhook router, ops settings and the Worker client), A46 (the ops Worker and its report protocol)
and A37 (internal signatures and server phone alerts). It adds Release Guard's intake checks and its one revert pull
request, the Worker's report intake, incidents with snooze and "Fix it", the server's own GitHub App tokens, and the
`ops` provisioner that gives the Worker each account's plan. No GitHub, Cloudflare, Stripe or Supabase API was called:
the tests run the routes against a fake GitHub API and A46's own Worker code in memory. Readings of the contract are in
`codium-deviations.md` under "A48 Release Guard and incidents (4 Nov 2026)".

## What changed

| Area            | Change                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| App tokens      | `api/_lib/github-app-server.ts`: `withRepositoryToken({account, repositoryId, purpose, …}, use)` mints an installation token for exactly one repository (`check`: Contents and Metadata read; `revert`: Contents and Pull requests write, Metadata read), checks its permissions and that it sees only that repository, hands `use` a client bound to that repository (paths cannot leave it; only a `revert` token can write), revokes it in `finally`, and records it in `ops:audit:<account>` before the mint and after the revoke. `readGithubAudit(account)` reads the log.                                                                                                                                                                                         |
| Intake          | `api/_lib/release-guard.ts` `releaseIntake`, called by the webhook's ops handler after A47's checks: a recorded release is a duplicate (no token, no count); `.vector/ops.json` at the deployed commit must name the account's `opsId`, have `releaseGuard: true` and the same environment; one script claims the release and counts it against the plan's releases a day (dedupe before increment); then the Worker's `release`. The Worker unreachable gives the claim and count back; its refusal is recorded skipped and not counted. Release records keep the deployment's ref and the host's page (for the rollback link).                                                                                                                                         |
| Reverts         | `openRevert`: one claim per repository, environment and sha holds the outcome. With a `revert` token it reads the range (compare, the commit's pull requests), then opens GitHub's GraphQL `revertPullRequest` when the range is exactly one merged pull request, else a restore commit of the good release's tree on top of the deployed sha on `vector/revert-<sha12>` with a pull request, only while the target branch's head is the deployed sha. Never when a workflow file is in the range or the file list may be incomplete. `.vector/ops.json` on the target branch is read again before each write. An open pull request from an earlier try is reused. GitHub unreachable answers 503 so the Worker resends; after 8 tries the revert is left to the person. |
| Reports         | `POST /api/ops/worker` (`api/ops/worker.ts`, `bodyParser: false`): A37's signature under `ops`, then `api/_lib/ops-incidents.ts` `handleOpsReport`. Each event is taken once by its id (`ops:event:<account>`, recorded after it was handled). `monitor.down` opens an incident and alerts the phone (also while paused); `monitor.up` resolves it and says so; `release.regressed` opens an incident, decides the revert (binding, Release Guard on, usable plan, snooze) and alerts once; `release.passed` marks the release. Malformed or unknown events are skipped.                                                                                                                                                                                                 |
| Incidents       | `/api/ops/incidents` (`api/ops/incidents.ts`): GET lists incidents with what failed, any snooze, the commits a revert undoes, migration-path warnings and Undo (the pull request, or "open in GitHub" and the host's rollback link). ## Interfaces for later packages

- **A50** (ops UI and crons): the screens read `/api/ops/incidents` and `/api/ops/releases`. Undo's `pull-request` gives
  `url` and `number` for "open in GitHub" or the desktop's merge with the person's own sign-in; `manual` gives `openUrl`
  and `rollback {host, url}` ("Roll back in Vercel" when `host` is `vercel`). The readiness checks for `on-call` and
  `release-guard` are A50's (recommended: `opsConfigured()`, plus `githubServerConfigured()` for Release Guard). The guard
  holds an account with the Worker's `suspend`; the cleanup can rely on incidents expiring after 90 days and release
  records after 35.
- **A57**: `eraseAccountOpsRecords(account)` (`api/_lib/ops-incidents.ts`, both Stripe modes) with
  `eraseAccountOpsSettings(account)` and the Worker's `erase`. The `ops` provisioner already does all three on `closing`.
- **A59**: `registerOpsRunStarter((trigger) => startCloudRun(trigger))`, adapting Codex's answer to `{id, url?}`. Until
  then "Fix it" answers 503 `OPS_FIX_UNAVAILABLE`. The binding reader (`registerRepoBindingReader`) stays A47's hand-off;
  until it is wired no repository is bound, so no release is watched and every revert is `not-bound`.
- **A49** (Ship Desk) can reuse `withRepositoryToken` with a new purpose if it needs server reads, and `ops-records.ts`
  for its cards.

## P7 review fixes (5 Nov 2026)

- **Listing on the server.** New `api/_lib/ops-listing.ts` (`opsPerkOpen`, `requireOpsPerk`, `opsAllowedAccounts`):
  new ops work needs its perk in `listedPerks()`, or the account in `VECTOR_OPS_ALLOW_ACCOUNTS` (new env, for the
  owner's own try-out before listing). The deployment intake ignores an unlisted Release Guard (`not-listed`);
  `requireOpsCaps(account, perks, …)` now takes the perks a route serves (A47's routes: domains On Call or Release
  Guard, monitors On Call, repositories each perk they turn on).
- **A revert needs Release Guard on at Vector.** `decideRevert` checks `requireOpsService` and the listing before
  `openRevert`; either refusing records Undo as `manual` with the new `ManualReason` `off`, and no revert token is
  minted. The store being down still throws for a resend.
- **Undo's head commit.** `RevertOutcome` (opened) keeps `headSha`: GraphQL `revertPullRequest { … headRefOid }`, a
  reused open pull request's `head.sha`, or the restore commit Vector made (or found on its branch). `IncidentUndo`
  carries it when it is a full sha.
- **Fix runs.** `startIncidentFix` needs the incident's perk listed (On Call for a monitor, Release Guard for a
  release). `OpsCaller` now has `client` (the token's marker), and the incidents route refuses `fix` from an unmarked
  token with 401 `CODIUM_SIGN_IN_REQUIRED` unless `MODEL_PLAN_REQUIRE_MARKED_TOKENS=false`.
- **Tests** (`test/release-guard.test.ts`, 36 pass, 1 CI-only skip): Undo carries the head of the GraphQL revert, the
  restore commit and a reused pull request; the `ops` switch off and an unlisted Release Guard both leave `off` and mint
  no write token while alerts still go out, and listing it opens the revert again; a fix run refuses an unmarked token
  (snooze still works), refuses while unlisted, starts once listed, and takes an unmarked token under the legacy
  override. `test/github-webhook.test.ts` (27 pass): an unlisted Release Guard watches nothing. `test/on-call.test.ts`
  (30 pass, 1 skip): each route refuses its unlisted perk, Release Guard listed opens domains and its repositories but
  not monitors or Ship Desk, the allowlist opens the rest and the plan still decides, removing works regardless.
  `test/ops-fixture.ts` sets the allowlist for its accounts, clears `CODIUM_LISTED_PERKS` and
  `MODEL_PLAN_REQUIRE_MARKED_TOKENS` per world, gives pull requests head shas and repositories a visibility.
- No edits to `api/_lib/model-plan-*.ts` (`model-plan-config.ts`'s `modelPlanRequireMarkedTokens` is only imported).
