# A28: account plan state and billing controls

A28 follows A27's public listing and qualified catalog contract. The account card uses the existing authenticated billing endpoints and their authoritative server checks. It adds no account setting, live subscription, provider route, deployment or external service activation.

The card shows canonical plan names, state badges, month usage, renewal/end time and available daily or listed service meters. Missing usage remains unavailable. Ultra never acquires a daily meter from stale input. Service rows use the current status listing, and model/task estimates require explicit tier membership; an older unqualified catalog does not imply access to every model. Purchased/top-up rows and purchase controls are removed while the legacy status decoder remains compatible.

Upgrade actions state the full canonical new monthly charge and carry behavior before opening checkout. Downgrades use the existing scheduled change endpoint; Keep my plan removes only a scheduled change. Paused, ending, frozen, unknown or malformed control states cannot initiate another plan purchase. Explicit disabled service status also blocks new purchases even if public config is stale. Independent review identified that lower-tier scheduling must remain possible during a sales pause: the final helper preserves that no-new-charge control before purchase availability gates, matching the server. The actual click handler rechecks the selected offer, and an immediate ref guard prevents duplicate pending actions.

Payment recovery preserves the distinction already established in A20: a card failure opens Stripe's payment-method update flow, while `action_required`/`confirm-payment` opens the ordinary portal to complete invoice confirmation. Paused account cards show that single billing recovery action, Refresh and the pricing link. Signed-in paused visitors on `/codium` see Update card or Confirm payment instead of plan purchase buttons. Account identity is read only after mount, never embedded in public prerender props; failed reads keep purchase disabled and offer retry. Back/forward restoration refreshes status and listing, and older refresh results cannot overwrite the latest read. Preview rendering disables every billing action.

Public response decoding drops private fields and validates optional state, schedule, meter and entitlement fields independently. Unknown future financial controls keep the readable legacy balance but block changes. Billing requests use explicit endpoints and methods, reject redirects, and accept only the existing exact Stripe origins or a matching bounded schedule response. Authentication tokens remain in browser requests and are not part of the public pricing view.
