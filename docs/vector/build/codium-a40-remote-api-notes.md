# A40 Remote API: implementation record

A40 builds on A39 (the relay Worker and its ticket format), A37 (the internal HMAC, `VECTOR_PHONE_APP_ORIGIN`) and A16 (desktop tokens and revocation). No Cloudflare, Supabase, Stripe or Vercel call was made, and nothing was deployed. The tests run the API's routes against the real relay Worker and its Durable Object in memory (the relay package's own fakes, SQL on a real SQLite engine), so every ticket the API mints is checked by the relay's own code. Readings of the contract are in `codium-deviations.md` under "A40 Remote API (4 Nov 2026)".

## Interfaces for later packages

- **A41 (desktop) and A42 (phone)** get tickets from `POST /api/remote/ticket` and connect to its `url` offering `vector.v1` and the ticket. A computer sends its desktop token; the phone sends its website session from its own origin. A device id is 16 random bytes, base64url (22 characters), made once per device and kept; a revoked id is refused for good, so a device that is unpaired makes a new one to pair again. A phone refreshes in-band with a new ticket before `expiresAt`. A ticket minted in the same second as a "Disconnect all" can be refused (the relay compares whole-second issue times with the millisecond kill); a client that is refused with `REMOTE_REVOKED` asks for a new ticket once: the API refuses a revoked account, and the relay refuses a revoked device again.
- **A42** shows `GET /api/remote/devices`, `POST /api/remote/devices/:id/revoke` and `POST /api/remote/kill`, and should add `remote`'s readiness check to `perkServices` (probably `remoteConfigured()`) once the desktop and phone halves exist. It should also register the `remote` status meter (`{computers, limit}`, §4.11) where it cannot form an import cycle: registering it from `codium-provisioners.ts` would, because `model-plan-status.ts` imports the provisioners through `model-plan-account.ts`.
- **A57** gets erasure from the `remote` provisioner (`closing` → `erase`). It can also call `relayErase(account)` directly from its erase step; both are idempotent.
- **A59** registers Codex's reader: `registerCloudRunReader((account, input) => listCloudRuns(account, input))`, from a module the `cloud-runs` route imports (or by passing the reader in that route).
- **§4.17** "Vector everywhere" later calls `isComputerOnline(account)`.

## Not done

- `remote` has no readiness check in `perkServices` yet, so it cannot be listed: Remote is not usable until the desktop (A41) and phone (A42) halves exist. A42 adds it.
- The `remote` status meter (`meters.remote`) is not registered (see A42 above). The phone's Devices page already falls back to the plan's count.
- The API does not check the device count before signing; the relay enforces it on every connection from the ticket's count, which comes from the snapshot. `GET /api/remote/devices` marks the devices past the limit.
- The cloud-runs reader is not registered; A59 does it.
- Nothing was pushed or deployed.
