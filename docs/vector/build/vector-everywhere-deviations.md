# Vector everywhere: deviations from the build contract (vector-everywhere-spec.md)

## 2026-11-11, VE-00 (CI lane)

- **Push to main is filtered by a scope job, not by the trigger.** The contract asks for every push to `vector-everywhere`, and for pull requests and pushes to `main` with a `paths:` list. One `on.push` block cannot give one of its branches a path filter, and a path filter on the branch would skip the lane after a rebase onto main (the old and new tips differ only in main's files). So `on.push` lists both branches with no paths, `on.pull_request` carries the `paths:` list, and a small `scope` job compares a push to main (`git diff --name-only --no-renames before after`) against that same `pull_request.paths` list, read from the workflow file with Bun's YAML parser and globs. The typecheck and test jobs wait for its answer. A change it cannot list (a new ref, missing history) runs the lane. The patterns use only `*` and `**`, which GitHub's filter and Bun's globs read the same way.
- **The paths list is wider than 6.6's wording, to cover files the WPs name.** Added `packages/web/src/pages/everywhere/**` (VE-42's `everywhere/link.astro` sits in a folder that `everywhere*.astro` does not match), `packages/web/src/components/marketing/everywhere/**` (6.6's second bullet), `packages/app/src/components/settings-v2/everywhere*` (VE-41's `everywhere-model.ts` is not `.tsx`), `packages/web/test/**/everywhere*` and `packages/schema/test/**/everywhere*` (so test helpers such as the fetch guard count too), and the two main helpers the runner imports read-only, `packages/desktop/src/main/github-auth.ts` and `github-api.ts`, beside the api/\_lib helpers the contract names.
- **The lane has a test of its own.** The contract's test for VE-00 is "the lane itself". packages/cloud/src/workflow-compliance.test.ts is on the 6.4 avoid list, so the lane's shape and its two scripts (the scope rule and the test picker) are held by a new packages/web/test/everywhere-lane.test.ts, which runs both scripts against temporary git repositories with a stand-in `bun`. The picker runs it in CI like any other everywhere test, so the lane never runs empty.
- **The lane also runs workflow-compliance.test.ts.** The test workflow checks it only on pull requests and pushes to main, so the lane runs it on pushes to the branch too (one step, no edit to that file).
- **Redis is the Valkey image the other lanes use.** The test job's service is `valkey/valkey:7.2.14-alpine`, pinned by the same digest as vector-sharing.yml, exposed on 6379 with `VECTOR_TEST_REDIS_URL=redis://127.0.0.1:6379`.
- **Steps that only some packages need run only when those packages have everywhere tests.** ripgrep (engine and core network guards), the turbo build of the engine, core and app dependencies, and the Electron runtime for desktop tests are gated with `hashFiles` on their packages' everywhere test paths.

## 2026-11-11, VE-01 (shared types and limits)

Nothing in the contract was wrong about the code. These are the choices packages/schema/src/everywhere.ts makes where the contract leaves a detail open, so later packages read it the same way.

- **Ids.** A jid is `vej_` plus 22 lowercase Crockford base32 characters: 10 of creation time in milliseconds, then 12 random ones. Ids sort by time, and every character is allowed in `vector/ve-[0-9a-z]{12}`. Which 12 (or 8) characters a branch takes is VE-02's `branchFor`. Lease ids and offer `jti`s are 26 random characters of the same alphabet. Devices use Codium Remote's device id pattern, copied, since that file is Codium's. Account ids are the UUIDs `requireAccountUser` accepts.
- **Offer times are milliseconds**, like Vector's other signed tokens (`vct_`, `vdg_`). "exp − iat ≤ 30 s" is `exp - iat <= 30_000`.
- **Codes.** 4.1 item 1 says the laptop declines a GitHub handoff whose trigger comment changed but names no code: it is `trigger-changed`, which, like `busy`, is not lasting (the server answers `handled: false`). The refusal codes add the cases 3.8 and 4.4 refuse without naming a code: `not-linked` (answered with the link prompt), `external`, `guest`, `bot`, `automation`, `not-connected`, `shared-place`, `link-invalid` and `unsupported`.
- **Strict and lenient decoders.** Everything a computer sends (report, settle, claim, decline) and the parsed `InboundTrigger` refuse unknown fields; offer claims do too. `decodeJob` drops unknown fields instead, so a server that adds an optional field in a later version does not stop older desktops; the runner only reads what the decoder returns. A job of kind `stop` or `command` is refused, though the type keeps the contract's union.
- **GitHub carries no thread text.** A GitHub trigger or job must have an empty task and context and a `github` reference (4.1); other platforms may not carry a `github` reference, and only Linear and Jira may carry an `issue`.
- **Settle summaries** are also refused when they hold a fenced code block, beside the diff forms E4 names; `sanitizeReply` on the computer already refuses fences, so a real summary never has one.
- **Thread links** must be https on the platform's own host: github.com, slack.com and its subdomains, linear.app, and subdomains of atlassian.net. VE-13 widens Jira's if its re-read finds other site hosts.
- **Slack installation keys** take three forms: `slack:E…:T…` (a workspace in a Grid organisation), `slack:T…` (a workspace on its own) and `slack:E…` (an organisation-wide install). VE-11 picks which it writes.
- **A job's reply format** must be its platform's: Slack mrkdwn for Slack, Markdown for GitHub and Linear, plain text for Jira.

## 2026-11-11, VE-02 (pure policy and framing)

Nothing here contradicts the contract's intent. These are the places packages/schema/src/everywhere-policy.ts, packages/core/src/everywhere/frame.ts and publish.ts differ from the contract's wording or fill a gap it leaves, so later packages read them the same way.

- **`decideRoute` runs twice.** It answers `offer` when the laptop is eligible; the intake offers, waits up to 20 s and calls it again with the same facts and `offer: {claimed, declines, unanswered}`. When every computer declined for a lasting reason but the reasons differ, the refusal names one in the order `not-mapped`, `model-not-allowed`, `local-mode`, `off` (the computer closest to working).
- **GitHub handoffs hand back.** For platform `github` every outcome but a claim is `{action: "hand-back", code}`, which VE-10 answers as `handled: false`: the repository's own Actions run is the fallback (4.1), so Vector everywhere never queues, dispatches or posts a refusal for a GitHub mention. Identity there is the trigger comment's author id against the binder's id (`mayTrigger` row `github-laptop-first`).
- **The queue needs what the laptop needs, except being online now.** Step 7 lists only "connected in the last 30 days" and "Wait for my computer". A queued job ends up on the computer, so it also needs the requester allowed on that computer (E14), the `remote` perk and Remote configured. A refusal says which (`no-place` with `why.computer` of `not-seen`, `wait-off`, `not-allowed` or `no-remote`).
- **`no-place` names both routes.** `why.actions` is `none` (no Actions route yet: no port, source not enabled, no R-A4 or R-A9), `bind` (the route exists but the repository is not bound to the sponsor, the App is missing or the workflow is not in Codium mode) or `public`. Step 6 asks for a private repository, so `internal` and a failed read count as not private.
- **Replies are sanitized to plain Markdown, then written per platform.** `sanitizeReply` returns platform-neutral Markdown and `formatText` writes it as Slack mrkdwn (escaped), Markdown or Jira plain text. Sanitizing twice changes nothing, so the computer (before settle) and the server (in `renderResult`) both run it without double escaping.
- **Stricter or wider than the wording, on purpose.** Images are removed whatever their host. github.com links stay only when they point into the job's repository, on every platform, GitHub included. Mentions are wrapped in code on every platform, not only GitHub. Slack `<@…>`, `<!…>`, `<#…>`, Jira `[~…]` and Linear profile links are removed. E-mail addresses and HTML comments (a forged `<!-- vector:job … -->` among them) are removed. Entities are decoded and zero-width, soft-hyphen and direction characters removed before any check, so none of them can hide a mention, a link or a token.
- **File names are code, not domains.** A bare token with a source-file extension (`README.md`, `setup.py`, `Node.js`), or one followed by `(` (`config.load()`), is kept wrapped in code instead of removed; inside code spans nothing is linkified. Every other bare domain outside the allowed hosts is removed.
- **Withheld texts.** The contract gives the posting-check text. `WITHHELD.secret` and `WITHHELD.code` are the fixed texts for a summary withheld because it looked like a secret or held code.
- **Shared places get even less.** A shared-place result carries only the outcome line and the PR link: also no branch name, held-back count, checks line or `needs` list (they go in `privateText`).
- **`branchFor(jid, issue?)` takes `{key, platform}`**, not a bare key, because the key is lowercased for Linear and kept as written for Jira. It uses the jid's random tail (the last 12, or 8, characters), so two jobs in one millisecond get different branches.
- **`heldBack`.** `.github/`, `.husky/` and `.githooks/` are held back at the top level, as their globs say. `.gitattributes` and `.gitmodules` are held back at any depth (a nested `.gitattributes` also sets filters). Paths compare case-insensitively, with `\` as `/` and Windows' trailing dots and spaces removed.
- **`stripClosingKeywords` also covers issue keys.** Beside GitHub references to other repositories, a closing word before any issue key but the job's own (`Fixes ENG-9` on job ENG-123) loses its keyword, since Linear's integration closes on those words. The word list is GitHub's plus Linear's (`closing`, `fixing`, `resolving`, `complete…`). The keyword goes and the reference stays as code. Same-repository `#12` references stay, as the contract says.
- **PR template details.** The title is the commit subject, `<issue key> Vector: <the task's first words>`, with no mention, reference, link or markup. The issue line is `Fixes ENG-123` for Linear and `PROJ-123` for Jira, as the contract says, and `Refs #12` for a GitHub job, which the contract leaves open. `commitMessage` (subject, job id, `[skip ci]`) is here too, so the runner and the template share the title.
- **Framing inputs the job does not carry.** `EverywhereJob` has no thread link and a GitHub job no thread text, so `frameTask(job, {thread?, threadUrl?})` takes them. `thread` is required for GitHub (labels `writer` or `untrusted`) and refused elsewhere. A GitHub link comes from the job's reference. Other links are written only when `threadUrlAllowed` accepts them. The thread the computer read must fit the same limits as a job's context (VE-10 trims it).
- **Small additions VE-05 to VE-07 need, all pure.** `renderEnd` (`lost`, `expired`, `not-started`, and Jira's two 50-minute texts), `ROUTE_NOTES` for `renderMilestone` (`received` "On it.", `finding`, `laptop`, `actions`, `waiting`), `overLimit`, `queueDeadline`, `SECRET_PATTERNS` (for the desktop's staged-diff scan), and in frame.ts `OUTSIDE_KEY`, `UNATTENDED_KEY`, `unattendedMetadata`, `outsideMetadata` and `sessionTitle`. frame.ts keeps its own copy of the outside key, so it does not load Brain. Its test checks that the copy equals `BrainSchema.OUTSIDE`.

## 2026-11-11, VE-01 and VE-02 review fixes (phase P1a)

These change choices recorded above; where they differ, this entry wins.

- **The queue also needs the `remote` switch on.** Nothing can be offered through a relay that is switched off, so `decideRoute` refuses `no-place` instead of queueing, with a new `why.computer` of `remote-off` ("Vector Remote is paused, so no computer can take jobs right now."). `no-remote` still means no perk or Remote not configured, and is named first.
- **A claim is final.** On the second call `decideRoute` answers `laptop` for `offer.claimed` before identity, plan, caps, repository and laptop eligibility, since the jobs route already moved the job to `claimed`. Only the global switch at `stop` still refuses, as the claim route does; `no-new`, the platform switch, the `remote` switch, a lapsed heartbeat and a cap counter that now counts the job do not. `RouteInput.counts` holds the counts from before the job.
- **`sanitizeReply` cleans until the text stops changing.** Removing markup can join what it separated (a token split by `<b></b>`, a tag built by removing an empty link, a mention after a removed domain), so each pass runs again, at most 8 times (text still changing after that is withheld with `WITHHELD.code`), and the secret and code checks run on the result as well as the input. That, not a single pass, is why sanitizing twice changes nothing.
- **Entities, escapes and code spans read as a renderer reads them.** Entities are decoded until none is left, with invisible characters removed every round; text still decoding after 32 rounds loses every `&`. Code spans are rewritten to one backtick each side on one line (backslashes before a backtick and unpaired backticks go, touching spans get a space), and outside code a backslash before ASCII punctuation goes. This also closes two mention forms the review did not list: `\@name`, and a mention after two backticks that close nothing, both of which render as plain text.
- **Address shapes.** A scheme with one slash, a backslash or none (`https:/host`, `http:host`) and a scheme-relative `//host` or `\\host` count as links. A bare host counts after any character but a letter, digit, `_` or `@`, with at most 126 labels so long runs of dots stay linear. A dot-led name after a space (`.env.local`) is kept as code, and a relative path to a source file (`src/utils.ts`, `../a.md`) becomes one code span. Inside code, `//…` is left alone (code shows as written, so `//go:build` stays); scheme and `www.` addresses still go.
- **Definitions and images.** Link reference definitions go also behind blockquote and list markers, and shortcut and collapsed reference images (`![a]`, `![a][]`) go.
- **HTML.** Only tag-shaped text on one line is removed (`<name` followed by a space, a line end, `/`, `>` or the end), so `i<len`, `Map<string, User>` and later paragraphs survive. A tag with no attributes inside code stays (`Promise<void>`); every other tag goes, inside code too.
- **Mentions** count after `.`, `/`, `-` and `+` too, as GitHub reads them; `wrapMentions` leaves e-mail addresses alone.
- **`looksLikeCode`** treats CR, U+0085, U+2028 and U+2029 as line ends, ignores invisible format and control characters, and allows leading spaces, so the settle decoder refuses those diffs too (E4).
- **The result's checks line** speaks of the pull request only when there is a link, of the branch when a pushed branch has no PR, and is left out for a `held` result.
- **`stripClosingKeywords` keeps the words.** The reference becomes code and the closing word stays (``Fixes `ENG-9` ``), so `Fixed utf-8 decoding` keeps its sentence. Keys still match in any case rather than only uppercase, as the review suggested, so a lowercase key cannot slip through; a term that only looks like a key is shown as code.
- **Not done: a secret scan in `decodeSettle`.** The review offered it as optional. `decodeSettle` lives in everywhere.ts, which the policy module imports, and the server already sanitizes the summary again in `renderResult`.

## 2026-11-11, VE-03 (server foundation)

Nothing in the contract was wrong about the code except one type rule (the last item). These are the choices api/\_lib/everywhere/{config,keys,store,crypto,switch,audit,dedupe,signature,limits,after,fetch}.ts make where the contract leaves a detail open, so later packages read them the same way.

- **The data key and sealing.** `VECTOR_EVERYWHERE_DATA_KEY` must decode to exactly 32 bytes (standard or URL-safe base64, padded or not). A shorter, longer or malformed value, or a placeholder whose bytes barely vary (fewer than 8 distinct values, such as all zeros), turns the feature off. The key id is the first 12 base64url characters of a SHA-256 of the key, so no extra variable is needed, and a later rotation only adds a second key to the ring (`open` already takes a ring; `seal` uses its first key). A sealed value is `ves1.<key id>.<iv>.<ciphertext and tag>`, all base64url, and is bound to a context (its store key) passed as associated data, so a sealed token copied into another record does not open there. `open` tells `unknown-key` from `tampered` and `malformed`, and refuses non-canonical base64url.
- **Env reading.** `VECTOR_EVERYWHERE_ENABLED` is trimmed before it is compared with `true` (env editors add line ends). A secret shorter than 16 characters or with spaces in it counts as missing, which turns its platform off; the HMAC helpers also refuse such a secret themselves. Ids (`VECTOR_SLACK_APP_ID`, client ids, `VECTOR_JIRA_FORGE_APP_ID`) must be printable with no spaces, at most 200 characters. GitHub needs none of our secrets (the handoff's OIDC verifier is injected, VE-10 and VE-31), so listing it is enough. The offer key must be an Ed25519 PKCS#8 private key (`\n` escapes accepted) with a key id matching `OFFER_KEY_ID_PATTERN`; without both there are no offers, but the rest of the feature can run. `readConfig` also answers `problems`: the names of variables that are set but unusable or needed and missing, never their values. An explicit `false` is not a problem.
- **The switch.** The environment gives only `on` or `stop`; `no-new` comes from Codium's switch once R-C6 adds it. The seam calls Codium's `readSwitch` only when Codium's `SWITCH_NAMES` lists `everywhere`, so it starts working with no change here. Codium's value can only make the switch stricter; Codium's `off`, an unknown value and an unreadable store all read `stop`. Codium's `remote` switch reads `on` or `stop` the same way, and `stop` when it cannot be read. `admits(state, "new" | "running")` is the one rule: `new` is a new trigger at the intake; `running` covers a claim of an offered or waiting job, reports, heartbeats, settles, the dispatch of an accepted job and the re-offer of a waiting one, which matches the phase P1a rule that a claim is final.
- **The store guard.** `everywhereStore` refuses, before `persistentStore` sees it, any command outside a fixed list or touching a key that is not under `vector:everywhere:`, so this code can never read or write Codium's or anyone else's records. Every write names its TTL except the records 3.13 keeps until changed.
- **Keys.** Every part is checked against its id's shape and account ids are written lowercase. Ids whose shape a platform or peer chooses (delivery ids, Forge token ids, A2A task ids) are kept when they match `[A-Za-z0-9._-]{1,128}` and otherwise replaced by `~` and their SHA-256, which no plain id contains. Platform user ids have one pattern per platform (Slack `[A-Z0-9]`, Linear UUIDs, Jira account ids with at most one colon, GitHub numbers), so `link:<installation>:<user>` stays unambiguous.
- **The audit log is a sorted set by time**, not a list, so entries older than 90 days can be dropped by age. One Lua script adds the entry, drops entries older than 90 days, keeps the newest 1,000 and moves the log's expiry. An entry has exactly `id`, `at`, `event`, `platform`, `installation`, `jid`, `code`, `device`, `actor` and `userId`; any other field is refused. `code` comes from a closed list (refusal, decline, outcome, route, job state and ending codes, erase reasons, and `admin` for a re-install by a platform admin), so no free text can travel in it. Events add `uninstall` and `disconnect` to the contract's list.
- **Cap counters.** Day and hour windows are UTC calendar windows (`d20261111`, `h2026111114`), and each counter expires a minute after its window ends. Live jobs are the size of `jobs:<sponsor>`, which VE-05 keeps. `readCounts` gives `decideRoute` the counts from before the job; `countJob` checks every cap again and counts the job in one Lua script, so two jobs arriving together cannot both take the last place.
- **Dedupe.** A delivery whose work never finished is not released by a call: its `pending` mark simply expires after 60 seconds, in time for the platform's retry. `useOnce(store, key, ttl)` is the same `SET NX` for single-use ids (Forge token ids, offer ids, GitHub handoffs).
- **`after()`.** "Runs inline where none exists" is read as: without a Vercel request context the work still starts at once in this process. `after` answers a promise that never rejects, so a caller can await it, and `drainAfter()` waits for every running step, for tests and the sweep. A failure is logged with the step's fixed name and an error code only.
- **`platformFetch` also checks paths.** Beside the host list, each host has its allowed paths: `slack.com` `/api/`; `api.linear.app` `/graphql` and `/oauth/`; `api.github.com` any path; `api.atlassian.com` `/ex/jira/` (the Forge remote's API base URL); and `forge.cdn.prod.atlassian-dev.net` `/.well-known/jwks.json` only (the Forge Invocation Token keys, which VE-13's fit.ts pins). Paths with encoded dots or slashes are refused. Only https on the default port with no user name or password; redirects are always errors, even when a caller asks to follow them; calls time out after 10 seconds unless the caller passes a signal. `readPlatformJson` reads at most 1 MiB. VE-11 to VE-13 re-check these hosts and paths against the platform pages.
- **Tests beyond the contract's list.** packages/web/test/everywhere-{keys,limits,after}.test.ts, and two helpers, packages/web/test/lib/everywhere-fetch-guard.ts (fails the test on any request off 127.0.0.1, localhost or [::1]) and packages/web/test/lib/everywhere-store.ts (an in-memory store behind the Redis REST API that knows the everywhere scripts by their exact text, and a bridge to the CI Redis). The lane's `packages/web/test/**/everywhere*` path covers both. Cases needing a real Redis (concurrent claims of a delivery and a single-use id, the audit and count scripts) skip locally without `VECTOR_TEST_REDIS_URL`.
- **A type fix in VE-02's policy module.** The root tsconfig that checks api/ turns on `noUncheckedIndexedAccess`, which the schema package's tsconfig turns off, so importing everywhere-policy.ts from api/ failed the api typecheck in `stripTags`. `codeRanges` now declares its tuple return type. No behaviour changes; packages/schema/test/everywhere-policy.test.ts passes as before.

## 2026-11-11, VE-04 (identity, links, installs and mappings)

Nothing in the contract was wrong about the code. These are the choices api/\_lib/everywhere/identity.ts, erase.ts and account-api.ts and the routes api/everywhere/{link,links,installs,repos,oauth-finish}.ts make where the contract leaves a detail open.

- **Files beyond the list.** api/\_lib/everywhere/erase.ts (the erase module R-C9 names), api/\_lib/everywhere/account-api.ts (the five handlers, built from injected dependencies; each route file is one line), and packages/web/test/lib/everywhere-account.ts (an account service fake, a loopback route harness and a Jira permission fake, all on 127.0.0.1). The VE-03 fake store gains sets, `GETDEL` and the two new scripts. store.ts gains `takeValue`, `takeJson`, `setMembers`, `addMembers` and `removeMembers`, and `swapValue` can also delete.
- **Keys beyond 3.13.** `linked:<installation>` (user ids linked there), `repos:<installation>` (mapped places), `linkcodes:<account>` (the hash of the account's one live code) and `linktries:<installation>:<user>` (failed attempts, one hour). Each index set is written before its record and an entry whose record is gone or points elsewhere is ignored, so erasing finds every record without scanning the store.
- **"A session whose platform identity differs."** A link code is made for one platform (required) and, when the page names it, one installation. Redeemed from another platform or installation it is refused (`link-invalid`) and used up. For Linear the OAuth state plays the code's part (single use, 10 minutes) and the sign-in must finish from the account that started it. A code forwarded to another person on the same platform still links, because both proofs pass; the defence there is the contract's notices: the platform user's private notice names the account's masked e-mail, and the account gets an e-mail and an audit entry, which the page shows with an unlink button. The tests say so.
- **Codes.** Stored as an HMAC-SHA256 under the data key, not a plain SHA-256, because an 8-letter code has only 40 bits. The alphabet is the digits and capitals without I, L, O and U; a typed O, I or L reads as 0, 1 or 1; codes show as groups of four with hyphens. Connect codes have 12 letters. Only an account's newest link code works, so making one ends the older. Every attempt that names a live code uses it up, whatever the answer. After 10 failed attempts in an hour a platform user is refused before any code is read.
- **The link notice.** The e-mail goes through the site's existing mail sender (`RESEND_API_KEY`, `VECTOR_PURCHASE_EMAIL_FROM`) when both are set; otherwise the audit entry is the only notice. It names the platform, the user id and the installation, never a display name. The account's e-mail is sealed into the code record for the code's 10 minutes and kept nowhere after. A failed send is logged by code and never undoes the link.
- **Moving a link.** A platform user who redeems another account's code moves the link, and the old account's log gets `unlink` with code `unlinked`. Linking again to the same account changes nothing and sends no second notice.
- **Installs.** The OAuth state may name the installation the install started for; an exchange that lands elsewhere is refused (`EVERYWHERE_WRONG_PLACE`, 4.2). The platforms' exchanges (Slack's install at VE-11, Linear's install and sign-in at VE-12) plug into `createAccountApi({exchanges})`; without one the finish answers 501. The authorize URLs and scopes are in `OAUTH` for VE-11 and VE-12 to re-check against the platform pages. A Jira connect code's issuer passed the ADMINISTER check, so redeeming one for a site another account connected changes the connector, as an admin's re-install does. The connect code and install records may carry the Forge installation id, for VE-13's token check.
- **Mappings.** (The `repo` word was narrowed by the phase P1b review entry below.) The record keeps 3.13's field names, with `null` in `repositoryIds` for an id not known yet: the `repo owner/name` word gives only a name, and VE-11 resolves the id. At most 20 repositories, each name once. The word is accepted from any linked person (not a bot, automation, external user or guest) on a connected installation, because at launch the sponsor is the requester's own linked account; the place keeps its private mark.
- **Routes.** While the feature is off every route answers 404 before the sign-in check and before any store read. Issuing a code, starting an install and finishing one also need the platform on. A link, installation or mapping that is not the caller's answers 404 rather than 403, so no route says whether someone else's exists. Bodies go through `requireTrustedJsonRequest` (origin and content type) and are at most 8,000 bytes. No route returns a token, a sealed value or a code's hash.
- **Erase.** (The order was changed by the phase P1b review entry below: the record goes last.) The installation record goes first (nothing new links to it), then live jobs, links (each linked account's log gets `unlink` with the reason, except an account being deleted) and mappings. The connector's log gets `uninstall` for `uninstalled`, `tokens-revoked` and `revoked`, and `disconnect` for `disconnected`. Live jobs are erased through the `JobEraser` seam, which VE-05 passes to `createAccountApi` and `EVERYWHERE_ERASE_PART`; until then there are no jobs. Account erase also deletes `jobs:<account>`, `seen:<account>` and the audit log. Revoking a platform token on disconnect is an optional `revoke` hook for the adapters (VE-06, VE-11); erase needs no data key.

## 2026-11-11, VE-05 (jobs, offers and leases)

Nothing in the contract was wrong about the code. These are the choices api/\_lib/everywhere/{jobs,offer,jobs-api}.ts and the routes api/everywhere/jobs/{claim,decline,report,settle,pending}.ts make where the contract leaves a detail open, so VE-06, VE-07 and VE-10 read them the same way.

- **Files beyond the list.** api/\_lib/everywhere/jobs-api.ts holds the five handlers, built from injected dependencies (environment, store, clock, Codium's switches, event hooks); each route file is one line, as VE-04's are. The test fake store gains the two job scripts and `ZREM`, `ZSCORE` and `ZRANGEBYSCORE … LIMIT`; the route harness gains `mount` and request headers.
- **How the fence works.** A job record is JSON whose first two fields are always `version` and `state`. The server computes the next record in TypeScript from the record it read, and one `EVAL` writes it only while the stored record still starts with that version and state (read with a fixed Lua pattern, so no JSON library is needed in the script). The same script moves the job in `jobs:due`, takes it out of the live sets when it ends and deletes its body then. A change that lost the race reads again and decides again, up to 8 times, then answers 503 `EVERYWHERE_BUSY`.
- **Keys beyond 3.13.** `livejobs:<installation>` (live jobs on an installation, so erasing it needs no scan) and `history:<account>` (every job the account sponsored in the last 30 days, for the job list and for account erase). `seen:<account>` holds `{at, device}` and `ready:<device>` holds `{account, at, …booleans}`, so the router reads "Wait for my computer" from the last computer seen.
- **Edges the diagram does not draw.** (The release after a claim was replaced by the phase P1b review entry below: a decline after a claim always refuses.) A decline after a claim (with its lease) refuses the job when the reason is lasting, and otherwise releases it: `claimed → offered`, so the intake (still in its window) or the sweep moves it on. A late claim of a job that just went back to the queue is allowed (`waiting → claimed`). Safety nets for a dead intake: `received` for 2 minutes ends `expired`, and an `offered` job past its 30-second offer goes back to `waiting` when it has a queue (`queueUntil`, kept on the record while claimed so a release can return to it), otherwise `expired`. An Actions run still `running` 135 minutes after it started (@vector's longest run of 120 minutes plus its publish step) ends `failed` until VE-30 settles it from `listCloudRuns`. A laptop job past its deadline is answered `stop`.
- **Endings.** A waiting Jira job ends with Jira's own text (`jira-waiting`), others with `expired`; `lost` and `not-started` as the contract says. Endings are audited as `settle` with the job's end state as the code.
- **The device on report, settle and pending** comes from the header `x-vector-device`, because Report and Settle refuse every field outside their shapes. A report or settle whose header or lease differs from the claim's is 409 `LEASE_MISMATCH`; a missing or malformed header is 400.
- **Answers.** claim: 200 `{job}`, or 409 `JOB_TAKEN`, `JOB_EXPIRED` or `EVERYWHERE_STOPPED` (`action: "stop"`). report and heartbeat: 200 `{action: "continue", leaseExpiresAt}`, `{action: "stop"}` (switch, cancelled job, deadline) or `{action: "lost"}`; 409 `JOB_ENDED` for a job that ended otherwise. settle: 200 `{settled: true}`; the same settle again answers the same and tells nobody twice. decline: 200 `{recorded}`. pending: 200 `{offers, waiting}`.
- **Switches.** With the feature off every route checks the token's signature and then answers `stop` with no store read. Under Codium's `stop` claims are refused, reports, heartbeats, settles and declines answer `stop`, and the call sweeps the account with `stop`: waiting, received and offered jobs expire and the rest are cancelled, so a computer's next report hears `stop` and nothing is pushed. `no-new` lets every jobs call through.
- **pending.** `GET` with the readiness booleans as query flags (`jobs`, `remote`, `local`, `sandbox`, `wait`, `room`, `projects`; `wait` defaults on, the rest off) and the device header. "The project allowed for this place's repository" is not one boolean, so the computer sends `projects` (at least one project allowed) and a `not-mapped` decline says the rest. Re-offering a waiting job moves it to `offered` and answers the signed offers in the response, so a computer picks waiting jobs up over HTTPS with no relay; VE-06 may also push them through the `offer` port. A computer that does not take jobs, or has Vector Local on, is offered nothing and the job keeps waiting.
- **What the server sends a computer.** `limits` are the highest a computer's settings accept ($50, 120 minutes, the deadline 120 minutes after the claim); for Jira the deadline is the earlier of 35 minutes after the claim and 50 minutes after intake. `reply.maxChars` is the summary limit, 1,500. The requester's sanitized display name lives in the sealed body (2 hours), not the 30-day record, which keeps ids only.
- **Stricter than the wording.** A settle's `branch` must be the job's own (the rule of core everywhere/publish.ts `branchFor`, repeated here because api/ cannot import core) or it is 400. `createJob` runs the computer's own `decodeJob` on a stand-in lease, so a job a computer would refuse is never made, and it checks the live cap of 3 inside its script, so two jobs created together cannot both take the last place (limits.ts `countJob` still counts the day and hour windows first; a refusal here leaves them one higher).
- **Offers on the server.** `signOffer`, `verifyOffer` (key id, signature, audience, account, at most 30 s of life, not expired, not dated more than 30 s ahead, and the `jti` used only after everything else passed), `offerJtiStore` (`offer:<jti>`, 1 hour) and `offerPublicKey`/`offerVerifyKey` for the raw 32-byte key VE-21 pins in `OFFER_KEYS`.
- **Hooks for VE-06.** `createJobsApi({events})` calls `claimed`, `declined`, `reported`, `settled` and `ended` after the response (`after()`), with the job record; a claim that found the body gone and the lazy sweep's endings go to `ended`. The production export has no hooks yet: VE-06 builds it with the adapters' events.
- **Erase.** jobs.ts `jobEraser` is now the default `JobEraser` of the account routes (VE-04) and of `EVERYWHERE_ERASE_PART`. Erasing an installation cancels its live jobs and deletes their bodies; erasing an account also deletes every job record and body of its 30-day history and its last computer's readiness.

## 2026-11-11, VE-03 to VE-05 review fixes (phase P1b)

These change choices recorded above; where they differ, this entry wins. Two of them are places where the contract was wrong about the code (the first two items).

- **The erase part has Codium's shape (contract wrong about the code).** R-C9 writes the part as `{id: "everywhere", erase: eraseEverywhereAccount}`, but Codium's `ErasePart` (codium-erase.ts, at the contract's codium tip and on origin/codium) is `{id, configured(), requires?, erase(account, {fetcher, now, deadline?})}`, and Codium calls `configured()` before its try. `EVERYWHERE_ERASE_PART` now has `configured` (true whenever the store's URL and token are set, as `persistentStore` reads them, so an account's records are erased even after the feature was switched off) and an `erase(account, context)` that uses the deletion's fetcher and clock. erase.ts repeats Codium's context type as `CodiumEraseContext`, since this branch cannot import Codium's file. The registration line in codium-erase.ts stays Codium's (R-C9).
- **`ready:<account>:<device>` (contract wrong about the key).** 3.13 names the readiness record `ready:<device>`, but the device id is the client's own choice, so one account could write over or delete another account's record by naming its device id. The key now holds the account too; the record, its 1-day life and what reads it are unchanged.
- **A claim is final.** After a claim, a decline with the lease ends the job `refused` with the decline's reason, whatever it is, from `claimed` and from `running`. Nothing releases a job back to `offered` any more, so no other computer and no Actions run can take a job a computer held (3.4, E8); for a GitHub handoff the job's end answers `handled: false` and @vector's own run goes on. The claim drops `queueUntil` (nothing returns to the queue after a claim), and `dispatchJob` also refuses any job that carries a claim's marks (`claimedAt` or `device`). This replaces the VE-05 item that released a job after a decline that was not lasting.
- **Dispatch writes the ticket first.** `ticket:<hash>` is written before the `dispatched` transition, so a dispatch that went through is always found by the start hook. A ticket left by a dispatch that lost starts nothing, because `startDispatched` requires the job to be `dispatched` with that very ticket.
- **Audit appends after a committed change are best effort.** Every jobs.ts audit entry that follows a written transition (create, offer, queue, dispatch, claim, decline, settle, refuse, cancel, the sweep's endings) is caught and logged by step, job id and error code. Otherwise a failed append answered 503 after the change was written, and the retry found the job already moved, so the result, the progress or the fixed reply was never posted.
- **One bad record stalls nothing.** The sweep (`sweepDue`, `sweepAccount`) and `offerWaiting` handle each job on its own and log a failure by job id and code. A job whose record is gone (expired before any sweep, or erased) leaves the index being swept, and `jobs:due` too, and its body goes, so it no longer comes back or holds a place under the live cap. A record that does not decode keeps its place: it may be a newer deployment's live job after a rollback, and dropping it from `jobs:due` would strand it once the newer code is back. Erasing deletes such a record: an installation erase deletes it from its live index, and an account erase deletes it with the history. Not done: `decodeJobRecord` still refuses unknown fields rather than dropping them, because this code writes back the record it decoded, and that would remove a newer deployment's fields.
- **The `repo` word is Slack's only, and only for an allowed requester.** `setMappingByWord` refuses Linear and Jira installations (`wrong-platform`), where the connector sets mappings on vectordev.ai. The caller passes `maySponsor` (the intake's perk check, or `sponsorListed` before the perk exists), and a linked account that may not sponsor runs is refused `not-allowed`. A mapping the connector set changes only by the connector's own word (`not-connector` for anyone else). A mapping another requester set may still be changed, as 3.8's "or an allowed requester" says. This replaces the VE-04 item that accepted the word from any linked person.
- **Erasing an installation removes its record last.** Live jobs, links and mappings go first, then the record with its place in the connector's list, then one more pass over jobs, links and mappings for anything written by a call that passed its installation check just before the record went. If a step fails, the record stays, so the disconnect (which still finds its connector), the platform's retry or the account deletion's next pass runs the erase again. This replaces the VE-04 item that removed the record first.
- **The lane's paths list api/\_lib/abuse.ts.** jobs-api.ts and account-api.ts import `requireTrustedJsonRequest` from it. The lane test now also works out, from the relative imports of api/\_lib/everywhere/\*\* and api/everywhere/\*\*, every file outside those folders that the server code imports, and requires each one in the paths, so the hand-kept list cannot fall behind again.
