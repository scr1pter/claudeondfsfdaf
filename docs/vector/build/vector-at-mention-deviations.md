# @vector build: deviations from the contract

The contract is [vector-at-mention-spec.md](./vector-at-mention-spec.md). Record here every correction that keeps the contract's intent, in the same commit as the code that needs it, newest last. Use one heading per package, `## <YYYY-MM-DD> <package id> (<package title>)`, and number each item. Say what the contract said, what was built instead, why, and which later packages or lanes it affects.

The first section is different: it lists where the contract itself departs from the Codium contract's §4.18 amendments and related SPEC text (`origin/codium:docs/vector/build/codium-build-spec.md`). It was written with the contract, before V00, so the owner and the Codium lane can see every departure in one place. Packages do not record these again.

## 2026-10-30 Contract (departures from SPEC §4.18 decided before V00)

1. **Amendment 2, "add a `run` audience".** The contract adds two per-endpoint audiences, `mint` and `bind` (spec 2.10), so a bind token can never mint and a mint token can never bind. The intent (a dedicated audience for run credentials, separate from `token` and `installation`) is kept. A59 needs no audience change.
2. **Amendment 9, "a per-run key the server gives after the OIDC check".** Session artifacts are encrypted under a key per conversation (thread) and binding generation, given only to a valid run token whose signed `thr` claim names that thread (spec 2.8, V27, INV-P5). A per-run key could not decrypt the previous run's session, which is the point of the artifact. Privacy copy says "encrypted per conversation".
3. **Amendment 10, "free a slot when the same check run mints again".** A second mint from a live check run renews the token in place: same reservation, same start and deadline, new `jti`, no extra charge, and the earlier token stops working (spec 2.6, INV-S9). Freeing and re-reserving would let a re-mint loop extend a run past the plan's longest run.
4. **Amendment 14, "register the App with the webhook from day one".** The App is registered with Deployments: read from day one, but the webhook is saved only after Codium's A47 router is deployed (section 4 step 3). Until then the mint's owner-id check catches transfers (INV-S11).
5. **SPEC §4.10 codes at the mint.** The mint answers one neutral 403 `BINDING_UNAVAILABLE` for the allowance reasons `none`, `payment`, `dispute`, `fraud`, `closing` and `not-in-plan` (`github-agents`), with no `reason` field, instead of `MODEL_PLAN_REQUIRED`, `MODEL_PLAN_PAYMENT_REQUIRED {reason}` and `MODEL_PLAN_ACCOUNT_CLOSING`. Mint responses reach workflows any writer controls and public logs, so they must not reveal the binder's billing state (P6). The contract also adds `limit: "scheduled"`, `RUNNER_NOT_SUPPORTED` and `BIND_NEEDS_DEFAULT_BRANCH`, and maps a mint-time service-off to `MODEL_PLANS_DISABLED` (spec 2.9.1).
6. **The scheduled-runs cap counts GitHub `schedule` events only.** A separate workflow that dispatches `vector.yml` on a timer makes `github-dispatch` runs, which the cap does not count. This is an accepted risk: the hours cap and runs-at-once still bound them, and copy never calls the scheduled cap unbypassable (INV-C4).
7. **Publishing credential.** SPEC A49 builds Ship Desk cards from App-bot-authored PRs, and the earlier draft published server-started runs with the App token "so CI runs". The contract publishes with `GITHUB_TOKEN` by default and always for server-started runs, because App-token pushes start the repository's own workflows with its secrets on unreviewed, possibly prompt-injected code (INV-S18, O14). Vector's PRs are therefore `github-actions[bot]`-authored unless a repository opts in. Affects Codium A48, A49 and A50 (spec section 5).
8. **Pre-A59 entitlement backing.** Until A59, `cloudAgentEntitlement`'s default `plan()` reads `modelPlanStatus`, which can settle a pending top-up under the billing lease, reads the OpenRouter management API, and reports a `renewing` plan as inactive (SPEC §4.4 allows new mints while renewing). This is accepted because the backing is dormant: the kill switch stays unset until A59 replaces the function body with `cloudAgentAllowance` (spec 2.3, O10).
9. **"Remove sudo" (the earlier draft's O3) is replaced by the agent sandbox.** Removing the runner's sudo did not stop a same-user process from reading other processes' environments, and left the runner in the `docker` group. The model now runs as a separate user with no sudo and no Docker access (spec 2.11.3, V16). This strengthens amendment 3 rather than departing from it, and is listed here because the earlier draft of this contract proposed "Remove sudo" as O3's default.

## 2026-10-30 V00 (CI lane and test wiring)

1. **Core step without `test/github-agents.test.ts`.** The contract lists `packages/core`'s `test/github-agents.test.ts` in the lane's core step. That file is V01's and does not exist yet. `bun test` exits 1 when no filter matches a file, but silently drops a filter that matches nothing while another one matches (both checked locally with Bun 1.3.14), so naming the file now would either fail the step or hide that it never ran. The core step runs `test/review/*.test.ts test/child-environment.test.ts`, and the lane policy requires every pattern a test step names to match a file. Affects V01, which appends the file to the core step in its own commit.
2. **Engine glob.** The contract names `test/cli/github.*.test.ts`. The lane runs `test/cli/github*.test.ts`, which also takes `github-action.test.ts` and `github-remote.test.ts`. Both test `src/cli/cmd/github.ts`, a file we own, and nothing else runs them on this branch.
3. **The lane runs its own policy test.** The contract adds the lane's policy to `packages/cloud/src/workflow-compliance.test.ts` but lists no step for it. `test.yml` does not run on this branch's pushes, so the lane's `api` job runs that file too; otherwise a later package could break the policy and see it only when the branch reaches a pull request.
4. **Pull-request paths.** The contract's four `api/` entries (`api/github/**`, `api/cloud-agents/**`, `api/_lib/github-*.ts`, `api/_lib/cloud-agents-*.ts`) become `api/**`, and the paths add `bun.lock` and the root `package.json`, as `vector-free-models.yml` and `vector-sharing.yml` do. No other workflow runs the three web GitHub tests (`test.yml` runs only `release-copy.test.ts` in `packages/web`, and the other `api/**` lanes run their own files), and those tests load shared modules outside the contract's list: `api/_lib/http.ts`, `abuse.ts` and `persistent-store.ts` (which Codium's lane also edits), `jose` (pinned in `bun.lock`), and the Bun version that `setup-bun` reads from `package.json`. With only the contract's list, a pull request that broke one of those would merge without any check running the tests. The engine, core and root `test/` files the lane runs need no extra paths here, because `test.yml` runs their suites on every pull request. Besides that, the paths name the lane's test files (`packages/web/test/github-*.ts`, `packages/engine/test/cli/github*.ts`, `packages/engine/test/tool/registry*.ts`, `packages/core/test/review/**`, `packages/core/test/child-environment.test.ts`, `test/api-module-loading.test.ts`, `test/cli-token.test.ts`) and the compliance test, so a pull request that changes only one of those tests still runs the lane. The lane policy requires `api/**`, `bun.lock` and `package.json` along with the contract's other entries.
5. **Three jobs instead of one list of steps.** The contract lists the lane's steps in one sequence. The lane runs them in three jobs, so one failure does not hide the other results and each job sets up only what it needs:
   - `api` (hosted API): the API typecheck, the three `packages/web` GitHub tests with `VECTOR_TEST_REDIS_URL` and the Valkey service, the root `test/` files, and the lane policy;
   - `packages` (engine and core): Node 24, ripgrep, the git identity, the engine GitHub step and the core GitHub step;
   - `node-bundle`: the Node-bundle build and smoke from `test.yml`'s `desktop-engine-node` job.

   "Append to the matching step" now means that step in its job. The `packages/app` and `packages/desktop` steps the contract describes (`GITHUB_ACTIONS=false bun --no-env-file test <file>`) start in the `packages` job with the first lane test file there (V24, V25); no lane package has added one at V00. V16's `sandbox-probe` is a job of its own.

6. **A stricter secrets check.** The contract's test checks for no `secrets.` reference. Expressions also reach a context by index and whole (`secrets['X']`, `toJSON(secrets)`, `github['token']`, `toJSON(github)`), which that check misses, so the lane policy refuses the word `secrets`, `github.token`, any index into `github` and `toJSON(github)` in every key and value of the parsed workflow, ignoring case so a capitalised name (`SECRETS.X`) is caught too. Comments are not read, so they can still say what the lane does not hold. Affects every later package that adds a step or job to the lane (V16's `sandbox-probe`, V30).

## 2026-10-30 V01 (Shared constants)

1. **"No imports" allows the required self-export.** Section 2.1 says the file has no imports and ends with `export * as GithubAgents from "./github-agents.js"`. Bun's `scanImports` reports that self-export as an `import-statement` record and leaves out type-only imports and re-exports (checked with Bun 1.3.14). The test therefore accepts exactly that one record, and also reads the code with its comments removed and refuses any `import`, any `require(` and any `from "…"` clause other than the self-export, so `import type` and `export type … from` fail it too.
2. **`withheldOnActions` uses the tools' real ids.** Section 2.1 and INV-S13 name `browser`, `vectorcloud` and `researchbrowser`. The last two are only keys of the registry's local tool map in `packages/engine/src/tool/registry.ts`. The tools are defined, offered, permitted and filtered by the ids `vector_cloud` (`tool/vector-cloud.ts`) and `research_browser` (`tool/research-browser.ts`), so with the contract's list the research browser, which the registry offers unconditionally, would stay offered on Actions. `withheldOnActions` returns `true` for `browser`, `vector_cloud` and `research_browser`, and still for `vectorcloud` and `researchbrowser`, so either spelling is withheld. Read INV-S13's list as `browser`, `vector_cloud`, `research_browser`. Affects V03 (the registry filter calls `withheldOnActions` with `Tool.Def.id`, and `registry-actions.test.ts` should use the real ids), the Hands lane's E5 and Codium's gateway computer-use list (section 5).
3. **`RUN_ID_PATTERN` itself refuses a lone `-`.** Section 2.1 gives `/^[A-Za-z0-9_.-]{1,128}$/` and adds "`-` alone is refused"; INV-K5 also says the run id is never `-`. That pattern accepts `-`: Codium refuses it with a second check (`validRunId` in `api/_lib/codium-pool.ts`: `RUN.test(run) && run !== "-"`). The constant is `/^(?!-$)[A-Za-z0-9_.-]{1,128}$/`, which accepts exactly what Codium's `RUN` plus `validRunId` accept, so V07's `readRunToken`, V12 and V27 refuse `-` with `RUN_ID_PATTERN.test` alone. It is no longer byte-identical to Codium's `RUN`.
4. **`runId` accepts only positive decimal ids.** Section 2.1 says "decimal ids; at most 87 characters". `runId` takes, for each id, a string of 1 to 20 digits with no leading zero or a positive safe integer, and throws a `RangeError` for anything else, so its result always matches `RUN_ID_PATTERN` and four 20-digit ids give 86 characters. Its parameters are `repositoryId`, `run`, `attempt` and `checkRun`, because a parameter named `runId` would shadow the function. Callers pass verified OIDC claims, which V08 already bounds to safe integers, so real runs never throw.
5. **`slugFromInstallUrl` takes `string | undefined`.** The public installation answer's `installUrl` is optional (section 2.2), so `undefined` returns `undefined`. The function matches the whole string against one anchored pattern instead of parsing a URL, so any other scheme, host, port, user info, letter case, query, fragment, encoded or extra path segment, or a trailing newline gives `undefined`, and the file needs nothing newer than ES2023 (`URL.parse` is not on every runtime that loads it).
6. **Lane wiring.** The lane's core step now runs `test/github-agents.test.ts`, which V00 deviation 1 deferred to this package. Following V00 deviation 4, the pull-request paths name `packages/core/test/github-agents.test.ts`, and the lane policy's list of checks the contract names gains it.

Noted for reviewers, not deviations: `MIN_AGENTS_CLI` is not defined here, because V14's file list adds it with the next CLI release's version (its section 2.1 row now says so). `MintStatus`, `Outcome` and `StopCode`, which sections 2.8, 2.12 and 2.16 use, are now named in section 2.1 with the tuples `MINT_STATUS`, `OUTCOME` and `STOP_CODES`, as the section 2 preamble requires for a new shared name.

## 2026-10-30 V02 (Mention parsing: word boundaries and the App handle)

1. **Mention order.** `DEFAULT_MENTIONS` (`command.ts`) and `TASK_MENTIONS` (`github.route.ts`) now equal `GithubAgents.mentions()`, ordered `/vector`, `/vs`, `/vectorscope`, `/vx`, instead of `/vectorscope`, `/vs`, `/vector`, `/vx`, as V02's equality test requires. The v2 workflow's bytes change in two places: the route job's `contains(...)` condition and the route script's `const mentions` list. The two golden lines in `packages/engine/test/cli/github.workflow.test.ts`, a file not in V02's list, are updated to match. Behaviour does not change: the parser sorts mentions by length, and the condition is an OR. The CLI's "Comments must mention …" message lists them in the new order. This settles the question the V01 progress entry left to V02: V14's "the v2 builder's output is byte-identical to before" takes the v2 output after V02 as its baseline.
2. **Inline code spans.** Section 2.2 says spans are ignored but does not define them. They are paired as CommonMark pairs them. A run of n backticks opens a span, and the next run of exactly n backticks closes it. A run with no partner is literal text. A backslash escapes the first backtick of the run after it, but inside a span a backslash is code. Code is replaced by one `#`, which is neither whitespace nor a boundary, so a mention glued to code (`` `x`/vector fix ``, `` /vector`x` ``) does not count either. The pass is linear in the body's length.

   The parser does not parse Markdown's blocks, yet pairing depends on where a block's text starts. So it pairs within paragraphs that end only where Markdown surely ends one:
   - a line that is empty but for spaces and tabs (a line of no-break or zero-width spaces does not end one);
   - a fence;
   - a comment that starts a line, which is an HTML block (item 7);
   - a quote that starts in a paragraph where no `>` has appeared yet. After a `>`, a quote may already be open (one can also start after a list marker), and a later quoted line may continue it.

   Inside a paragraph, any line could start a block: a list item, a heading, a table row, or the line a quote's paragraph continues on. So the parser pairs from the start of every line to the end of the paragraph, and text that any of these pairings makes code counts as code. Quoted lines stay in their paragraph for pairing, masked so that no mention on them counts; a line whose list markers are followed by `>` (`- > x`, `1. > x`) is quoted too. Where the blocks start can therefore only make the parser refuse a mention that GitHub shows. Apart from the cases listed below as not modelled, it never counts a mention that GitHub shows only inside an inline span.

   The table pins the review's cases: a list item or a heading after a stray backtick, ``` \`` /vector fix` ```, and a line holding only a no-break space or a zero-width space. It also pins quotes that continue across lines, and the cost. In `` `foo⏎bar` /vector fix `x` ``, the line after the wrapped span could start a block, so the parser refuses a mention that GitHub shows.

   Not modelled, so a mention can count although GitHub shows it only as code:
   - A construct that takes a backtick before a span can open: an autolink or raw HTML tag (`<…>`), a link's destination or title, or a GFM extended autolink (`www.…`). HTML comments are modelled (item 7).
   - A GFM table, which pairs each cell on its own.
   - A fence that GitHub opens or ends where the parser does not (see below).

   The table pins one such body for each, as a task.

   Fences. A line that starts with three backticks or tildes opens a fence, as before V02, and so does one whose list markers (`- `, `1. `, `- 1. `, each followed by one to four spaces) are followed by them. The review found that ` - ```sh⏎  /vector review⏎  ``` ` reviewed although GitHub shows the command as code. A fence opened after a list marker is inside the list item, so it also ends at the first non-blank line indented less than the item's text (a tab counts as four columns), which ends the item. That line is then read afresh and may open a fence of its own. A `>` quoted line never opens a fence, as before: a quote's lines are masked anyway, and its fence ends with the quote.

   Fence detection is still not exact. GitHub does not open a backtick fence whose info string holds a backtick, a fence indented four or more spaces inside a paragraph, or a fence after an ordered marker other than `1.` that continues a paragraph (such a marker cannot interrupt one). It does not close a fence at a line indented four or more spaces. And a fence opened on a line of its own inside a list item ends where the item ends, which the parser does not track. Where the parser and GitHub disagree on a fence, they can also disagree on the code spans around it, because a fence ends the parser's paragraph and hides its backticks from pairing. Where the parser's fence closes at a line where GitHub's opens, a mention after it counts although GitHub shows it as code; the table pins the last two cases as tasks. Indented code blocks, which 2.2 does not name, are not ignored.

3. **The `.` rule applies per line.** "A `.` that ends the text or precedes whitespace" is read line by line: a `.` at the end of any line precedes the newline. So `/vector.` at the end of a line is accepted, and `/vector.x` and `/vector... fix` are refused.
4. **Trailing invisible characters.** Section 2.2 says a mention may be followed by "the end of the line". Clients append zero-width spaces, soft hyphens and byte order marks, which the verb-line trim already ignored (`/vector review​` reviews). Each line therefore loses trailing characters from that set before the boundary tests, so a bare `/vector​` stays a task, as it was before V02. An invisible character inside a line is no boundary: `/vector​x` is refused.
5. **`/vectorx review` is now refused.** The earlier corpus had this body as a task. Refusing it is the intended effect of 2.2's word boundary, and the table row now expects `none`.
6. **One shared table, in a file outside V02's list.** The table is `packages/core/test/review/mention-cases.ts`, a module that is not itself a test. Both `command.test.ts` and the engine's `github.route-script.test.ts` import it, so the route-script test runs "the same table" the contract asks for. Importing a `.test.ts` file would register its tests a second time. The lane's pull-request paths already cover `packages/core/test/review/**`.
7. **HTML comments are read with the Markdown around them.** Section 2.2 says the parser "still strips HTML comments". It used to cut every `<!--` up to the next `-->` out of the body before reading anything else. The review found two ways this let a mention count although GitHub shows it only as code. On GitHub, a code span that opens before a `<!--` holds it as code, so cutting the comment could delete the backtick that closes the span (``Type `<!--` then --> and ` /vector fix ` ``). And a line that held only a comment became blank, which ended the parser's paragraph, and a span across it, where GitHub's paragraph goes on (a comment line indented four spaces). Comments still never count, but now:
   - Every `<!--` up to the next `-->` is found as before, then masked instead of cut: all but whitespace, backticks, backslashes and the characters of comment, quote, list and fence markers become `#`. No mention inside one counts, and the Markdown around it keeps its shape.
   - A comment that starts a line (indented up to three spaces) is an HTML block, as on GitHub. It runs across blank lines and fences to the line holding `-->`, and the rest of that line is read as text of its own. A block whose `-->` never comes runs to the end of the body, as on GitHub, so `<!-- note⏎/vector review`, which reviewed before, is refused.
   - A comment elsewhere is read with the code spans: whichever of a backtick run and a `<!--` comes first takes the text after it. A `<!--` may also be literal text (after a backslash, or where a Markdown flavour refuses the comment: CommonMark 0.31 allows `--` inside one, earlier versions do not), so the parser follows both readings and refuses what either makes code. A comment that no reading makes code is removed, as before, so `/vector <!-- note⏎more --> review` still reviews.

   The table pins the review's bodies, a template comment across a blank line, an unclosed one, and a comment that a quote's lazy line closes. Not modelled: GitHub's page is HTML built from the Markdown. Where the Markdown leaves a comment open in that HTML (an HTML block inside a list item or quote ends with its container, and a second `<!--` can follow the `-->` that ends an HTML block's line), the page can hide more than the Markdown shows. The parser reads only the Markdown, as before.

8. **A review reads a dismissal with the workflow's mentions (phase review, V00–V03).** The route job parses a comment with the workflow's `MENTIONS` and answers a `dismiss` that the dismissal is read on the next review. The review job then read dismissal replies with `DEFAULT_MENTIONS`, which is `GithubAgents.mentions()` without the App handle. Once V14 bakes `@<slug>` into `MENTIONS`, or whenever a repository edits its own list, a `@<slug> dismiss` the route job accepted would have been lost and the finding raised again. `ClassifyContext` (`packages/core/src/review/state.ts`, a shared file outside contract 0.2) takes the workflow's `mentions`, and `classifyPrior` reads replies with them, falling back to `DEFAULT_MENTIONS` when they are absent, as in local reviews. `github.review.ts` (a shared file, also edited by Codium's A26) passes `ctx.mentions` in its one `classifyPrior` call; that is its only change. `state.test.ts` › "reads a dismissal with the workflow's mentions, the App handle included". V14 needs nothing more here.

Noted for reviewers, not deviations:

- The parser's existing passes were made linear, because the route job parses every comment that passes its `contains()` filter, and does so before the writer check. The HTML-comment search now uses `indexOf` instead of a lazy regex (item 7 changes what is done with what it finds); the regex took about 500 ms on a body of about 16,000 unclosed `<!--` under Bun 1.3.14. Both trailing trims now count back from the end of the line instead of using an end-anchored regex, which took about 8 s on 65,536 characters of trailing punctuation. `command.test.ts` holds these to 250 ms per body at GitHub's 65,536-character limit.
- `command.test.ts` checks that `command.ts` imports nothing and that its source is printable ASCII, so V09's relative import from `api/` stays safe and the invisible characters the parser trims stay visible to reviewers as escapes.

## 2026-10-30 V03 (Actions safety floor: withheld tools, env stripping, repo-work policy)

1. **The policy reaches every request through a process-wide pin, not one user message's `system`.** The contract has today's `github run` add `githubSystemInstructions` to "the session's system instructions", and INV-S14 asks that every Actions task session carry it. A user message's `system` reaches only the turns that message starts, because each loop step reads the newest user message. Several writers add a newer user message without it: auto-compaction and its continue message, the judge's repair after a FAIL, the research verdict follow-up, and background-subagent notes. Subagent and judge sessions, prompted by the task tool and the task manager, get no `system` at all. So a long run, a judge FAIL or a subagent would have gone on without the policy.
   - What was built instead: `LLMRequestPrep.pin(system)` in `packages/engine/src/session/llm/request.ts`, a shared file outside contract 0.2. It adds the pinned text after the session's own system text in every request the process prepares: every session, agent and turn, the quick lane, titles and compaction included.
   - `githubRun` pins `githubSystemInstructions("<owner>/<repo>")` before anything can reach a model and never unpins it. Its background subagents, the turns their notes start and the titles `effectCmd` waits for go on sending requests after `githubRun` returns, until the instance is disposed, so an unpin in its cleanup would send those without the policy. Tests unpin in their own scope. It passes no `system` on its prompts, so the text is not sent twice.
   - A process-wide value is right here because `vector github run` is one process for one task in one repository. Nothing else pins it, so the desktop, the server and `vector run` are unchanged.
   - The text goes in the per-session block, so the stable block a provider caches across sessions is unchanged.
   - Copying `system` in each follow-up writer was not chosen: it would change five shared writers, still miss subagent sessions, and the next new writer would miss it again.
   - Affects V17 (the lift keeps the pin in `githubRun`, with no unpin), V18 (the agent phase pins the same text before any session) and V20 (the review job does not pin it yet).
2. **MCP tools are withheld where they are offered.** The contract puts the whole guard, "including MCP tools", in `registry.ts`. MCP tools never pass through the engine's `ToolRegistry`: `SessionTools.resolve` (`packages/engine/src/session/tools.ts`, a shared file outside contract 0.2) merges `mcp.tools()` itself. `registry.ts` exports one predicate, `actionsWithheld(id)`, which is `onActionsRunner(process.env) && withheldOnActions(id)`. The registry and the MCP loop both call it, the loop with the MCP key (`<server>_<tool>`), so a `computer` or `computer-x` server's tools are withheld. `registry-actions.test.ts` proves the MCP case through the real session loop with a fake MCP service, by reading the tool list the provider request offered.
   - A computer-use server is withheld whole, not only its tools, because its resources (a screenshot, say) and instructions reach the model too, and its other tools act on the same computer. `actionsWithheldServers(servers, keys)` withholds a connected server when its own name or the own name of any tool it lists (each sanitized as `McpCatalog` does) matches the computer-use pattern. INV-S13's "MCP tool names included" is read as both an MCP tool's key and its own name, so a `computer` tool on a `desktop` server is withheld, with the whole `desktop` server. The check is `GithubAgents.computerUse(name)`, the pattern half of `withheldOnActions`, now named in section 2.1. The bridged ids (`browser`, `vector_cloud`, `research_browser` and their spellings) are Vector's own tools, so a server that only shares one of those names, such as a browser-automation server named `browser`, is not withheld; its tools, resources and instructions stay together. `actionsWithheldMcpTool(key, withheld)` withholds an MCP tool whose key `withheldOnActions` matches or whose server is withheld.
   - A tool key (`<server>_<tool>`) does not say where the server's name ends, so the server check reads a key as belonging to every server whose prefix it carries. A server `a` beside an `a_computer` that lists a tool is therefore withheld too. This errs only towards withholding.
   - `SessionTools.resolve` judges the servers from the same `mcp.tools()` snapshot its MCP loop offers. It leaves a withheld server's tools out, leaves the server out of `list_mcp_resources` and `list_mcp_resource_templates` and out of the check that decides whether those tools are offered, and `read_mcp_resource` answers that it is not connected. The three resource tools judge the servers again when they run. `SystemPrompt.mcp` (`packages/engine/src/session/system.ts`, another shared file outside contract 0.2) leaves out a withheld server's instructions, judging the servers from the tool keys `mcp.instructions()` already lists, so it asks the MCP service for nothing more. MCP prompts reach a session only as commands, which `github run` never sends.
   - Phase review (V00–V03): the first version asked `actionsWithheld` of the server's name. That matched the bridged ids exactly, so a server named `browser` lost its instructions and resources, and `read_mcp_resource` called it not connected, while its `browser_*` tools stayed offered. It also read MCP tool names only through the key, so a `computer` tool on a `desktop` server was offered.
   - The server itself still connects, so a local one's process still starts on the runner. Not connecting it was not chosen: the MCP service builds its connections once per instance, while these checks read the environment on every call, as the registry's do (item 4). The test's fake MCP service gives a `computer`, a `desktop` (with a `computer` tool), a `browser` and a `docs` server resources and instructions, and checks what the provider request carried and what the two resource tools returned. 8. **Every key a script touches is declared, so the redeem input names two accounts.** 2.5's `redeemAndBind` input held the code, identity, workflow version, takeover flags and `now`. The redeem script must also add the repository to the code account's `bindings:<account>` set and, on a takeover, remove it from the old binder's, and Redis documents that a script must receive every key it touches in `KEYS`, on standalone servers as well as clusters. No CI job reaches Upstash, so an undeclared key there would first fail at the owner's acceptance run (section 4), and building the keys inside Lua would also write the key layout a second time (2.4). So `RedeemInput` gains `account` (the code's account, as `peekBindCode` returned it) and `current?` (the account bound when the caller applied O6; absent when it was unbound), and the module builds all five keys with its own builders. The script refuses before any write when the code's account is not `account` (`code`), or when the repository is bound to an account that is neither `account` nor `current` (`changed`: the binder changed after the caller judged O6, so its takeover flags describe someone else). `recordRepoBinding` returns `{ok: true, binding} | {ok: false, refusal: "code" | "elsewhere" | "changed"}`; `redeemAndBind` maps `code` to 403 `BIND_CODE_INVALID` and both others to 409 `REPO_BOUND_ELSEWHERE`, as 2.8 step 5 expects of a bind that lost a race. A binder change between V10's step 3 and the redeem is thereby refused, not judged with stale flags. The script consumes the code with `GET` and a later `DEL` in the same script, which is as atomic as 2.5's `GETDEL`. `bindingsForAccount` sends two reads, the account's set and then one script with each named binding's key declared; every other function sends exactly one store command. Every read runs inside a script (`HGETALL` and `SMEMBERS` too), so the reply is a flat array whether the client speaks RESP2 (Upstash's REST API) or RESP3 (Bun's `RedisClient`, which the test's fake uses; checked locally, it answers a bare `HGETALL` with a map). Affects V10, which passes `peekBindCode`'s account and the account `bindingFor` returned at step 3, and may re-read and retry once on `changed`.

Affects V10 (validate or normalize the body's `defaultRef`) and V24 (the desktop sends `refs/heads/<default branch>`).

11. **Validation, and what malformed stored data does.** 2.5 named no input rules. Every value a function would write, or would use to build a key, is checked before any store command with the same rules the reader applies, and a bad one answers 400 `INVALID_REQUEST` with no store command: accounts are lowercase UUIDs; ids are decimal safe integers with no leading zero; repository names, logins and refs use the OIDC verifier's patterns; `workflowVersion` matches `^[1-9]\d{0,3}$`; visibility and suspension reasons are their enums; the takeover flags are booleans; times are positive integer milliseconds. A code that is not `vbc_` plus 43 base64url characters gets the one 403 `BIND_CODE_INVALID` from both `peekBindCode` and `redeemAndBind`, also with no store command. Stored data is read strictly: a binding hash with an unknown, missing or malformed field, or whose `repositoryId` is not its key's, and a bind code whose JSON does not parse to exactly 2.7's shape, answer 503 `PERSISTENT_STORE_UNAVAILABLE` (INV-S16), never a refusal that could be mistaken for a cause and never a grant. The redeem script checks the code, the binding fields O6 reads and the types of the account sets and the binder-left set before its first write, and writes `INCR` first, so a corrupt counter fails the script with nothing written. The O6 fields pass the reader's own rules in Lua, whatever the takeover flags say: `ownerId`, `boundAt` and a present `lastUsedAt` are decimals with no leading zero up to 2^53 − 1, and a present `suspended` is one of the three reasons. Lua's `tonumber` alone reads exponents, hex and padding, and every string, the empty one included, is true in Lua, so a malformed suspension or owner id would itself have been grounds for a takeover where every reader answers 503. The suspend script refuses an unknown stored `suspended` the same way, and checks its generation with the same rule. `bindingsForAccount` skips a set member whose binding is gone or belongs to another account (an expected leftover), and fails the whole listing with 503 when a member is not an id or a member's binding is malformed. Affects V10 (the bindings list and unbind answer 503 then) and V11, whose INV-P3 test compares stored fields with 2.18; that row now lists a bind code's fields.
12. **A suspension names the binding it was decided against.** 2.5 had `suspendBinding(repositoryId, reason)`, which suspended whatever binding held the repository id when its script ran. Every caller decides against a binding it has just read: V12 at step 6 (the owner id differs) and at step 9 (V09's binder check, a GitHub round trip, finds no write access), and V28 on a delivery the router dedupes but does not order. In between, the repository can be rebound, taken over (by an App-verified admin under O6, say) or unbound and bound again, and the old call would then suspend the new binding: its fresh run tokens die, `binder-left` hides a private repository from its legitimate new binder and is never replaced, and O6 lets any other writer take it over at once. So the function takes `binding: Pick<RepoBinding, "repositoryId" | "generation">`, the binding as the caller read it, and its script leaves the stored binding and the counter alone (`stale`, or `missing` once there is none) unless the stored binding is that one: its `generation` equals the one read, or is one more on a suspended binding, because that binding's own first suspension by another caller moved it (`binder-left` then still replaces another reason, INV-P3). Every rebind, takeover, unbind and bind after an unbind moves the generation and clears the suspension, so a later binding never matches. A late `binder-left` still reaches the read account's binder-left set (deviation 13). A stored `generation` that is not a decimal answers 503 before any write. The parameter is required, not optional: no caller suspends a binding it has not read, and an unguarded form would keep the race. Affects V12, which passes the binding it read at step 6 at both steps, and V28 (2.14): read `bindingFor(id)` first and pass it, and for `transferred` skip a binding whose `ownerId` already equals the payload's `repository.owner.id`, since it was bound after the transfer.

13. **Binder-left is kept for the account, outside the binding.** Deviation 6 and 2.5 kept `binder-left` only in the binding's `suspended` field, and 2.8 and 2.16 had V10 and V11 hide a private repository's name, run URL and actors by reading it there. But O6 lets any other writer take a `binder-left` binding over at once, and a takeover, a rebind and an unbind all delete the hash, while the account's run records, with the repository's name, run URL and actors, stay for 90 days (2.18). After any of them, nothing in the store would have recorded that the account's binder lost access, and the account's run list would have shown that detail again (INV-P3). So the module keeps the fact in a new key, `binder-left:<account>`, a SET of repository ids (2.7, 2.18). The suspend script adds the repository to the binding account's set in the same script that records `binder-left` (on an unsuspended binding, or replacing another reason), after the `INCR`, so a corrupt counter writes nothing. Only two things remove a member: a later bind of that repository by the same account, in the redeem script, because that binding's binder has write access again; and V11's erase. `suspendBinding`'s binding therefore also names its `account` (`Pick<RepoBinding, "repositoryId" | "generation" | "account">`), so the set's key is declared (deviation 8). A stored binding of another account is left alone, like one with another generation, but the member is the read account's fact, not the binding's: V12 decides `binder-left` at step 9 after a GitHub round trip, and if a takeover or an unbind lands in between, a suspension that ran first would have kept the member while one that runs second would have written nothing. So a late `binder-left` still adds the member, and nothing else, when the binding read is gone and the counter has passed its generation (an unbind, perhaps then another account's bind and unbind), or when another account's binding holds the repository and was bound after the one read (its generation, less one when it is suspended, is past the one read: a takeover, or an unbind and another account's bind); the set then ends the same whichever script lands first. A later binding of the read account's own skips it, because its bind cleared the member and its binder could bind. The one ordering the store cannot see is such a rebind that is itself gone again (unbound, or taken over) before the late suspension runs: the member is then added although that rebind's binder could bind, which hides more, never less, until the account binds the repository again. The suspend script reads the stored account with the reader's rule (a lowercase UUID) and, once the binding is gone, the counter with the decimal rule, and answers 503 for either before any write. V12 and V28 pass the binding `bindingFor` returned, which carries the account. The hiding also stops reading `visibility`. The stored visibility is the bind token's and nothing updates it, so a repository made private after the bind would have stayed visible to a former binder. A `binder-left` binding, and every run of a repository in the account's set, hide the name, run URL and actors whatever the stored visibility; for a public repository that hides what GitHub shows anyway, which fails closed. 2.8's bindings row, 2.16's last bullet and the V11 and V26 lines say so; INV-P3 is unchanged. The set has no expiry, like `bindings:<account>`: a fixed one would have to outlast the account's run records, whose expiry V11 sets. Nor is a member dropped when the account's last run of that repository expires: run records expire one by one and `runs:<account>` is trimmed to 200, so knowing that none remains would take a scan of the account's runs, and the member is a bare repository id of a repository the account bound itself. 2.5, 2.7 and 2.18 state the one retention: until the account binds that repository again, or its erasure. Affects V10 (hide every `binder-left` binding), V11 (read the set in `listCloudRuns`, delete it in `eraseCloudAgentsAccount`, list it in the INV-P3 key check with 2.18's retention; nothing else removes a member), V12 and V28 (pass the binding as read).

Noted for reviewers, not deviations: the bind-code JSON and the binding hash are decoded with Effect Schema structs that refuse excess properties, and inputs are checked with the same field schemas (`Schema.is`). The test reaches the store through `persistentStore` and an in-process `Bun.serve` fake of the REST endpoint backed by a real Redis or Valkey, starts no subprocess, and never names V04's limits table.

2. **Validation and strict decoding.** 2.6 named no input rules. Every input is checked before any store command (400 `INVALID_REQUEST`): lowercase UUID accounts; `RUN_ID_PATTERN` run ids; decimal repository ids with no leading zero; `THREAD_PATTERN` threads; integer generations of at least 1; 22-character base64url `jti`s; the source and purpose sets, with the purpose `scheduled` exactly when the source is `github-schedule`, so no purpose can skip the daily count; an active allowance with integer limits and a meter epoch matching `METER_EPOCH_PATTERN`; times that are positive integers a `Date` can hold, so every one names a UTC day. `consumeKey` must be a `ticket:<sha256>` key, so no caller can delete an arbitrary key. 3. **Reservations are charged up front.** 2.6 charged `used:<account>:<epoch>` only at settle, and summed live reservations separately. Two problems followed. First, a settle must write the used key of the run's epoch, which neither `settleRun(account, rid, now)` nor an idle sweep knows before its script runs, and every key a script touches must be in `KEYS` (V05 deviation 8). Second, 2.7 lets `live:<account>` expire at the latest deadline plus 1 day, so a run nobody settled, on an account with no ledger call in that time, would never be charged at all: a client that drops its settle step would get a free run. So a fresh reserve adds the whole reservation to `used`, and every settle path gives back the reservation minus the one formula's charge, into the run's own epoch only. `left` (INV-C2) and the formula (INV-C3) are numerically unchanged: `used(epoch)` is now settled seconds plus that epoch's live reservations, so `left = allowanceSeconds − used(epoch) − Σ other epochs' live reservations`, and `cloudAgentSecondsUsed` answers `used(epoch)` minus that epoch's live reservations, which is still settled seconds. **Unsettled runs (found in the second review).** As first built, the live hash kept 2.7's expiry, the latest deadline plus a day, while the `used` key it charges lives until 40 days past the period's end. A run that no settle reached within that day then lost its record and stayed charged its whole reservation (up to the plan's longest run: 30 minutes of Plus's 5 hours, 120 of Ultra's) unless the account happened to reserve or read agent time within the day. That covers a cancelled job, a lost runner and a failed settle call, and also a run whose token a rebind, an unbind, a takeover or a suspension killed, which V07 refuses to settle however well the client behaves (INV-S8). This entry had offered the first group to the owner as a trade-off, with a V18 settle step under `always()` as its mitigation; 2.11 and V18 never defined that step, and it could not have read the run token anyway, because `sandbox run` unlinks the token file (2.13). Both readers of `used`, the reserve and the agent-time read, settle that epoch's idle runs by the formula before they read it, so no limit or meter ever sees an unsettled run's whole reservation, however late the next call comes, and no client step is needed for the charge (INV-C3). The cost is retention: an unsettled run's record (no names: the repository id, the thread number, times, the epoch, source, purpose, generation and token id) can stay as long as the account's agent time, at most 40 days past the period's end, where it had stayed at most a day past its deadline; 2.18's live-run row says so. Deviation 6's exception remains: a run that a reserve of another epoch removes keeps its whole reservation in its own epoch, which no limit reads. A run no settle reaches still has no outcome in its run record (2.16); that is the run-record side, not the ledger's. Affects 2.6, 2.7's `live` and `used` rows, 2.18, INV-C3, V11 (the stored-data list), A18 and A59.
4. **Signatures name the token and the reservation, and the reserve answers what the token signs.** 2.6 had `reportRun(account, rid, now)`, `settleRun(account, rid, now)`, `releaseRun(account, rid)` and `{ok: true, deadline, startedAt, renewed}`.

V12 checks the token (one EVAL) and then calls the ledger (another), and a renewal can land in between; without the check, a token replaced by a later mint could still heartbeat or settle the renewed run, which INV-S8 forbids. A replaced token's heartbeat answers `{live: false}`, its settle `{settled: false, seconds: 0}`. `settleRun` gives back into the token's epoch; with any epoch other than the record's, the whole reservation stays charged. `seconds` is what the run stays charged.
   - `reserveRun`'s success is a union on `renewed`, and carries the record's `epoch`, `thread`, `source` and `purpose`. A renewal keeps the record's values whatever the new mint body asked for, so V12 signs `epoch`, `thr`, `src` and `pur` from the answer, never from the body or the allowance: the thread is fixed at mint (2.4) and V27's artifact key is bound to it, and a patched body could otherwise change it on a renewal (INV-C6). The epoch the token signs is then always the one the reservation was charged to.
   - `releaseRun(account, rid, reservation: {renewed: false, jti, epoch, startedAt})` acts only when the record's `jti`, `epoch` and `startedAt` are the reservation's, and gives back the whole reservation and, when the record is `counted` (item 14), the scheduled run on the start's UTC day. A `renewed: true` answer cannot be passed (the test proves that with `@ts-expect-error`, checked by `packages/web`'s typecheck), and is refused at run time with 400 before any store command; a release with the fresh reservation's details after a renewal finds another `jti` and changes nothing.

5. **Only the reserve and the agent-time read judge runs idle.** INV-C3 said idle runs are settled "by the next ledger call for that account". `reportRun`, `recordCodiumRequest`, `settleRun`, `releaseRun` and `liveRun` touch only their own run and judge nothing idle, so the gateway hook adds one small script to each Codium request and never settles the account's other runs, and INV-C3's own case holds: a run with no heartbeats whose last Codium request was at +20 min is idle-settled at +31 min, by the next reserve or read, at 20 minutes. The idle rule is strict: exactly 600 s after the last activity a run is still live; 1 ms later it is idle (both measured from a heartbeat and from a request). INV-C3's last clause now names the two calls.
6. **A run of another epoch.** A sweep cannot give back into an epoch it was not given a key for, and neither can 2.6 step 2's generation-change settle: the reserve's script holds only its allowance's `used` key, and the epoch a replaced record names is known only inside the script. `reserveRun`, which needs the slot, removes an idle run of another epoch than its allowance's, and settles a replaced run of another epoch (the same check run minting again after a rebind, across a period change), with no give-back: that run's whole reservation stays charged in its own epoch, which no limit reads once the account has moved to a new one (INV-C5), though that epoch's agent-time read stays high by up to the unused part (a Max run whose last heartbeat was at +5 min, replaced at +6 min across a renewal, reads 2700 s there, not the formula's 300). 2.6 step 2 and INV-C3 had said every settle path, a generation change included, charges the formula, and this item had named only the idle case (found in review); 2.6 and INV-C3 now name both, and so does the settle with another epoch's token (deviation 4). Refusing such a re-mint until the record goes idle would not help: the rebind has already killed the record's token, so it would be swept 10 minutes later, still without its epoch's key. `cloudAgentSecondsUsed` frees no slot, and its epoch is the caller's, which may be stale around a renewal (Codium's snapshot) or `none`, so it settles only idle runs of the epoch it is asked about and leaves others alone; removing them there would overcharge the current epoch by their unused reservations. The spec's Errors bullet says so. A "wait" retry is spaced by the usual delay, capped at `RETRY_MAX_DELAY_NO_HEADERS` (30 s) and at what is left of the window; the attempt and 15-minute caps do not apply to it, since the window replaces them.
   - **The spacing has a floor and a ceiling (review).** Because the window replaces the attempt cap, a gateway that answered concurrency with a zero or tiny `retry-after-ms` would have been polled in a tight loop for the whole 15 minutes. `GatewayRule` gains an optional `minDelayMs` (`RETRY_INITIAL_DELAY`, 2 s, when absent), and a "wait" retry waits `min(max(delay, minDelayMs), 30 s, what is left)`. The agent phase passes its clock's `minDelayMs` (`RETRY_INITIAL_DELAY` by default; the tests' `fakeClock` uses 1 ms). A `retry-after` longer than 30 s is shortened to 30 s by design: the spec's "polling at most every 30 s" asks for it, and a run's 15-minute window and its deadline matter more than the server's hint, so a refusing gateway is polled up to about 30 times in the window. The spec's Errors bullet now names both bounds.
   - A row that answered "wait" has waited out its window when it becomes the final error, so the phase records it as a draft with the busy reason.
