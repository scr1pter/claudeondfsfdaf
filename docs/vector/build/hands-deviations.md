## 2026-10-28 E0 (shared schema files)

Smallest changes that keep the contract's intent; later packages should build on these shapes.

1. **`ComputerState` is an Effect Schema** (value and type of the same name), not a plain type. It crosses the bridge in `act` and `heartbeat` responses and becomes the `computer.state` bus event (E6b), so it needs decoding. The other desktop views (`ComputerPrefs`, `ComputerPolicy`, `ResolvedComputerSettings`, `ComputerPlatform`, `PermissionsView`, `AlwaysAllowed`) stay plain types; `PREFS_KEYS`, `POLICY_KEYS`, `SETTINGS_KEYS` and `PLATFORM_KEYS` give their keys at run time (compile-checked as complete) for the INV-T1 shape test.
2. **`ComputerApps.category(app, signals)`**: `signals` gains optional `windowClass`, because 2.3 keys the table by window class (ConsoleWindowClass, CASCADIA_HOSTING_WINDOW_CLASS, taskbar classes) but its signature only had `childShell`.
3. **`AppMatcher`** is one app (or family) per entry: `{key: "builtin:<slug>", name, category, macos?: bundleIds[], windows?: {aumid?, windowClass?, binary?}}`, ids case-insensitive, a trailing `*` matches by prefix. `TABLE` exports every entry (never categories first). `ComputerPrefs.unblocked` stores a DEFAULT_BLOCKED entry's `key`.
4. **`builtinRule`** also returns `key` and `name` (for Settings rows and the unblocked check). Added `builtinVerdict(app, {unblocked}, signals)` (the built-in layer of section 2.6 that D15's `access()` should call first), plus `matches`, `find`, `benign`, `isNever`. A DEFAULT_BLOCKED match reports `reason: "user"` (BlockReason has no `default`; the verdict uses `blocked: default`).
5. **System rule vs DEFAULT_BLOCKED.** Disk Utility, Find My and Migration Assistant are Apple platform binaries, so "system and not benign is security" would make them never and contradict 2.3/1.5 K ("removable", [Allow]). `category` therefore treats a system identity that matches DEFAULT_BLOCKED as its listed category. **Cross-package risk (C1, M6, W7):** the helpers' system deny must exempt the DEFAULT_BLOCKED system entries, or a user's [Allow] for them is refused with `protected` at the helper.
6. **BENIGN_SYSTEM** adds ordinary Apple apps under M6's "and similar": Reminders, Contacts, Messages, Maps, Music, TV, Podcasts, Books, Freeform, Stickies, QuickTime Player, Font Book, Dictionary, Weather, Clock, Chess, News, Stocks. FaceTime, Photo Booth, Voice Memos, Home and Journal are left out (calls, camera, microphone, home devices, private journal), so they stay `security`.
7. **Keychain Access** is `password-manager` (reason `passwords`, copy "can't use password managers or Keychain") rather than `security`; 2.3 names it under both and both are never.
8. **Bridge shapes left open by 2.8:** `acquire` returns `{lease}`, `{code: "busy", holder}` or `{code: "permissions", missing}` as 200 bodies; empty responses are `{ok: true}`; `AppQuery` is `{key}` or `{name}`; `openApp.app` also takes `{path}`; `act` takes 1 to 10 steps.
9. **Helper shapes left open by 2.10:** array results are wrapped (`displays.list` gives `{displays}`, `apps.list` gives `{apps}`) so a response stays `{id, ok: true, ...result}`; `cancel`'s argument is `target` because the frame envelope already uses `id`; request ids are non-negative integers; keyboard ops (`input.key`, `input.type`, `input.hold`) carry the `pid` the focused app must belong to instead of `captureId, x, y`; `input.hold` holds a key combo for `ms`; `permissions.request` and `permissions.reset` return the permission status; `app.activate`, `app.launch` and `window.focus` return `{foreground?}`. `HelperEvent` includes `exit`, which only desktop main's supervisor raises.
10. **`ComputerBackend.capture`** returns `bytes: Uint8Array` (the schema package is browser-safe; a Node Buffer satisfies it).
11. **`appKey`** escapes `%` and `|` inside Windows exe parts (`%25`, `%7c`) so two identities can never share a key; ordinary values are unchanged. An exe identity with `verified: false` keys as `unsigned` even if a publisher string is present. `parseAppKey` rejects keys that are not lowercase.
12. **Shared constants live in E0's modules:** `Computer.MENTION_KEY` (D1's `Hands.MARKER` should reuse it), `ComputerApps.VECTOR_APP_IDS`, `HELPER_SUFFIX` and `ELECTRON_HELPER_SUFFIXES` (D1's `helperBundleId` and C1's generator should reuse them), `Computer.LIMITS` (section 2.12 numbers), `Computer.BRIDGE`, `Computer.HELPER_CLI`.
13. **Display text** in ask metadata, part metadata, the mention marker and state rejects control and bidi characters; producers clean text with `Computer.clean(text, max)`.
14. **Not identifiable from identity alone (helpers must cover them):** the Windows Run dialog is matched by its window AUMID `Microsoft.Windows.Shell.RunDialog`, which only the helper can read (W7); Windows Credential Manager shown inside a Control Panel (explorer) window has no identity of its own (W7).
15. Tests live in `packages/core/test` as the contract says, although `packages/schema/test` exists and runs with bun.

## 2026-10-28 E1 (permission policy)

1. **`canAlwaysApprove` for `computer_app` accepts only concrete app keys.** The contract's check is `always.every((p) => p.startsWith("app:"))`. The code also rejects the bare prefix `app:` and any pattern containing a wildcard character (`*` or `?`, the two `Wildcard.match` treats specially), so `app:*` or `app:macos:*` can never be saved as Always allow. This is stricter in the safe direction and keeps the contract's own cases (`["app:macos:com.apple.calculator"]` true, `["*"]` false). An app whose key really contains `*` or `?` simply gets no Always offer.
2. **Reason string values.** The contract names `AFTER_SCREEN_REASON` and `FLAGGED_SCREEN_REASON` without values. `AFTER_SCREEN_REASON` takes the engine design's value for the `new_destination` ask ("Text on your screen can steer the agent, and this address or recipient is new: you did not give it."); `FLAGGED_SCREEN_REASON` is the section 1.5 C reason line for flagged screen text. Neither names the feature, so `hands.ts` stays the only place the name is written.
3. **Gap until E2 (no ask is skipped, but INV-C5's "never kept" half belongs to E2).** Because `canAlwaysApprove` is now true for `computer_app` with app keys, an "always" reply is no longer downgraded to "once": the engine's `Permission.reply` pushes the pattern into its in-memory `approved` list, and `PermissionV2.reply` writes it to the saved table, where `savedRules` purges it on the next read (`isSensitiveAction` is true for every `computer_*`). Neither path can answer a computer ask, because `requiresApproval` is now true for every `computer_*` (the engine starts with `needsAsk = true`; V2 returns `ask` whatever the allow rules and saved approvals say, and both auto-resolve loops skip such requests). E2 removes the engine push ("skip approved.push for computer*\*") and owns "V2 never saves computer*\_"; the V2 save path (`reply === "always" && save.length` → `saved.add`) should also skip `computer\__` there rather than relying on the purge.

## 2026-10-28 E2 (ctx.ask returns the answer; the engine never persists a computer grant)

1. **New read accessor `Permission.Service.approved()`** (packages/engine/src/permission/index.ts), plus the exported type `Permission.Answer = "once" | "always"`. A `computer_*` entry in the in-memory approved list has no observable effect through `ask`/`reply`/`list`, because every `computer_*` request always asks and both auto-resolve loops skip it. So the INV-C5 test "an always reply to computer_app leaves approved empty" needs to read the list directly. Nothing outside the layer implements the interface, so no stubs change.
2. **A computer "always" answers only its own ask.** The contract says to skip `approved.push` for `computer_*`. `reply()` now returns right after resolving a `computer_*` request, so it also skips the same-session auto-resolve loop: an unrelated request that waited in that session stays the person's to answer. Non-computer "always" replies still push and run the loop, which resolves with "always". V2 does the same: `save = reply === "always" && save.length && !isSensitiveAction(action)`. It saves only when `save` is true, and it runs the follow-up loop only after a save. For every non-computer action this matches the old condition, because `canAlwaysApprove` true implies `canAutoApprove` true. Tests: "reply - an always reply to a computer permission answers only that ask" (engine) and the waiting-request block in "V2 never saves computer\_\*" (core).
3. **`isSensitiveAction` (core V2) already matched every `computer_*` id**, because `canAutoApprove` is false for the whole prefix. It was not extended; a comment now says so. The V2 save path now skips sensitive actions instead of relying on the purge in `savedRules`, as E1's note asked.
4. **The plugin bridge stays `Promise<void>`.** `packages/engine/src/tool/registry.ts` maps `toolCtx.ask(req)` through `Effect.asVoid` before handing it to a plugin, because `@vectordevai/plugin`'s `ToolContext.ask` returns `Promise<void>` and the wider type does not fit it. The plugin API is unchanged.
5. **Test harness.** "V2 never saves computer\_\*" uses an in-memory `PermissionSaved` replacement that records every `add`. Without it the test could not tell a write that the next `savedRules` read purges from no write at all: under the old code the post-save loop purges it within the same `reply`.

## 2026-10-28 E3 (agent defaults and plan-mode gating)

1. **Tool-list asks cover both kinds of tool-list agent.** The contract points at the research agents' block (374-376). The read-only specialists (explore, review, judge, security) also build their rulesets from a tool list, so both now spread `computerAsks(tools)`, a small function exported from `packages/engine/src/agent/agent.ts`. No agent's list includes `computer` today (subagents never get the tool, INV-S10), so the function is exported for the test to check directly. Those agents keep denying every `computer_*` through their `"*": "deny"`.
2. **Plan mode's denies are applied last as well.** The contract adds `computer_interact: "deny"` and `computer_sensitive: "deny"` to the plan block, which merges before the user's rules. In this codebase user rules override plan mode's own rules (for example `task: {general: allow}`), so a user or trusted-repo `"*": "allow"`, or `agent.plan.permission.computer_interact: "allow"`, would have reopened them. The two denies stay in the plan block and are also applied after the config loop and the user ceiling, so no rule reopens them. `computer_app` still asks in plan mode. The `computer` tool itself stays offered, because `Permission.disabled` keys on the tool id and not on `computer_*`. E6 can therefore read plan mode's observe-only state from the ruleset (`Permission.evaluate("computer_interact", "*", ruleset).action === "deny"`) as well as from the agent name.
3. **No allow evaluates to allow for a `computer_*` permission (stricter, ruleset level).** After the config loop, a final pass puts an ask for the same pattern right after every allow rule that covers a computer permission. That covers `"*": "allow"`, `"computer*": "allow"` and named or pattern-specific allows, from user, repository and agent config. So the merged ruleset reads `ask` where the runtime asks anyway (`PermissionPolicy.requiresApproval`, E1), and a deny written after the allow still wins. A deny written before an allow now reads as `ask`; before this pass it read as `allow`. The tool id `computer` is not touched. Session-level rules, which are merged after agent rules at run time, are outside this pass. requiresApproval still makes them ask, and E6's refusal in plan mode is the authoritative check there.

## 2026-10-28 E6a (bridge transport deadlines and cancellation)

1. **A dedicated Node HTTP client owns no hidden deadline.** The service uses Effect's `node:http` client with a scoped agent and `timeout: 0`; the shared fetch client can impose a header deadline before a long act or handoff finishes. The transport owns the complete act deadline, including response decoding, and a ten-minute queued-acquire deadline. `awaitControl` and `handoff` have no overall deadline. Other commands have a 30-second deadline; cancellation cleanup has its own five-second bound and never recursively cancels itself.
2. **Long polling preserves the root queue.** Desktop D13/D19 must return `pending`/`busy` at least once every 60 seconds. The engine repeats those replies, with a 100 ms pause to bound retries from an immediately busy bridge. It does not force a disconnect every 60 seconds: the contract makes disconnect a cancellation, which would otherwise discard that root's queue position on every poll. Act responses with `waiting` return immediately; E6b decides when to call `awaitControl`.
3. **A queued root needs cancellation without a lease.** The original `cancel` request required a lease, but `acquire wait:true` has none. Disconnect is insufficient when abort arrives between poll replies, leaving no active request to disconnect. `cancel.lease` is therefore optional: **without a lease, D13/D19 must remove only the authenticated request's `rootSessionID` from the acquire queue and must never stop or release an active holder**. A supplied lease retains the existing holder-work cancellation semantics. The transport sends this root-only cancellation on queued timeout, abort, or fiber interruption, including between polls. The shared schema and fake bridge pin this distinction for the desktop implementation.
4. **Transport tests are split by boundary.** `test/computer/transport.test.ts` uses an injected Effect HTTP client and TestClock for long deadlines and interruption; `test/tool/computer.test.ts` exercises the real local HTTP transport against the fake bridge. Neither accesses OS permissions, input, or screen content.

## 2026-10-28 E6 (root leases, app consent, and single actions)

1. **The conflict-resolution table governs app consent.** Section 1.3 explicitly says one `computer_app` ask covers seeing and operating an app; E6 bullet 3 would otherwise ask at observe level for a first read and again for a click. Normal tasks request interaction consent at first app touch, including reads. Plan mode and an app-specific interaction deny use observe consent and cannot send input. The legacy observe/interact permission names remain policy checks, never additional prompts.
2. **The caller chooses an approval ID.** `Tool.Context.ask` now accepts an optional `id`; the existing SessionTools wrapper already forwards it to Permission. The engine passes that exact ID to `grant` and `remember`. A rule-only context returning no answer cannot grant access. Desktop D16 remains the authority: it must observe the matching ask and user reply before accepting either command.
3. **Program paths resolve before launching.** The original `access` accepted only a name/key, while `openApp` accepted paths without an approval field. `access.app` now also accepts a path, which D16 must resolve without launching. `openApp.requestID` carries the separate once-only run-program approval for the canonical resolved path. The agent's path and an accessibility label are not identity evidence.
4. **Sensitive approval binds the whole proposed step.** Labels, app keys and frame IDs alone cannot distinguish same-labeled targets or different key combinations. `SensitiveAskMetadata.stepDigest` is the SHA-256 of canonical step JSON, computed by shared `ComputerSensitive.digest`. D16 must match it against the exact bridge step (or canonical open path), alongside app/frame evidence, before consuming a sensitive request ID once. The model never supplies this proof.
5. **Inspection can carry observed classifier context.** Optional `layout`, `focusedMenuShortcuts`, `programPath`, and `clipboard.text` fields supply E7's pure checks. They come from the desktop, never model assertions. Layout must match the app's platform; program paths must be canonical. Clipboard text means the complete contents within the bound, never a truncated preview. Missing or oversized clipboard evidence does not waive the desktop's live credential/paste checks. D16 and the native helpers must supply and re-check their actual observations before input.
6. **A later mention means a later message.** The root conversation retains denial message IDs across task boundaries. An app marker in the same message that received Deny cannot reopen that ask; a later marker lifts only the denial and asks again. Cached task grants never replace a fresh desktop access verdict, so revocation and changed identity take effect.
7. **One authoritative idle event ends the lease.** The existing SessionStatus service publishes `session.status` with idle followed by deprecated `session.idle`. Consuming both can stop a successor task started between them. The global ComputerSession service consumes the status event, cancels the task generation, drains its FIFO, and releases the lease. Conversation denials survive; frames and task grants do not. D13 must also release an acquire whose connection disappears before the engine receives its lease; root-only cancellation still removes only a queued root, as specified in E6a.
8. **Successful input gets a fresh budgeted capture.** The existing `act` request has no capture budget and its response lacks visible apps, hidden count and pointer. E6 follows it with `screenshot` using the active model's bounded plan, rather than trusting uncapped act pixels. It keeps the perceptual hash even when image output is disabled. This costs an extra capture; D19 may optimize only while preserving those guarantees. Image verification happens before a frame is remembered or returned, including the direct-completion abort path; rejected captures invalidate coordinate state. The processor also invalidates that state if its later normalization rejects the image after settings changed. Zoom never replaces the full-frame ring.

## E6b — Batches and attended control flow

1. **The state event belongs to the compatibility stream.** `ComputerEvent.State` is the single canonical `computer.state` definition and joins `EventManifest.Definitions`, reaching `/global/event` and the legacy SDK. It stays out of `ServerDefinitions` and the current Protocol event union because this release explicitly excludes V2 sessions from computer use. The current client generator is still run as requested; it should have no surface change. This follows the schema package's event-classification rule rather than promoting a V1-only event into the current API.
2. **Questions gain typed metadata.** Existing V1 Question requests had no metadata field. An optional union of `HandoffQuestionMetadata` and `CheckInQuestionMetadata` is now accepted by the Question service and retained in the request/event. Ordinary questions omit the field. The current Question contract is unchanged.
3. **A pause can wait by lease.** `awaitControl.waitId` is now optional: pointer waits retain their exact returned ticket, while an ordinary pause waits on the authenticated lease's control state. The original act pause/state and typed error did not supply a ticket. D19 must distinguish these two cases and never resolve a different lease's wait.
4. **Live batches retain engine policy restrictions.** `act.allowedApps` names only identities checked against the active agent/session policy for this call. It restricts access and never grants it. D16 must return an app pending gate for a live target outside this list, even when a desktop grant already exists; absent or empty lists authorize no engine-checked target. Without this field, a later batch step could reach an app whose desktop grant predates an engine policy denial. The engine adds an identity only after resolving and checking it at a pending gate. A fresh access verdict may confirm sufficient existing task or Always consent without another ask; only a newly observed ask ID is forwarded, never an old approval replayed merely to satisfy the policy gate.
5. **One step can need two proofs.** The existing approvals array can now hold up to twice the batch-step limit: distinct app and sensitive request IDs may share a rebased index. A new destination is checked before input, then asked again against a changed pending target when necessary. D16 must treat every supplied sensitive proof as a required gate for its observed ask reason, match the complete step digest and live target, and consume it once. A stale target proof must produce another pending gate even when the desktop's own classifier would otherwise permit the step; it must never be silently ignored. The ask's original step index describes the user's batch; the bridge approval index describes the resubmitted suffix.
6. **Generic batches can contain non-input actions.** The generic schema includes reads, captures, open and focus, while the wire `Step` union contains input and wait only. Contiguous input steps are sent together through `act`; standalone generic actions run between those groups in order. Executed prefixes are never replayed. After a pause or handoff, a fresh observation returns to the model and the remaining old actions are not resumed automatically.
7. **The lease owns its heartbeat and clock.** A two-second heartbeat continues between tool calls and stops with its task generation. Active time uses Effect's clock and excludes nested asks and desktop waits. Any heartbeat failure stops and releases the known lease; the desktop's engine-quiet timeout remains a separate backup. State is validated against the lease and holder before publication and throttled across heartbeat and act reports to once per second.
8. **Current-call observations count as outside content.** A batch can inspect a target before any of its output reaches saved history. `ComputerEntities.unvouched` therefore accepts an explicit observed flag from the tool's real inspection; its default behavior for other callers is unchanged. This closes the gap for new destinations proposed during the same call while retaining exact user-supplied destinations as evidence.
9. **Completed steps remain counted if capture fails.** Input counts come from validated `act.done`; reads and other standalone actions count once. Open/focus are counted as soon as their command succeeds, before capture. A separate completion marker distinguishes failure of an action from failure of its follow-up observation so the exact failure sentence is emitted for every unexecuted suffix action. Configured text budgets are shared across batch outputs before fencing, with no generic output-file spill.

## D10 — Overlay pages and layout

1. **Pages take views, not state.** The pages consume plain `OverlayMessage` objects (`glow`, `banner`, `cursor`, `fade`) from in-page `message` events whose `source` is the page's own window, and from `window.computerOverlay.onState` when a preload provides it. The pure `glowView(state)` and `bannerView(state)` in `features/computer/overlay-page.ts` build the views in main from phase, mode, backend, step, the pause, the secure-input app, the app in use, the open ask's id, kind and title, the queue's length, the stop keys and reduced motion; holder and queue titles, `ask.detail` and directories never reach an overlay renderer (INV-S11, INV-T2). Both return undefined for the remote backend and for `off`, `setup` and `ready`. `messageScript(message)` builds the `executeJavaScript` source (JSON with `<`, U+2028 and U+2029 escaped) and `pageUrl(html)` a base64 UTF-8 `data:` URL, because a `#` in a CSS colour would end a plain one. **D17 obligations:** load the pages with `pageUrl(glowStripPage(edge) | bannerPage() | cursorPage())`; send glow and cursor views with `executeJavaScript(messageScript(view))` and banner views through the banner preload's `onState`, never raw `ComputerState`; close or hide every overlay when `glowView`/`bannerView` return undefined; after the 2 s Done or Stopped flash, send every overlay its end view (the `bannerView` and `glowView` of the Done or Stopped state, whose glow view carries `end: true`, and a cursor `hide`) and then `{type: "fade"}`. Cursor messages carry window-local DIP (the global DIP point minus the window's origin). **D18 obligation:** in background mode, when `ComputerOverlayLayout.cursorVisible` is false, hide the ghost and set `step` to `ComputerMainCopy.workingBehind({app})`.
3. **Layout signatures.** `features/computer/overlay-layout.ts` (`ComputerOverlayLayout`, no imports) uses Electron-shaped DIP rects `{x, y, width, height}` and displays `{id, bounds, workArea, scaleFactor}`, so `screen.getAllDisplays()` passes straight in; no function reads `scaleFactor`. `stripBounds(display)` returns `{edge, bounds}[]` (top, right, bottom, left; top and bottom span the width, the sides sit between them; the thickness shrinks to a third of a tiny display). `bannerBounds(display, width, place = "top")` gains `place: "bottom"` for stepping aside; a non-finite width reads as 640. `stepAside(state, home, point | undefined, now)` takes an explicit clock (`Aside = {aside, clear, at}`, starting from `HOME`), treats a missing point as a timer tick, and measures against the top (home) rect only. A step within 24 px, inclusive, also restarts the 5 s while the banner is already down, so steps that keep landing under it never bring it back on the timer (planning critique); a step between 24 and 48 px resets the clear count only. **D17 obligation:** keep the `Aside` state per run, call `stepAside` for every pointer step (global DIP) and on a timer at `state.at + ASIDE.ms`, and place the banner with `bannerBounds(display, width, aside ? "bottom" : "top")`.
4. **The chord label moved.** `ComputerSettings.chordLabel` moved unchanged to `ComputerMainCopy.chord(accelerator, platform)`, because the banner needs it and desktop main cannot import the Settings model (it uses the `@/` alias and the onboarding model). `main-copy.ts` now imports `Computer` at runtime for `clean`. The Settings page's stop-shortcut sentence calls the new function; its rendered label stays covered by `hands-settings.spec.ts` in CI.

An app ask shows Deny and Allow; a sensitive ask Deny and Allow once, both click-only as in the dock (1.5 C "They respond to clicks only", D4); a handoff Continue; a check-in Keep going (`keep-going`); a pointer ask Hand over and Not now; every ask button carries the ask's `requestID`, and the banner never offers Always (INV-C4). Without an ask: Take over while working or waiting in the foreground; Resume for every pause reason, reading Keep going for the away pause (1.5 C) and sending `resume` (E6b step 4); a pointer pause with no ask shows only Stop (D9.6, D9.7). Press Continue when you're done."), falling back to "Your turn", rather than only "Your turn" (1.5 C), because the target app often covers Vector and the banner may be the only place that says what to do. **D17 obligation:** the `computer-overlay-act` handler rejects every action in `Computer.OVERLAY_ANSWERS` unless it carries a `requestID` equal to the open ask's id; a missing id is a mismatch. ## D13 — Bridge server

Each item keeps the contract's intent (sections 2.8 and 4.2 D13, INV-R4, E6a.1 to E6a.3, E6.7). Items 12 to 14 bind D19, D22 and C8.

1. **The executor seam.** `ComputerExecutor {run(request, key), cancel(key)}`. The key is the contract's requestKey, `{id, command, rootSessionID, sessionID, directory, lease?}`: frozen, new for every HTTP request, and passed to `cancel` as the same object `run` received. `ComputerError(code, message)` lives in `computer-bridge.ts` for D14, D16 and D19 to throw. `unavailableExecutor` is the stub until D19. `capabilities` is a function, sync or async, because availability changes at run time; a throw, a rejection or a value that `Computer.Capabilities` refuses answers 409 unavailable (the engine's probe then reports `bridge_unavailable`). A throw or rejection is logged by error name and a refused value by a fixed line without its values, so a capabilities bug that makes Hands unavailable still leaves a line. Every diagnostic goes to the `warn` function `startComputerBridge` is given (`(message, ...fields)`), which defaults to `console.warn` for the tests and the Node check: desktop main's console reaches only the process's stdout and stderr, never electron-log's files or the `exportDebugLogs()` bundle (`initLogging` spies only the renderer console), so D22 passes the log file's warn (D13.13).
2. **A client has left when the response or its connection closes before the response finished.** The contract says "the request's `close` before a response is written", but Node fires the request's own `close` as soon as its body has been read (Node 22.22 probe), so that wording would cancel every request and leave it unanswered; the Node check's "answered normally" case fails with exactly that change. The listeners go on the response and on `request.socket`, before any other work, and check `writableFinished`. The connection's `close` is needed for HTTP pipelining: Node never fires `close` on a response queued behind another on the same connection (it gets its socket only when the one ahead finishes), so without it a pipelined request's run was never cancelled and its late lease never released (Node 22.22 probe: an act and an `acquire {wait: true}` pipelined, then the connection destroyed, cancelled only the act and left lease 7 held). The connection listener is removed whenever the response closes, which Node does after every finished answer too, so a keep-alive connection gathers no listeners. The engine's client does not pipeline today; the bridge does not rely on that. A client gone before its command starts never starts it (its body was read, then it left); `cancel` runs at most once per request, only while its run is pending and never after it settled, after the current event (a microtask), and a throw or rejection from it is logged by command and error name.
3. **A lease the engine never received is released (E6.7).** An acquire that settles with `{lease}` after its client left or after `stop()` answered it, and an acquire whose `{lease}` answer was written but closed before it finished, get a `release` on the acquire's own envelope with a new key; a failing release is logged. Busy and permissions results release nothing. A lease whose answer finished belongs to the engine: if the engine dies after that, E6's idle release or D18's 10 s engine-quiet boundary ends it.
4. **Check order and refusals.** Host and token (401) come before the route (404), the protocol (426), the size (413) and the body (400), and a stopped bridge answers an authenticated request 409 unavailable, so a caller without the token learns nothing. `Host`, `Authorization` and `Vector-Computer-Protocol` must each be sent exactly once (read from the raw headers: Node keeps only the first of two `Host` lines). The token is compared as `timingSafeEqual(sha256(header), sha256("Bearer " + token))`, so both sides always have 32 bytes. Refusals (400, 401, 404, 413, 426) carry `connection: close`: without it Node drains an unread body after the answer, so a caller without the token could keep a connection reading an endless body; the bridge never reads such a body itself. Every response is JSON with `cache-control: no-store`, `x-content-type-options: nosniff` and no CORS headers; refusals are `{error}`, and only 409 is `{ok: false, code, error}`. A declared length over 64 KiB is refused before any byte of the body; otherwise the body is counted as it arrives, nothing past 64 KiB is kept, and the rest is read and dropped until Node closes the connection after the 413.
5. **Strict input.** Bytes must be UTF-8 (`isUtf8` from `node:buffer`; a fatal `TextDecoder` throws instead of returning, which would leave the request unanswered), a leading byte-order mark is refused, and `onExcessProperty: "error"` refuses an unknown field at any depth. The protocol header must be one decimal integer in [1, `Computer.PROTOCOL`]: missing, duplicated, `0`, `01`, `1.0` and `2` are 426. The E0 schemas already bound every string and carry the `ui_\d{1,6}` pattern, so nothing is restated.
6. **Output is encoded with the command's response schema, not decoded.** Every E0 optional field is `optionalKey` on the wire and `optional` in the type (`schema.ts` `optional()`), so a result with an explicit `undefined` optional key, such as `{done, frame: undefined, state}` or capabilities with `reason: undefined`, fails decoding but encodes with the key dropped (probe with effect 4.0.0-beta.83). Encoding also drops unknown fields at any depth and still enforces every check. A result that does not encode is 409 failed, logged by command; an encoded body over 8 MiB is 409 `frame_too_large` and exactly 8 MiB is sent. Any rejection other than a `ComputerError` is 409 failed with a fixed sentence and logged by command and error name only; a rejection or a mismatched result is logged even when its client has left or `stop()` already answered, because a run that fails while it is being cancelled is the likeliest executor bug. A `ComputerError`'s text has the token replaced by `[redacted]`, is cleaned with `Computer.clean(text, 2000)` and is then cut to 2000 UTF-16 units without splitting a surrogate pair: `clean` counts code points while `BridgeFailure.error` counts units, so 2000 emoji would fail `BridgeFailure` and the engine would report a generic failure instead of the code. A `ComputerError` whose code is outside `ComputerErrorCode` (a cast code, as from a helper built against a newer or misspelled list) is not a refusal: like any other rejection it is 409 failed with the fixed sentence, and it is logged as the fixed line "Computer bridge error code is not known" with the command, neither the code nor the text, also after its client left, so version skew between a helper and desktop main still leaves a line.
7. **Instance-based, with a bounded stop.** `startComputerBridge` keeps no module state, unlike the browser bridge. `stop()` cancels each pending run, answers every open request 409 unavailable ("The computer bridge stopped.") with `connection: close`, refuses new work, closes the server and its idle connections, waits for the close at most 1 s and then cuts what is left; it is idempotent. Node's server timeouts fit the long polls: `requestTimeout` (300 s) applies only until a request has arrived, `headersTimeout` is 60 s and `server.timeout` is 0, so a received request may wait as long as its command needs.
8. **A Node-run check of the bundled bridge (a CI addition).** Bun 1.3.14's `node:http` never reports a client that leaves, so `createBridgeHandler` is exported as a test seam that the Bun unit test drives with a stream request and a recording response, and `test/computer/bridge-node.ts` checks the bundled bridge under Node: a cancel with run's key when the client leaves, a client that leaves at once never leaving work uncancelled, the undelivered lease's release, no cancel for an answered request, `stop()` during a long poll, an early 413 while the client still sends, a 401 whose endless body is cut off, a pipelined act and acquire whose client leaves (both cancelled, the late lease released), and twelve sequential requests on one keep-alive connection with no `MaxListenersExceededWarning`. The unit-lane step bundles it with `bun build --target=node` and runs it under the job's Node 24. Each check is bounded by 1 s except the `stop()` check, 5 s, because Windows retries a loopback SYN that an RST refused (TcpMaxConnectRetransmissions) for about 1 to 2 s before it reports `ECONNREFUSED`, and that check requires exactly `ECONNREFUSED` after the stop; the bridge's own deadline there is unchanged: `stop()` must still resolve in under 900 ms. In the Bun test, oversize and raw-header requests use one fresh `node:net` connection each, because Bun's shim misread a reused connection after an oversize body (a 431 from its own parser in a probe). The Bun test also checks the bind itself, since the URL is built from `Computer.BRIDGE.host` whatever address the server listens on: `::1` and `127.0.0.2` on the bridge's port must be refused (a wildcard bind accepts them), each tried only where the host can listen on it (macOS has no `127.0.0.2`, some hosts no IPv6), and at least one must be usable.
9. **The timingSafeEqual test mocks `node:crypto`** with the originals copied into a plain object first; a factory that spreads the live module namespace hangs Bun 1.3.14. The mock covers the whole file, which is safe because each desktop computer test file runs in its own Bun process.
10. **The unit step finds desktop main's files by name.** It also runs `./src/main/computer-*.test.ts`, so D14 to D23 need no workflow edit (extends C1.11). The token is `randomBytes(32)` as hex, as the contract asks, not the browser bridge's `randomUUID`.
11. **The bridge does not decide whether it runs.** It reads no environment, adds no IPC and is not started from `index.ts`; D22 does that.
12. **For D19.** `run` executes every command and `cancel(key)` stops only that request's work: for an `acquire` key, remove that request's queue entry and never release or stop an active holder (E6a.3); for an `act` key, stop that act and `input.releaseAll`; for an `awaitControl` key, end that wait; for a key whose work already ended, do nothing (the bridge never sends one, but `cancel` must be idempotent). The `cancel` command itself arrives through `run`: without a lease it removes only that root's queued acquire. A run that `cancel` ends should settle with a `ComputerError` with a known code (for example `stopped`): any other rejection, or an unknown code, is logged even after its client left (D13.6). A `release` the bridge synthesizes carries the acquire's envelope and is an ordinary release. Long polls (`acquire` with `wait`, `awaitControl`) must answer within 60 s (E6a.2).
13. **For D22.** Start the bridge with D19's executor, the capabilities function and `warn: (message, ...fields) => getLogger().warn(message, ...fields)` from `src/main/logging.ts`, so its lines reach the desktop log files (D13.1), put the URL and token only in the sidecar's start message (never its spawn environment), and call `stop()` on `will-quit`.
14. **For C8, a gap the contract leaves.** No package checks the disconnect and `stop()` paths under Electron's own Node runtime; the evidence is Node 22.22 locally and Node 24 in the unit lanes. C8's desktop e2e should abort an in-flight bridge request (expecting the cancel and input release) and quit with a request open (expecting it answered and the bridge closed).

## D14 — Helper protocol, supervisor and native backend

1. **One production codec, with bounded framing.** `computer-protocol.ts` consumes partial length prefixes and UTF-8 JSON, pairs capture headers with exactly one binary frame, and discards oversized frames while streaming. Invalid messages expose fixed diagnostic text, never private payloads. Request IDs start at 1; malformed/id-0 responses fail the client closed. Per-op schemas validate every response, and a helper cannot manufacture the supervisor's `exit` event.
2. **The supervisor has injectable OS boundaries.** `ComputerHelper` owns signature/hash preflight, fixed paths/argv, detached native processes, hello, heartbeats, deadlines, restart admission and a one-shot probe. Tests inject the in-process C1 helper and a manual clock, never real native input or OS permissions. The Mac Team ID is read once per supervisor, with strict helper verification on each start. Unknown signing identities do not become ad-hoc builds. Windows requires the caller's build-time hash for the current architecture; C3/D22 still supply it. `helper_missing` is an availability reason, not a wire error code, so `HelperUnavailableError` preserves that reason with the existing `unavailable` code.
3. **Every launch shares the restart budget.** After the first launch, automatic restart, demand-driven request/start and explicit Resume all use the same three-per-rolling-minute admission. A crash during a run latches until explicit Resume. ## W9 proposal for owner review — real calibration and a separate listener heartbeat

**Owner approved on 11 November 2026:** “Yes, implement the setup check and listener health redesign.” Implementation and verification are in progress; approval is not a passing native/device result. This section preserves the reviewed proposal for the now-approved revision to [W9, User-input detection and Stop](./hands-build-spec.md#w9--user-input-detection-and-stop-helper-side). The previous contract required a tagged no-op probe every two seconds and its actual Raw Input receipt within 500 ms. The previous production service also required an initial matching pulse before foreground readiness. The approved design replaces that periodic end-to-end raw-packet proof with two separately described proofs; it is not a reinterpretation of a metadata heartbeat as hardware delivery or a test-only bypass.

Current source anchors are [service readiness, sample acceptance and challenge scheduling](../../../packages/desktop/native/computer-helper/windows/src/user_input.cpp#L129) and [actual callback provenance, zero-move submission and exact route ownership](../../../packages/desktop/native/computer-helper/windows/src/user_input_native.cpp#L153). The service currently rejects a 500 ms expired challenge, requires its initial pulse, refreshes challenges at two seconds and refuses stale listener/scope identity. The native listener checks actual registered routes and pumps a bounded message batch; neither successful registration nor a live thread alone currently counts as the matching pulse.

The reason for review is an API guarantee gap, not a proven diagnosis of every hosted failure. Microsoft documents `SendInput` success as insertion into an input stream, not a guarantee that a zero-distance move produces `WM_INPUT`. `WM_INPUT` is a separate registered device-message path whose packet is read through `GetRawInputData`. Thus a zero-distance `SendInput` cannot supply the documented periodic receipt guarantee assumed by the present design. [Wine's zero-move handling](https://github.com/wine-mirror/wine/blob/c28e3a549fc76b9c3c2f92058db98a1c78a9325d/server/queue.c#L2219) is additional source evidence, not proof that real Windows always drops these probes. [SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput), [WM_INPUT](https://learn.microsoft.com/en-us/windows/win32/inputdev/wm-input), [GetRawInputData](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getrawinputdata).

**Approved change:** allow one-time actual mouse and keyboard Raw Input calibration for the current listener generation and verified environment, followed by a private listener-thread heartbeat every two seconds with the existing 500 ms response deadline. Calibration proves delivery once. Heartbeats prove only that the same listener thread, window route and bounded processing path are healthy at the checked times. They do not prove that new hardware packets are still being delivered. The owner accepted this changed periodic guarantee; silent device/kernel delivery failure with a healthy pump remains a residual limitation. Runtime and device validation are still required.

### Proposed admission and proof boundary

1. Start in **Needs calibration**, with all agent mutations denied. Create the existing private Raw Input listener and verify its current generation, exact message-only HWND, both mouse/keyboard registrations, expected flags, listener-thread health, current default input desktop and permissible helper/foreground integrity. Do not adopt or overwrite another route. Microsoft notes that the last registration for a device class wins within a process; successful registration alone is insufficient, so inspect the actual routes. [RegisterRawInputDevices](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerrawinputdevices), [GetRegisteredRawInputDevices](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getregisteredrawinputdevices).
2. In an explicit setup UI, ask the user to move the pointer and tap/release the shown safe modifier. Accept calibration only from real `WM_INPUT` callbacks handled by that current listener, successfully decoded with the existing strict mouse/keyboard shape checks and reported-hardware provenance. Both device classes must be demonstrated; a private heartbeat, `SendInput` return value, own marker, posted message, low-level hook or unknown/system-origin sample cannot satisfy either bit. Provenance must be sampled in the callback, not invented later; unavailable provenance remains unavailable. Microsoft's source-identification API reports message-source facts, not a general proof of physical authenticity. [GetCurrentInputMessageSource](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getcurrentinputmessagesource).
3. Keep only mouse-seen/keyboard-seen calibration state bound to the exact generation/environment and the existing bounded transient modifier/release state needed to finish the gesture safely. Do not translate characters, retain key history, log scans/key values, device names, raw packets, cursor coordinates or identifiers, or persist calibration across helper/listener restarts. Setup has no agent injection. Missing either class leaves the agent unavailable; unknown provenance must not be downgraded to hardware to make setup complete.
4. After calibration, require a fresh private metadata challenge completed on the **same raw listener thread**, then the user's explicit Start/Resume. Each challenge carries the listener generation, current session/run/observation epoch and revision, a monotonically increasing sequence and one absolute deadline. An acknowledgement from another thread, prior generation/scope, duplicate sequence or expired request is rejected. Generate/check its deadline at issuance; queueing, dispatch and final acceptance consume that same 500 ms, with no new budget when the listener wakes. Continue at the existing two-second cadence. The response contains bounded private metadata, not `WM_INPUT`, raw event content or an assertion of recent hardware delivery.
5. On that listener thread, service the private challenge through the existing bounded pump and verify exact registration ownership plus fresh desktop/integrity facts before acknowledgement. At service admission and final mutation/publication fences, require calibration, a healthy current listener, the current-scope heartbeat and all existing policy/epoch checks. A fresh environment observation remains subject to the existing 500 ms freshness check; the heartbeat does not waive it. A scope change retires all old challenges/readiness. Reusing calibration is allowed only while the exact listener generation, route/configuration and verified environment remain unchanged; the new scope still needs its own fresh challenge and explicit Start/Resume.
6. Any unknown/malformed raw sample, registration/configuration or device change, listener/thread/window failure, desktop/session/integrity change, expiry, cancellation or shutdown first revokes local readiness and mutation authority, initiates existing held-input release, and retires outstanding challenges before any queued notice can publish. Require explicit recalibration after an invalidated generation/environment; never let a heartbeat revive it. If state cannot be verified, remain paused. No automatic Resume follows calibration, a healthy acknowledgement or a later return to the default desktop.

The production detector still uses Raw Input to identify actual takeover and the existing Esc/chord rules, with its minimal callback separated from capture/UIA work. Genuine takeover still revokes before unsolicited event publication. Main's independent banner/tray/chord Stop, cancel/EOF/shutdown handling and five-second dead-man cleanup remain intact. This proposal adds no low-level detection hook, synthetic `WM_INPUT`, periodic cursor displacement, helper privilege/service, unattended calibration or replacement for the separate guardian's actual full receipt/release predicates. Capture, input and UIA deadlines are outside this revision.

### Required user-facing state

Setup must say plainly: “Move your pointer and tap/release the indicated key so Vector can verify takeover detection. The agent will stay paused during setup.” Show separate mouse/keyboard completion indicators and distinguish **Needs calibration**, **Checking listener**, **Ready after calibration**, and **Paused — detection unavailable**. The ready explanation must say that delivery was calibrated and the listener is being health-checked, rather than claiming continuous hardware delivery proof. Provide explicit Recalibrate and Start/Resume controls. A closed calibration/health reason may explain failure without exposing input content. Inability to calibrate a supported device, VM or remote session must remain visible and unavailable; it is not permission to fabricate a pass or silently fall back.

### Validation required before an implementation could be accepted

- **Source and pure state-machine checks:** exercise actual shared admission/retirement code at exact 500 ms expiry and the two-second schedule; reject stale generation, HWND, epoch/revision, sequence, duplicate and late acknowledgements; prove that heartbeat-only startup, one-class-only calibration, unknown/injected/own-tag samples and synthetic messages cannot enable mutations. Test reset/recalibration and queued-publication races, no implicit Resume and bounded metadata with no raw/key history. Tests must separate “calibration observed” from “pump healthy,” rather than renaming the old synthetic-receipt assertion to green.
- **Actual native x64/ARM64 checks:** build under the unchanged warning policy; use an owned isolated listener/window fixture to verify real registration readback and loss, same-thread challenge processing, termination and cancellation, exact deadline handling and generation retirement. Stall the actual listener thread and reconfigure only its owned routes to prove revocation/cleanup.
