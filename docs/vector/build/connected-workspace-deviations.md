# Connected workspace: where the build departs from, or reads into, the contract

## 2026-11-09, CW-02 (core connect/policy.ts, findings.ts, frame.ts)

The contract was right about the code for CW-02. These are choices where it is silent, all on the fail-closed side, recorded so CW-03 to CW-08 build on the same reading:

- **`connect_model` for an unreadable price.** `reviewConsents` asks `connect_model` for a model whose cost kind is `unknown`, as for a priced one, because Vector cannot show it is free (I10). `plan` (Codium), `free` and `local` do not ask unless the repository picked the model.
- **Any spend-guard stop refuses.** `effectiveCap` refuses a review whenever `run.stopped` is set, whatever the stop reason, and when a run with a dollar limit has nothing left. A local model still has no dollar cap.
- **The check-command list is read, not copied.** `checkCommands` and `checkCommandRules` read VectorScope's list from the exported `reviewPermissionRules({ checks: true })`, since `CHECK_COMMANDS` is not exported, so both stay one list. The fix child's rules are VectorScope's bash rules with `allow` turned into `ask`, after a leading `bash * deny`.
- **Read-pattern selection is sound, not literal.** `readPatterns` drops a pattern only when a later requester allow covers it, or when a VectorScope deny covers it and no later VectorScope rule could reopen one of its files without a later requester allow. Under the build agent's defaults this gives `.docker/config.json`, `**/.docker/config.json`, `.kube/*` and `**/.kube/*`, as section 3.2 says; a user's own deny on `*.env.*` is kept, because VectorScope reads `.env.example`. `readBlock` is the exact per-file check the hub runs on what it finds.
- **Check 1 ignores letter case** and also fires when the `.vector` directory itself changed, because on a case-insensitive disk `.vector/Review.json` is the file the review reads.
- **Comparing working-tree reviews.** An earlier finding nothing matched is labelled `fixed` only while its file is still among the reviewed changes (when the caller passes them); otherwise it is left out with a note. A match with an earlier `dismissed` finding stays `dismissed`. Fixed findings are appended with an empty body. For a branch, a fixed finding keeps the bucket the earlier run gave it, or reads as `still-open` (from VectorScope's state) when that run does not name it.
- **The model-facing findings block is bounded.** `frame` lists every finding, but past about 40,000 characters later findings lose their bodies, and past half again as much they are counted; the text then points at `connect findings` with the run id. Results themselves still carry up to 200 whole findings.

## 2026-11-09, CW-03 (engine connect/adapter.ts, hub.ts, members.ts, adapters/index.ts)

The contract was right about the code for CW-03. These are the readings where it is silent or only sketches a shape, recorded so CW-04 to CW-09 build on them:

- **Names.** Engine modules re-export themselves as a namespace, so the adapter interface is `ConnectAdapter.Adapter` (with `ConnectAdapter.HelperHandle`, `ConnectAdapter.HandoffContext` and `ConnectAdapter.Factory`), not a bare `ConnectAdapter` interface. `adapters/index.ts` exports `ADAPTERS`, typed `Factory<never>[]`; CW-04 widens that type to the services its adapter needs and adds them to the hub's `deps`, where the layer graph checks them.
- **The context carries more.** Besides the contract's fields, `HandoffContext` has `spend` (the requester's run as `ConnectPolicy.RunSpend`, from `guard.running`, `guard.snapshot` and `guard.stopped`, for `effectiveCap`), `previous` (the `since` run) and `source` (the review a fix works from). `progress` takes an update without `at` and stamps it.
- **The hub asks `connect` itself.** Before it hands a run to the adapter, the hub asks `connect` with the pattern `<member>.<action>` (`vectorscope.review` for a review), once per run, so a user's `connect: deny` holds whatever an adapter does. The adapter asks `connect_model` and `connect_write` through `context.ask`; the hub asks `connect_model` once per request for each model, and `connect_write` every time with no "Always" patterns.
- **Read rules come first.** The hub runs the read-rule check before the adapter, so for a review it comes before section 4.2's checks 1 and 2: nothing is asked about a model for a review the read rules would refuse anyway, and no model runs in either order. The check walks every file and directory under the review directory except `.git`, enters a directory only when one of `ConnectPolicy.readPatterns` could match beneath it, follows a link to a directory inside the review directory under the link's own name (a link that leaves it is an external read, which review sessions are denied), confirms each match with `ConnectPolicy.readBlock`, and refuses (fail closed) on an error or past 500,000 entries.
- **What the hub refuses on its own.** Everything while `experimentalConnect` is off; `background: true` until CW-08; a requester session that is a hidden helper (`internal` set: no chains); a run whose directory does not exist; a member whose `describe()` fails, names another id, lacks the action, or is not ready; a `since` that is not a review of a comparable target in the requester's session; a fix whose run or finding ids are not there. The requester's rules are its agent's (`requester.agent`, else the default agent) merged with its session's. A run with no session asks through the caller's `ask` or is refused at its first question.
- **Request id and the cap.** The hub derives the request id itself (the last message the user wrote, newest first, through `Session.findMessage`), never from the caller; a run with no session is its own request. The per-request cap counts review runs saved in the session since that message plus the ledger's, each once; a refused run did no work and does not count.
- **Results.** A tool part or note stores the whole encoded run under `metadata.connect` (`ConnectHub.metadata`); `fromPart` reads it back only from a `connect` tool part or a synthetic text note. An adapter result the schema refuses fails the run; a refused, failed or cancelled review reads `not-reviewed`.
- **The helper handle** also refuses a session whose `internal` name is not the member's own (`vectorscope.…`), any call once the run is over, and more than 200 helper sessions. On a cancel the hub cancels every helper session the run prompted, through the caller's prompt calls.
- **Registry.** `members.ts` lists agents (not hidden ones), the named helpers, Parallel Workspaces, skills, saved workflows, MCP servers and the GitHub agent (from `.github/workflows/vector.yml`); members reached through a tool (`tasks`, `browser`, `computer`, `vector-cloud`, `tool:<id>`) only when the caller passes `ToolRegistry.ids()`, as the HTTP view will. Only adapters report `sendsTo`: an agent's or tool's destination follows the session's model, which the registry does not resolve (no model call, no catalog fetch). Vector Local turns a ready member off when it runs in a cloud or sends code past this computer and the listed model servers; MCP servers keep MCP's own "Off in Vector Local" status.

## 2026-11-09, review repairs for CW-01 to CW-03

A review of phase A1 found places where the contract reads the code wrongly or where CW-02 and CW-03 chose the open side. These readings refine, and where named supersede, the two entries above:

- **The read check covers the repository, not the folder.** Section 3.2 says the hub globs "the review directory". A reviewer reads the whole worktree with no external-directory question, VectorScope reviews from git's top level, and the read tool names files relative to the instance's worktree. So the hub checks from the instance worktree when it holds the folder, naming files relative to it; a folder of an instance outside git from the folder itself, also naming files relative to "/" as the read tool does there; a folder outside the instance (a task's worktree) from the nearest folder at or above it that holds `.git`. `ConnectPolicy.readBlock`'s doc now says this.
- **Links in the read check.** A link to a directory inside that root is walked again under its own name only when some rule could tell a file under it from the same file under its real name (`ConnectPolicy.sameBeneath`, over every pattern of the requester's read rules, the ask when none matches, and VectorScope's review rules); otherwise its files are checked where they lie. A package store linked from many workspaces is walked once. `MAX_SCAN` rises from 500,000 to 2,000,000 entries.
- **Read errors fail closed.** Only a folder that vanished during the walk (ENOENT, ENOTDIR) is skipped. Any other error, and any error on the top folder, refuses with `read-rule`, as the CW-03 entry already said.
- **Vector Local at admission.** The hub applies `ConnectMembers.gate` when it admits a run, so a member that reports ready but runs in a cloud or sends code past this computer and the listed model servers is refused with `unavailable` before anything is asked.
- **Requests.** With the flag off, `run` returns a refused run and reads, records and publishes nothing. A request the schema refuses ends refused with `input`, unrecorded, unpublished and with no adapter call; `run` never dies on it. A requester of kind `agent` whose session has a parent (a subagent) is refused with `not-allowed`; a workflow stage (`kind: workflow`) is not.
- **The request a run belongs to.** An automatic compaction after an overflow copies the user's last message into a new user message after its marker and summary. The hub skips that copy and walks on to the message it copied, so the per-request cap and the once-per-request `connect_model` answer hold across it. Text parts marked `ignored` are not the user's words, as for `SessionTaskSize.real`.
- **Saved runs.** Only a `connect` tool part in an assistant message carries a run. The synthetic-note branch is gone until CW-08 defines a note a client cannot write, because a client can send a synthetic text part with any metadata. A saved run that never ended (its tool part was cut off) reads as cancelled, "Vector stopped before this hand-off ended.". `runs({ sessionID })` merges that session's saved runs with the ledger's. `since` compares only with a review that completed or was partial. Signing saved runs, or checking their helper sessions, was not added: the first needs a key the engine keeps across restarts, and the second accepts reused ids. The guest-writable part route (`PATCH /session/:id/message/:mid/part/:pid`) is the server owner's to close.
- **Dismissed findings.** This supersedes the CW-02 bullet "A match with an earlier `dismissed` finding stays `dismissed`". `compareWorktree` no longer carries `dismissed` over from a saved run: the match reads `still-open`. Only CW-17's owner click dismisses.
- **`connect_write` before CW-07.** The hub refuses `connect_write` with `permission` while `PermissionPolicy.requiresApproval` does not cover it, because until CW-07 adds that line nothing keeps an allow rule, a saved approval or an auto-accept from answering. The hub test checks both states, so CW-07's line turns it into "asked every time" with no test change.
- **The helper handle** also refuses the requester's child sessions that existed when the run was admitted (an earlier run's helpers), a session another live run holds, and a prompt that sets `tools`, `budget` or `noReply` or runs as any agent but the member's own (`review` or `security` for VectorScope).
- **Remote MCP servers** are listed with place `your-cloud`, since their code runs on another host. MCP members keep MCP's own status and skip the registry's Vector Local gate, because MCP applies Vector Local to its servers itself.
- **Framing.** `escapeUntrusted` escapes every "<" and the characters that read like one (fullwidth, small, angle brackets and quotes) after dropping format characters (`\p{Cf}`), instead of only "<untrusted". A ">" is left as it is: without a "<" nothing reads as a tag.
- **Check 1 through links.** `editedSettings(changed, links)` also takes the settings paths whose real path differs from their own (CW-04 resolves `.vector` and each `SETTINGS_PATHS` entry with realpath, relative to the repository root). It fires when a change edits a link's target or a file beneath a linked directory, and when a link could not be resolved (fail closed). A target outside the repository cannot be edited by the changes and does not fire.
- **Not done: MCP status without starting MCP.** `MCP.status()`, the registry's MCP source in section 3.1, sets up MCP's per-instance state on first use, which starts every configured server. A status read that does not start MCP needs a change in engine mcp/index.ts, outside connect's files (sections 7.2 and 7.3), so `members()` keeps calling `MCP.status()` until the owner allows an additive read there.

## 2026-11-09, CW-04 (engine connect/adapters/vectorscope.ts, connect/review-prompt.ts)

The contract was right about the code for CW-04. These are readings where it is silent or where the code made one choice necessary, all on the fail-closed side:

- **Check 1 reads settings changes from the working tree, whatever the target.** `executeLocalReview` reads review.json, review.md, REVIEW.md and .gitattributes from the working tree for every non-PR target, so check 1 looks at every path that differs between the target's base (HEAD, or the merge base for a branch) and the working tree or the index, at untracked files, at the branch's own commits, and at untracked files git ignores under `.vector` and `.gitattributes` (an agent can write an ignored settings file as easily as a tracked one). A staged review therefore also stops when an unstaged edit touches a settings file. `changed`, used to compare with an earlier review, stays the target's own list. A git error, a missing base or a repository with no commits refuses with `input`, so check 1 never passes on what it could not read. Settings links are resolved as the A1 entry says; a settings path that resolves to the repository's top level itself counts as unresolved.
- **Readiness comes before check 1.** The hub calls `describe()` when it admits a run, and `describe()` reads review.json from the instance's worktree and resolves the review and triage models through `resolveReviewModel`, `MIN_CONTEXT` and `capabilities.toolcall`. A model that cannot run refuses the run with `unavailable` before check 1. So does an edit under `.vector` that voids workspace trust, when the review model's provider comes from the project's own config. No model runs either way, and the result is never clean. "Off" is reported when Vector Local is on and the resolution error carries the provider's own "off in Vector Local" wording; every other failure is `unavailable`.
- **One network note.** For a Vector Codium review model, the provider's `getModel` may wait for vectordev.ai's Codium catalog when the account has none yet. That is an existing destination, reached through `resolveReviewModel` as section 3.1 names it; connect adds none.
- **The model the review uses is the one connect checked.** `executeLocalReview` resolves its models again. Connect wraps `resolveModel` so that a review or triage model other than the one check 2 resolved (and asked `connect_model` about) fails the review with a plain message instead of running.
- **Cap and consent over two models.** The dollar cap is worked out as local (no cap) only when every model is local; otherwise for the priced, unknown or other non-local kind. Personal Brain documents go only when every model sends to this computer or a model server, never in a shared review. A result's `sendsTo` is the review model's, or the triage model's when that one sends the diff further, with a note naming both when they differ.
- **Results.** Check 1 firing gives state `completed`, verdict `incomplete`, the settings note and no `sendsTo`. Nothing to review gives `completed` and `not-reviewed`. A review that could not start or whose every reviewer failed gives `failed` and `not-reviewed`. A partial outcome, a pass that failed, timed out or stopped, or an unreviewed file gives state `partial`. A cached outcome carries no sessions and no cost, since this run made and spent nothing. Any Codium involvement shows as plan usage with no dollars. Stdout is read only for `cached`; every note is Vector's own.
- **What the adapter refuses itself.** Through CW-06 it lists only the `review` action (`fix` arrives with CW-07). It refuses with `unavailable` a run with no session to parent the reviewer sessions, and a run with no prompt calls to build the helper handle from. The bridge also refuses prompt options, as well as every member but `prompt` and `cancel`.
- **Layer graph.** The adapter's services join the hub's dependencies through `connect/adapters` `DEPS`. `ConnectHub.node` depends on both; `ConnectHub.nodeWith` (tests with fake adapters) keeps the hub's own `ConnectHub.DEPS`. None of the added nodes reaches the prompt loop or the tool registry.
- **Owner.** VectorScope's member carries owner `vectorscope`: the code is on main, but it is VectorScope's.

## 2026-11-11, CW-05 (engine tool/connect.ts and connect.txt; registry.ts, agent.ts, session/memory.ts, connect/members.ts)

The contract was right about the code for CW-05. These are readings where it is silent, or where the shared-file line counts came out slightly different:

- **Shared-file lines.** registry.ts has 7 added lines, not 6: the import anchor holds two imports (`ConnectTool` and `ConnectHub`, the second for the `ConnectHub.node` deps line). session/memory.ts changes the two `taint` call sites as the contract says, but at 120 columns the formatter splits the first condition, so that hunk is 1 line out and 4 in. agent.ts has exactly the 2 lines. Every hunk sits at its named anchor, more than two unchanged lines from the hands and vector-at-mention hunks in the same files.
- **Who the tool refuses, before any hand-off.** Any agent but `build`; a session with a parent (from `ctx.parentID` or the stored session) or with `internal` set; a session `FreeModelGuests.marked` reports; and, for `review` only, a Light or chat request (with the escalate hint) or a request the engine did not size (fail closed: the build agent's root requests are always sized, so only an unexpected caller gets here). These refusals are not runs: nothing is recorded, published or counted.
- **The size gate covers `review` only.** `findings`, `status` and `cancel` read or stop what this session already holds and spend nothing, so they also work on a Light request (the user asking "what did it find?" is usually Light). Subagents, helpers and guests are refused for every action.
- **Only a review saves a run.** The tool saves `ConnectHub.metadata(run)` in its part for `review` alone. `findings`, `status` and `cancel` save `{ action, run }` under other keys, because the hub reads a run from any `connect` tool part, and a copy of an earlier review in a later part would count toward the later request's cap.
- **Arguments the action does not take are refused**, not ignored: `run` or `findings` on a review, and `base` with a target other than `branch`. `max_cost` is held above 0 by the parameter schema (an invalid-arguments error) and checked again with `ConnectPolicy.maxCostInput`. A `since` that is not a run id goes to the hub, which refuses the request with `input`.
- **Output.** A review's output is `ConnectFrame.frame(result)`; the run id line ("Pass it as `since` ...") is added only for a completed or partial review. `findings` puts the selected findings, with bodies and suggestions, in the same untrusted block under the same preamble; `status` uses only Vector's words (summary, verdict, where the diff went, cost), never finding text.
- **Connect's own tool is not a member.** members.ts adds `connect` to the tools that are not listed as `tool:<id>` members, now that `ToolRegistry.ids()` includes it while the flag is on.
- **The hub is built with the registry whatever the flag.** `ConnectHub.node` is in the registry's deps, so its layer (and the VectorScope adapter's, which only captures services) is built with the flag off too. It reads, records and publishes nothing then, and the tool is not offered.
- **Known edge of the name rule.** `taint` reads a tool part named `connect` as a subagent's report by its name, as the contract says. A custom or plugin tool a user names exactly `connect` is therefore held as `subagent` rather than `mcp`, flag on or off. Both hold memory writes for the user; only the stated reason differs.

## 2026-11-11, review repairs for phase A2 (CW-04 to CW-06)

A review of phase A2 found eight things; all eight held up against the code (the two on the registry's name check are one finding). These readings refine, and where named supersede, the CW-04 and CW-05 entries above:

- **A stored outcome sent nothing.** This supersedes the CW-04 bullet's "A cached outcome carries no sessions and no cost": it also carries no `sendsTo`, since section 3.2's `sendsTo` is where this run sent the code, and the triage-model note is left out. It gets the note "Connect sent no code this time: these findings are from that earlier review." (`VectorScopeAdapter.CACHED_NOTE`).
- **Check 1 runs three times.** Once before anything else, again right before `executeLocalReview` (after the `connect_model` question, which can wait on the user for any length of time, and after the lazy load), and once more after it returns. An edit found the second time gives the plain check-1 result with no model run. One found the third time gives `completed`, `incomplete`, no findings, the settings note plus "They changed after connect checked them, while the review ran, so what it found is not shown." (`SETTINGS_CHANGED_NOTE`), and keeps the run's sessions, cost and `sendsTo`, since they were made, spent and sent. A git error in the third check counts as an edit. What is left: an edit made and undone between VectorScope's own read of its settings and the third check. Those reads are in cli/cmd/review.ts (VectorScope's, section 7.1), so connect cannot see the bytes the review read.
- **Check 1 reads raw bytes too (`drifted`).** git's view of the working tree can be told to look away: an assume-unchanged or skip-worktree entry (sparse checkout sets skip-worktree), `core.ignoreStat`, `core.trustctime` with `core.checkStat`, or a clean filter defined in `.git/config` with an attribute in `.git/info/attributes`. (The engine's git already runs with `core.fsmonitor=false`.) So check 1 also compares every settings file's bytes in the working tree, read as the review reads them, with the same file at the target's base, through `git cat-file --batch --follow-symlinks`. A file that is there is looked up under its real path, so links and a case-insensitive disk read the same file on both sides. One that is not there is looked up under its own name, with git following links inside the base tree. Carriage returns before a line feed are ignored, so a checkout's line-ending conversion is not an edit. A file on one side only, or one git cannot answer for, counts as edited. A base link that leaves the repository counts only once the file no longer leads out of it, so replacing such a link with a folder in the repository edits every settings path beneath it. Settings files under a smudge filter, `ident` or `working-tree-encoding` now always fire check 1 (fail closed; none of them is a usual setup for these four files). On a case-insensitive disk an edit to `.vector/review.md` is listed under both `review.md` and `REVIEW.md`, since both names read that file.
- **VectorScope's branch state file is trusted only when connect saw VectorScope write it.** The state file (`<git dir>/vector/review/<branch>.json`) is plain JSON, and a shell can write it. The adapter keeps, in memory, a hash of each state file as VectorScope left it after one of connect's branch reviews, and passes `full: true` to `executeLocalReview` whenever the file differs, or connect has no hash for it. A stored outcome (`cached`) or an earlier head (an incremental range) then always comes from what VectorScope wrote. The cost: the first connect branch review in an engine process, and the first after a restart or after a `vector review` of that branch, reviews the whole branch, and VectorScope's state starts over from that review, so findings an earlier `vector review` left open do not come back as still open or fixed in it. Re-reviews (`since`) in the same process keep VectorScope's labels. What is left: a write in the instant between VectorScope's own write and connect's read of the hash.
- **The registry knows its own connect tool.** This supersedes the CW-05 "Known edge of the name rule" bullet. The offer filter in `tools()` runs only while `experimentalConnect` is on, and then offers the built-in tool to build alone and a custom or plugin tool whose id is `connect` to no agent, so it can neither replace the built-in nor write `connect` tool parts the hub would read as runs. With the flag off a custom tool named `connect` is offered as it was before CW-05. registry.ts has 3 lines at that anchor (a comment and a two-line condition), not 1, so 9 added lines in all; the hunk is still at the anchor named in 7.2. Left as it is: a `connect` tool part a custom tool wrote earlier, while the flag was off, is read as a run only if its metadata decodes as a whole run under `ConnectHub.METADATA_KEY`.
- **Memory holds an unknown connect tool as an outside tool.** `taint` counts a `connect` tool part as a connected tool's report only when it carries the built-in tool's metadata (a run under `ConnectHub.METADATA_KEY`, or `action` `review`, `findings`, `status` or `cancel`). Any other part named `connect`, and a built-in part still pending, is held as an outside tool (`mcp`, the stronger hold), so `carried()` passes it up from a subagent again. The memory.ts hunk is one block at the two call sites: a five-line helper with a one-line comment between them, the first condition over parts instead of names, and the second call site's line back as it is on main with the check on the line after it. A custom tool that writes the built-in's metadata shape is still held as `subagent`; both hold memory writes.
- **What the `connect_model` question shows.** The hub puts the model, where the diff goes and the cap in the ask's `metadata.description`, but no client read it: the desktop dock showed only the patterns (the model id) and the TUI only "Call tool connect_model". The desktop now shows it, for `connect`, `connect_model` and `connect_write` asks that carry a connect run id: new app features/connect/consent.ts (`connectConsentDetails`, with its test) and two additive hunks in app pages/session/composer/session-permission-dock.tsx, a file neither 7.1 nor 7.2 lists. One hunk is an import after the `Icon` import, the other a row after the tool-description row, each at least three unchanged lines from the hunks Hands has in that file. No i18n key was added, since app i18n has a parity test across every language; the sentence is Vector's English, as the hub writes it. **The TUI is not done:** tui/src/routes/session/permission.tsx is outside 7.3's safe zone and Hands edits it. The request to its owner is a `connect`/`connect_model` branch that shows `metadata.description` (or it joins CW-11). Until then `VECTOR_EXPERIMENTAL_CONNECT` stays off by default, and CW-25 must not turn it on first.
- **Dead field.** `Checked.resolved` is gone; `Checked` is `ConnectPolicy.ReviewModel`, and the `resolveModel` wrapper keeps comparing model names.
