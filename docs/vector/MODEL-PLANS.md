# Vector Codium

Codium is Vector's managed coding-model plan: four monthly subscriptions, Plus, Pro, Max and Ultra, at $10, $50, $100 and $200 a month (plan ids `vector-10`, `vector-50`, `vector-100`, `vector-200`, which never change). There are no top-ups, no annual prices and no overage charges. A plan gives models from several labs with zero data retention and no provider keys, a private monthly pool of model spend that is never published, and the perks listed for its tier. The workspace stays free.

**Nothing is on sale.** `MODEL_PLANS_ENABLED=false`, Stripe is not connected and `ROUTE_ACCEPTANCES` is empty, so the gateway serves no model route and nothing can be bought. Source changes do not activate sales. The owner's steps, in order, are in [owner-actions/codium-payments.md](owner-actions/codium-payments.md); the guards the owner operates afterwards are in [owner-actions/codium-owner-guards.md](owner-actions/codium-owner-guards.md).

The build contract is [build/codium-build-spec.md](build/codium-build-spec.md). Each work package records what it built in `build/codium-<id>-…-notes.md`, and departures from the contract are in [build/codium-deviations.md](build/codium-deviations.md). This page is the summary.

## What people see

- **Usage is a whole percentage of the month**, the same figure everywhere: Settings → Usage and Settings → Account in the app, `vector codium` (alias `vector credits`) in the terminal, and the account page on vectordev.ai. `used + left = 100`, and meters report the share left as `aria-valuenow`.
- **Codium work shows the label "Codium"** in place of tokens or a price: in sessions, Settings → Usage, the TUI, `vector run --format json`, exports, Vectorscope reviews and GitHub evidence. Session costs and dollar spend limits leave Codium steps out; step and loop limits still apply.
- **No amount leaves the server.** Status, `/models`, the estimate API, errors and every page carry shares, counts and the public caps from `ENTITLEMENTS` only (invariant P1).
- **When the month is used up**, Codium pauses until renewal. Own keys, Vector Local and free models keep working. The person can upgrade and keep what's left of the month.
- The desktop and CLI show the provider as **Vector Codium**; its stable internal id remains `vector-plan`.

Public pages: `/codium` (pricing; `/pricing` redirects there), `/account` (the plan card), and `/docs/codium` (the docs page; `/docs/plans` and `/docs/pricing` redirect there).

## Plans and caps

`packages/schema/src/codium-entitlements.ts` (`CodiumEntitlements`) holds what each plan includes as counts, hours, shares and flags, never dollars. The API, the app, the CLI and the website import it, and every number on a page comes from it.

|                                              | Plus | Pro  | Max  | Ultra |
| -------------------------------------------- | ---- | ---- | ---- | ----- |
| Usage, multiple of Plus                      | 1x   | 5.5x | 12x  | 25x   |
| Codium requests at once                      | 3    | 6    | 12   | 24    |
| Requests a minute                            | 30   | 60   | 120  | 200   |
| Daily limit (share of the month per UTC day) | 25%  | 25%  | 40%  | none  |
| Longest context                              | 256K | 256K | 512K | 768K  |
| First in line when busy, one retry           | no   | no   | yes  | yes   |

The private pool of each plan is `MODEL_PLAN_<price>_CREDITS_USD` (or `MODEL_CREDIT_MARKUP_PERCENT`). Codium stays off unless Pro, Max and Ultra pools are 5.5x, 12x and 25x Plus's within 0.05, because the pages publish those multiples. The perks of each tier (§1.1 of the contract) are in the same module and are shown only when listed (below). `api/_lib/codium-limits.ts` holds the server-only limits: the trust ramp, the pool ramp and the renewal grace.

## The listing rule and `CODIUM_LISTED_PERKS`

A perk appears on `/codium`, the account page, Settings and `/docs/codium` only while `listedPerks()` (`api/_lib/codium-perks.ts`) lists it:

`CODIUM_LISTED_PERKS` (comma list) ∩ the `codium` switch and the perk's service switch on ∩ not in `perks-off` ∩ every perk it requires listed (transitively) ∩ its service ready ∩ for Track B perks `CODIUM_TRACK_B_LIVE=true` ∩ for App perks a configured GitHub App.

- If the store cannot be read, nothing is listed. With `MODEL_PLANS_ENABLED=false`, nothing is listed.
- The readiness table holds real configured checks only. Today it has `priority`, which needs `MODEL_PLAN_GLOBAL_INFLIGHT` and a valid reserve (`MODEL_PLAN_PRIORITY_RESERVE`, default 0.2), `second-opinion` and `review-panel`, which need their judges and review pair served (below), and `alerts`, which needs the VAPID keys and `VECTOR_PHONE_APP_ORIGIN` (below). Each later service work package adds its own check after its gate; an environment listing cannot claim an unfinished service.
- `founding` is resolved at runtime only: its readiness check is the founding window (below), so it leaves every page the moment the window closes.
- `GET /api/model-plans/config` answers `publicCodiumTiers()` with `listed`, accepted models and public caps, cached `s-maxage=60, stale-while-revalidate=30`. Prerendered pages never capture the listing: their scripts read the configuration after loading and remove whatever is no longer listed. The account status carries the same `listed` set.
- Copy lives in `packages/schema/src/codium-copy.ts` (`CodiumCopy`): perk text, the computed taglines (a tagline never names an unlisted perk), `COMING`, the free-workspace list and `tierView()`.
- Vector Velocity is always tagged Coming, with the owner-approved planned-size wording, no date and no part in today's purchase. Vector Labs is not shown; whether it returns as a Coming row is an open owner decision.

## The plan cache

Only reconcile writes an account's plan. Every other service reads its `EntitlementSnapshot` (`api/_lib/codium-entitlements.ts`), which carries the state, the plan, the period, `meterEpoch`, the ramp and the effective caps.

- **Read rules.** A missing snapshot runs one on-demand reconcile, and a `none` answer is cached for 60 seconds. A stale snapshot (over 6 hours old, or past its period end) is served while one reconcile runs, at most one a minute per account. The gateway refuses a snapshot whose `livemode` differs from the server's Stripe mode.
- **No Stripe call on a hot path** (M4). Chat, `/models`, status and entitlement checks read only the store.
- **Store keys** all sit under `vector:codium:<live|test>:` through `codiumKey()` (`api/_lib/codium-keys.ts`), so test and live records never mix. OpenRouter keys created in test mode are named `Vector test …` and capped at `CODIUM_TEST_CREDIT_CAP_USD`.

### States

| Stripe                                              | State / reason               | Codium models                                                                    |
| --------------------------------------------------- | ---------------------------- | -------------------------------------------------------------------------------- |
| no subscription, `incomplete`, `incomplete_expired` | none                         | 402 `MODEL_PLAN_REQUIRED`                                                        |
| current period paid and unreversed                  | active                       | served within the caps                                                           |
| period ended, renewal invoice not yet paid          | renewing                     | the previous key serves until period end + grace, then 503 `MODEL_PLAN_RENEWING` |
| renewing past period end + grace                    | paused / payment_pending     | 402 `MODEL_PLAN_PAYMENT_REQUIRED`                                                |
| `invoice.payment_action_required`                   | paused / action_required     | 402, action `confirm-payment`                                                    |
| `past_due`                                          | paused / payment_failed      | 402, action `update-card`                                                        |
| `unpaid` or `canceled`                              | ended                        | 402 `MODEL_PLAN_REQUIRED`                                                        |
| full refund of the current period's charge          | ended / refunded             | 402                                                                              |
| partial refund                                      | no change                    | unchanged                                                                        |
| open dispute on any Codium charge                   | frozen / disputed            | key disabled at once                                                             |
| early-fraud warning                                 | frozen / early_fraud_warning | key disabled at once                                                             |
| `risk.blocked` or owner freeze                      | frozen / owner               | key disabled at once                                                             |
| account deletion                                    | ended / closing              | key disabled                                                                     |

A won dispute returns to the Stripe-derived state with the same `meterEpoch`; a lost one ends the plan, sets `risk.blocked` and cancels the subscription. Every new period, including the one an upgrade starts, gets a new `meterEpoch`, so per-period meters start fresh.

## Payments

- **Checkout** (`POST /api/model-plans/checkout`) needs a website session or the desktop's sign-in. An account that already has a subscription gets 409 `MODEL_PLAN_EXISTS`. Checkout shows the consent text and asks the bank for 3-D Secure on a first payment of `CODIUM_3DS_MIN_USD` (100) or more. In test mode only `VECTOR_ADMIN_EMAILS` may check out.
- **Webhook** (`/api/model-plans/webhook`): signature over the raw body, exactly the 20 events in `MODEL_PLAN_WEBHOOK_EVENTS`, objects re-fetched at the pinned API version `2025-02-24.acacia`, reconcile within 8 seconds or a durable queue item. Replay every 10 minutes covers any lost event; an hourly risk sweep and a daily sweep at 04:23 UTC recheck disputes, renewals, duplicate subscriptions and key limits.
- **Renewals.** On `invoice.created` the outbox finalizes and charges the renewal within about a minute, only for the governing, unfrozen, not-superseded subscription while `codium` is on and the OpenRouter balance covers what is owed (M7); otherwise it pauses collection or leaves the charge to Stripe's schedule, and emails the owner. On `invoice.paid`: a new key at the full pool, a new `meterEpoch`, the old key off. During `renewing`, the old key serves until `periodEnd + CODIUM_RENEWAL_GRACE_MINUTES` (120, at most 360), so nobody who pays is locked out (M11).
- **Upgrades** (`POST /api/model-plans/change` to a higher plan) are allowed only while the account is active with no open invoice, not past due or frozen, with no scheduled downgrade, while `sales` is on and funding can reserve the sale. The upgrade is a new Checkout Session that starts a new month today, charged in full. When it is paid, the old key goes off, and the carry is `max(0, oldLimit − usage − held)`, once, only from a paid, unreversed period of the same customer. The old subscription is cancelled exactly once, its open invoices voided and drafts deleted. A true-up 12 minutes later can raise the new key to `oldLimit − finalUsage` and never lowers it. Carried usage ends at the next renewal (M6).
- **Downgrades** are a subscription schedule: the current price to the period end, then the lower price. `DELETE /api/model-plans/change` releases it ("Keep my plan"). A schedule is released before the portal's cancel flow opens.
- **Portal** (`POST /api/model-plans/portal`): one no-change configuration for payment methods, invoices and cancellation at period end. The old `flow:"change"` answers 409 `MODEL_PLAN_CHANGE_UNAVAILABLE`, pointing to the account page.
- **Failed payments** pause Codium and plan perks (`update-card` opens the portal's payment-method flow; `confirm-payment` opens the invoice confirmation). They do not extend the month. A plan ends when Stripe's retries give up.
- **Refunds and disputes.** A full refund of the current charge ends the plan. A partial refund changes nothing, so never refund partially to end a plan: use the owner page's "Refund and end". A dispute on any Codium charge freezes the account and voids collection until it closes (M5).
- **Early-fraud warnings** freeze the account. An actionable warning with `CODIUM_EFW_REFUND=true` (the default) refunds the warned charge and the current period's charge if different, and cancels at once. `CODIUM_RADAR_BLOCKLIST_ID` adds the card to a Radar block list.
- **Ramps.** For 7 days after the first paid Max or Ultra invoice (`CODIUM_TRUST_RAMP_DAYS`), hosted limits are reduced. When that first payment was not authenticated with 3-D Secure, the key holds 30% of the pool for 72 hours, released by an outbox job, and Ultra keeps a 40% daily share for that first period. The pages say "New Max and Ultra accounts start with lower limits while trust builds."
- **Emails and the ledger.** A purchase confirmation email restates consent, renewal and cancellation. Each Codium charge writes a private ledger entry, read only with `CODIUM_OWNER_SECRET` at `/api/model-plans/ledger`.

### Founding members

`api/_lib/codium-founding.ts` (WP A31). The window is the earlier of `CODIUM_FOUNDING_LIMIT` (500) paid founders or `CODIUM_FOUNDING_DAYS` (90) after `sales-opened-at`, the first paid month (`MODEL_PLANS_SALES_OPENED_AT` overrides it). Before the first paid month the window has not started, so it is open. An invalid founding setting closes the window and nothing else: it is named on the owner page ("Founding window settings"), never among the problems that turn Codium off.

- **Checkout.** While `founding` is listed, a first checkout reserves a slot (`founding:reserved`, until two days after the checkout closes) and only then marks the session and its subscription with a founding token (`vector_founding`). An expired or replaced checkout gives its slot back (`checkout.session.expired`, read again from Stripe). An account that has, or had, a founding record gets no slot.
- **The number.** The first paid reconcile turns the token into a number with one script (`founding:count`, `founding:member:<account>`), so a replayed or parallel `invoice.paid` assigns one number and counts it once (M13). The snapshot carries `founding: {number, boost}`; status sends `founding: {number}` only, never the boost.
- **What it keeps.** +10% usage on Plus and Pro only (`subscriptionPlanCredits` applies `ENTITLEMENTS[plan].foundingBoost` to a subscription carrying the token). The server copies the token onto upgrade checkouts, so an upgrade keeps the mark and the lock, and the boost only where the new plan has one; a downgrade by schedule keeps the subscription and its token. The lock is "your price won't go up while you stay subscribed": when a price rises, list the old price id and amount in `STRIPE_MODEL_PLAN_LEGACY_PRICES_<price>` (`price_id:cents,…`) and subscriptions on it stay paid at exactly that amount. A plan change pays the new plan's current price.
- **The end.** Founding ends when the subscription carrying it is deleted (`customer.subscription.deleted`) and no other live subscription carries the token. A resumed scheduled cancellation, a failed payment, an unpaid plan and an upgrade's supersede keep it. An ended record is kept, so the account never gets a second number; account deletion erases it (P5).
- **Founders page.** Founders may list themselves, with an optional display name (1–40 letters, digits, spaces, `.`, `'`, `_`, `-`), from the account page (`GET|POST /api/account/founding`). `/founders` shows them by number; `GET /api/founders` answers only with the page's random slug (in the address's fragment, sent as `x-vector-founders`) until 30 founders are listed, then to anyone. `?badge=<number>` serves that founder's SVG badge. Reconcile hides a frozen plan's entry and shows it again after recovery, and account deletion erases the record, whether or not `founding` is still listed; the `founding` provisioner does the same sooner while it is in `CODIUM_LISTED_PERKS`.

### Roadmap vote

`api/_lib/roadmap.ts` and `GET|POST /api/roadmap` (WP A34), shown in the desktop's Settings → Roadmap vote when the status lists the vote for the plan (`entitlements.vote`).

- **Who.** Max and Ultra vote while the plan is active or renewing; Ultra also nominates. The route decides from the snapshot (`requireEntitlement(account, "vote" | "nominate")`), never from the client, and takes only a Vector account token (`vct_`), never a run token.
- **Ballots.** Each UTC quarter's ballot (`roadmap:<yyyy-qn>:ballot`) opens and closes inside that quarter. One ballot per account (`roadmap:<yyyy-qn>:ballots`, a hash keyed by a SHA-256 of the account id), changeable until the close. One nomination per Ultra account a quarter (`roadmap:<yyyy-qn>:nominations`, written with HSETNX), for the owner to consider for the next ballot. `roadmap:quarters` lists every quarter holding any of these.
- **Results.** After the close, as totals, once at least 20 ballots are counted. A ballot counts when it was cast before the close, for a candidate on the ballot, with a plan that included the vote when it was cast (the plan is kept with it). The winner reads "Planned for the next release cycle." with no date; a tie shows no winner until the owner records one of the tied candidates.
- **Owner.** `bun script/roadmap-ballot.ts open <quarter> --candidates <file.json> --closes <date> --mode live|test` publishes a ballot of 2 to 10 candidates whose copy names no date, month, quarter or "soon". `close`, `results`, `decide <quarter> <id>` (ties only) and `nominations` do the rest; none prints who voted or nominated.
- **Deletion.** `eraseAccountBallots(account)` removes the account's ballots and nominations from every quarter; account deletion calls it from A57. Ballots and nominations are otherwise kept until the account is deleted.

### Second opinion and second-lab reviews

WP A35. Both run in Vector itself, on models the gateway checks against the plan like any other request; nothing on the server grants them.

- **Second opinion.** With LLM-as-a-judge on and Settings → General → Second opinion on (`general.secondOpinion`, off by default, shown only when the status lists `second-opinion` for the plan), each prompt carries `secondOpinion: true`. When the judge checks work a Codium model did, it runs on the plan's judge for that model (`CODIUM_JUDGES`, listed per entry as `codium.judge`) when no judge model is configured and the judge comes from another lab (`packages/engine/src/session/second-opinion.ts`). Plus lists no judges.
- **Review pairs.** A Vectorscope review on Codium without a `triageModel` runs the plan's review pair (`CODIUM_REVIEW_PAIRS`, listed per entry as `codium.review`): the first pass on DeepSeek and each finding checked on another lab's model. A pair from one lab warns and runs one pass. `panel: true` in `.vector/review.json` adds a judge from a third lab (`judgeModel`, or the plan's panel judge) that makes the final call (`packages/core/src/review/second-lab.ts`). The summary footer says "Checked by a second lab" or "Checked by three labs", with own keys too, and nothing when a lab cannot be named.
- **Listing.** `second-opinion` is ready once every plan that includes it can reach at least one judge among the served models; `review-panel` once every plan's triage, confirm and panel judge are served and come from three labs. Neither is ready before A60 accepts the staged routes.

### Phone alerts and shared service plumbing

WP A37 builds the server pieces the phone app (A38), Remote (A39–A42), Vault (A44) and the ops and hosted services use. Phone alerts are ready to list once the VAPID keys and `VECTOR_PHONE_APP_ORIGIN` are set (A38); the owner then adds `alerts` to `CODIUM_LISTED_PERKS`.

- **Push.** `api/_lib/web-push.ts` encrypts each message for each phone as RFC 8291 says and signs it with VAPID (RFC 8292). `GET /api/notify/subscribe` answers the VAPID public key; `POST {subscription}` stores a browser's push subscription (a website session, from the site or `VECTOR_PHONE_APP_ORIGIN`; only the browsers' own push services; at most ten per account, a new one replacing the oldest); `DELETE {endpoint}` removes one whatever the plan. `POST /api/notify/send {ciphertext, key?, urgency?}` takes only end-to-end ciphertext (base64url, at most 3,072 characters) from the desktop app's own sign-in, 60 an hour, and relays it to every phone. `sendServerAlert` sends the server's own alerts, a title and a category tag only (P7). Subscribing and sending need a plan that is active or renewing (§4.4), the `push` switch on and the VAPID keys set; a push service's 404 or 410 deletes that subscription. Subscriptions live in `notify:subs:<account>`; `eraseAccountPushSubscriptions` and the `push` provisioner delete them when the account is deleted.
- **Outbound fetches (S8).** `api/_lib/safe-fetch.ts`: https on port 443 only, no host that resolves to a private, loopback, link-local, multicast, reserved or metadata address (any one of its addresses), the connection made to the address that was checked, redirects never followed, 10 s and 64 KiB by default.
- **Internal calls.** `api/_lib/hosted-internal.ts` signs and checks calls between this server and the relay, ops and hosted services: HMAC-SHA256 over the service, method, path, timestamp, nonce and body hash, under a key derived per service; 300 s of skew, each nonce once, 10 s timeout, no redirects.
- **R2.** `api/_lib/r2-presign.ts` presigns R2 URLs for 900 s at most; an upload signs its exact `content-length`.
- **The phone app (A38).** One web app at `https://remote.vectordev.ai/phone/` for every phone surface (Remote, the cloud computer's live view, production cards, alerts), with one service worker whose scope is the whole phone origin. `packages/app` builds it (`bun run build:phone` → `dist-phone`), the website build copies it to `/phone`, and `vercel.json` serves it on the phone origin only: every other path there redirects to `/phone/` except `/api/`, which the app calls on its own origin; `vectordev.ai/phone` redirects to the phone origin. The phone origin alone gets a strict CSP (`default-src 'none'`, scripts, styles and the worker from itself, connections to itself, the account service and, from A42, Remote's relay), `Permissions-Policy: camera=(self)` and `Service-Worker-Allowed: /` on `/phone/sw.js`. The app signs in to the Vector account on its own origin, reads the status, and shows a route only when its perk is listed and the plan includes it; on iPhone and iPad, pairing and alerts happen only in the installed Home Screen app. Each deploy writes `/phone/version.json`, and an open app reloads once onto a newer build. Settings → Notifications (desktop) gains phone alerts: which events a computer sends and quiet hours, shown once the plan includes listed alerts and the desktop can send them (A41).

- **The Remote relay (A39).** `packages/relay` is a Cloudflare Worker, `vector-remote-relay`, with one Durable Object per account, named by an HMAC of the account under the Worker's `ACCOUNT_KEY`, so the relay never stores the account id. A computer or phone connects to `wss://<relay>/v1/connect` offering `vector.v1` and a ticket from the API (A40) in `Sec-WebSocket-Protocol`; the relay answers `vector.v1` only. A ticket is Ed25519, for the relay's audience, at most five minutes long, good for one connection, and carries the device, its role, the plan's paired-computer count and viewer-hours, and the period's meter epoch (`packages/relay/src/ticket.ts`). The relay passes end-to-end ciphertext between the account's phones and computers byte for byte and stores none of it. Its SQLite storage keeps the paired devices (id, role, the name shown in Settings, the public key, when each paired and was last seen) and each period's viewer and awake time. Caps: the plan's computers and five phones, counted in pairing order; frames of at most 64 KiB and 20 a second; a phone that sends no data for 30 minutes is closed; viewer time per period up to the plan's viewer-hours, awake time up to 1.5 times that. Heartbeats are answered by the runtime without waking the object, its alarm runs only while a phone is attached, and a computer that keeps streaming with no phone attached is closed. The API calls the relay with A37's signed requests: `kill` (revoke every connection and ticket issued before a time), `suspend` (paused, frozen or an owner hold), `presence` (behind `isComputerOnline`), `devices`, `revoke-device`, `erase` (account deletion) and `flags` (the kill flag); `job-offer` is reserved and answers 501. The value `1` under the key `kill` in the Worker's `REMOTE_FLAGS` namespace turns the relay off. The wire protocol is `packages/relay/src/protocol.ts`; setting it up is [owner-actions/remote.md](owner-actions/remote.md).

- **The Remote API (A40).** `POST /api/remote/ticket {role, device, name?, key?}` mints one five-minute relay ticket and answers `{ticket, url, protocol, expiresAt}`; the device connects to `url` offering `protocol` and the ticket, and refreshes in-band with a new ticket before `expiresAt`. A computer needs the desktop app's own sign-in (a `vct_` token marked `desktop`; a pasted CLI token gets 403 `DESKTOP_SIGN_IN_REQUIRED`); a phone needs a website session sent from `VECTOR_PHONE_APP_ORIGIN` (otherwise 403 `REMOTE_PHONE_APP_REQUIRED`); run tokens get 401. Both need an account that is not revoked, Remote configured and the `remote` switch on (503 `REMOTE_UNAVAILABLE`), and a plan that is active or renewing within grace and pairs computers, read from the snapshot (402 or 403 otherwise). The paired-computer count, viewer-hours, meter epoch (a hash, so no Stripe id reaches the relay) and period come from the snapshot and §4.2, never from the request; 300 tickets an hour per account. `GET /api/remote/devices` lists the paired devices with the plan's limit and the fair-use state, and `POST /api/remote/devices/:id/revoke` unpairs one for good; both work whatever the plan. `POST /api/remote/kill` is "Disconnect all": every connection closes and earlier tickets are refused. `GET /api/remote/cloud-runs` lists the account's runs of Vector's GitHub agent from Codex's run records, on every paid plan, once the integration commit registers the reader (until then `{runs: [], available: false}`). The `remote` provisioner suspends the account's relay while the plan is paused or frozen, closes connections from earlier tickets on a freeze's `revokedBefore` and when a plan ends, lifts the suspension when it recovers, and erases the account's relay data when the account is deleted. Revoking an account's tokens (account deletion) also closes its relay connections, and the `remote` switch on `/owner/codium` sets the Worker's kill flag. `isComputerOnline(account)` (`api/_lib/remote-relay.ts`) asks the relay's presence. Remote became listable with A42 (below).

- **Desktop Remote (A41).** The desktop's main process keeps one relay connection while Remote is on and a phone is paired or pairing (`packages/desktop/src/main/remote-link.ts`). Pairing shows a QR of `https://remote.vectordev.ai/phone/pair#<offer>`: the computer's device id and static X25519 key and a one-time secret, in the fragment no server receives. The phone answers with its own key and a passkey made for that pairing, sealed under the secret and bound to a transcript HMAC; the desktop checks the passkey itself (`packages/core/src/webauthn/verify.ts`, origin exactly the phone app's) and both screens show a six-digit check code the person compares before anything is stored. Each phone connection is X25519 (ephemeral and static) + HKDF-SHA256 + AES-256-GCM with a key per direction and sequence numbers (`remote-crypto.ts`). What a phone may ask of the engine is an allowlist (`remote-routes.ts`): sessions, messages, status, todos and diffs to read; a new session (title only); a text-only turn; abort; question answers; and permission answers, which are `once` only after a passkey check on the desktop, or `reject`, never `always`. A turn a phone started is never auto-accepted: the app asks the desktop before its auto-accept answers (`permission-auto-respond.ts`). Engine events stream only while a phone watches, at most four batches a second per phone, and keep-awake then holds the computer awake for busy sessions, including those waiting on a person. "Disconnect all phones" (the tray now, Settings → Remote with A42) makes a new identity, closes every relay connection of the account and frees the old device. Phone alerts are sealed under the computer's alert key, which only paired phones hold, and go through `POST /api/notify/send`; the app sends them only for the events and outside the quiet hours chosen in Settings → Notifications, and only while `alerts` is listed for the plan. Keys and paired phones are sealed with the OS credential store. Vector Local blocks both connections (`remote`, `phone-alerts`) unless the person allows them.

- **Remote on the phone and Settings → Remote (A42).** Settings → Remote (desktop) turns Remote on, pairs a phone with a QR code of the pairing link and the six-digit check (`settings-v2/remote.tsx`; the QR encoder is `packages/app/src/utils/qr`), lists the paired phones and has "Disconnect all phones"; it shows "N of limit computers paired" from the status's `meters.remote {computers, limit}`, which the status route reads from the relay's device list while `remote` is listed (`api/_lib/remote-meter.ts`). The phone app (`packages/app/src/phone/remote/`, routes `pair`, `sessions`, `approvals`, `devices`) runs the same encryption as the desktop (`packages/core/src/remote/crypto.ts`, moved from the desktop) with a static key it cannot export (a non-extractable WebCrypto key in IndexedDB), scans the QR code inside the installed app (the browser's BarcodeDetector where it has one, Vector's decoder elsewhere), makes one passkey per computer, and connects only to `wss://relay.vectordev.ai`, the one socket host the phone origin's CSP names. Sessions are read and steered with text turns; Approvals allow once with the passkey, which the computer verifies, or deny; Devices lists, revokes and disconnects from the API. The phone sends data only on its person's actions: live changes arrive as events and are applied without asking again, so the relay's 30-minute idle close still applies. `remote` is ready to list once tickets can be minted and `VECTOR_PHONE_APP_ORIGIN` is set; the owner lists it after the outside security review.

- **The ops Worker (A46).** `packages/ops-worker` is a Cloudflare Worker, `vector-ops`, with one Durable Object per account (named by an HMAC of the account under the Worker's `ACCOUNT_KEY`) that runs On Call checks and Release Guard watches from a single alarm. The API sends it, with A37's signed requests under the `ops` key: `plan` (the plan's ops caps from the snapshot and `validUntil`, periodEnd + 24 h, after which nothing runs by itself), `config` (the verified domains and the On Call URLs), `release` (a production deployment that reported success), `state`, `suspend` (the ops guard or the owner), `erase` (account deletion) and `flags` (the kill flag). A check is a GET with an 8 s timeout, at most 6 in flight per account, `https` on 443 to a verified host only (matched exactly, every address looked up over DNS-over-HTTPS and public), never following a redirect: a same-origin 3xx counts as up and a cross-domain one fails. 401, 403, 429 and bot challenges are inconclusive; two failures in a row make a URL down. Max checks every 5 minutes and Ultra every minute. A release watch starts 60 s after the deployment's success, compares with the last good release every 30 s for the plan's watch length (a path that passed then and fails twice in a row now is a regression), ends when a newer deployment arrives, and is deduped by (repository, environment, sha) before the plan's releases a day are counted. The alarm is always at least 25 s ahead, and work due within those 25 s shares the wake; wakes are capped per hour. Storage keeps state changes and hourly totals only. The Worker reports `monitor.down`, `monitor.up`, `release.regressed` and `release.passed` to `POST /api/ops/worker` (A48), signed the same way and retried with the same event ids until a 2xx. The value `1` under `kill` in its `OPS_FLAGS` namespace stops every check, watch and report. The interface is `packages/ops-worker/src/protocol.ts`; setting it up is [owner-actions/hosted-ops.md](owner-actions/hosted-ops.md).

- **The GitHub webhook router and ops settings (A47).** Every delivery from the GitHub App goes to `POST /api/github/webhook` (`api/_lib/github-webhook.ts`): the `x-hub-signature-256` HMAC over the raw body under `VECTOR_GITHUB_APP_WEBHOOK_SECRET` (constant-time, S4), then the event filter (a `ping`, or an event no handler named, is answered 200 before any store read), then the dedupe by `x-github-delivery` (pending for 60 s, done for 7 days; a failed delivery is freed so a redelivery runs again), then each handler that named the event, at once, with 8 s each. A handler is `{id, events, handle({name, action?, deliveryId, payload})}` (Codex's spec 2.14); the route's list in `api/github/webhook.ts` holds Codium's `ops` handler, and the integration commit (A59) adds Codex's. The ops handler (`api/_lib/github-webhook-handlers/ops.ts`) sends a `deployment_status` that succeeded, in the environment a bound repository's ops settings name (without case; never a transient one), to the ops Worker's `release` when Release Guard is on, the plan allows it now (Max or Ultra, active or renewing within grace), the ops services are configured and the `ops` switch is on; the URLs are the production URL joined with each path, on verified domains. A `pull_request` opened by the App's bot (`<VECTOR_GITHUB_APP_SLUG>[bot]`) from a branch of the same repository goes to the Ship Desk intake A49 registers. An uninstall, a repository removed from the App, deleted or transferred drops that repository's settings from every account that has them. A repository's owner is its binding (Codex's `bindingFor`, registered at A59 with `registerRepoBindingReader`); until then no repository can be set up. The settings routes, for an account token or a website session (run tokens get 401): `/api/ops/domains` (a domain is verified by a TXT record `_vector-verify.<domain>` = `vector-verify=<token>`, read over DNS-over-HTTPS, or the same line in `https://<domain>/.well-known/vector-verify.txt`, fetched under S8 with no redirect; checked again weekly by the daily job, and verified for at most 14 days without a successful check), `/api/ops/monitors` (On Call URLs on verified domains, within the plan's URL count) and `/api/ops/repos` (Release Guard and Ship Desk per bound repository; answers the `.vector/ops.json` to commit, with the account's `opsId`). Adding needs the ops services, the `ops` switch and a plan with ops caps; reading and removing work whatever the plan. After every change the Worker gets the verified domains and monitors (`config`); a change it missed is sent by the next write or the daily job. The owner's `ops` switch also sets the Worker's kill flag.

- **Release Guard and incidents (A48).** The deployment intake (`api/_lib/release-guard.ts`) takes a release the webhook handler passed (bound repository, Release Guard on, usable plan, verified URLs), dedupes it by repository, environment and sha, reads the repository's `.vector/ops.json` at the deployed commit with a read-only one-repository App token (`api/_lib/github-app-server.ts`; revoked after use and audited under `ops:audit:<account>`), and counts the plan's releases a day only after the dedupe, before the Worker watches it. The Worker's reports reach `POST /api/ops/worker` (A37's signature under the `ops` key; each event taken once by its id). `monitor.down` and `monitor.up` open and resolve On Call incidents and alert the phone (titles only; through a payment retry too). `release.regressed` opens an incident and exactly one revert pull request per repository, environment and sha: GitHub's GraphQL `revertPullRequest` when the range from the last good release is one merged pull request, otherwise a restore commit of the good release's files on `vector/revert-<sha>` with a pull request, only while the target branch's head is the deployed sha. Nothing is written when a workflow file is in the range, the branch moved, `.vector/ops.json` on the target branch (read again before every write) no longer opts in, or the App is missing; Undo then offers "open in GitHub" and the host's rollback link. The server never merges (S9). `/api/ops/incidents` lists incidents with the commits a revert undoes, migration-path warnings and Undo, snoozes one (1 to 24 hours: no alerts and no automatic revert for that URL or repository and environment) and starts "Fix it" (Codex's `startCloudRun`, registered at A59 with `registerOpsRunStarter`, only on the person's tap, within the plan's fix runs a day). `/api/ops/releases` lists the releases taken. The `ops` provisioner pushes the Worker the snapshot's plan (`opsPlanFor`) and erases everything ops on account deletion.

The removed route `/api/model-plans/topup` answers every request with JSON 410 `MODEL_TOPUP_REMOVED`, so an older Vector shows a message instead of a bare 404. Status still sends `purchased: {bought: false}` because the 1.99.111 and 1.99.112 decoders require it (H7).

### Brain Vault

WP A43 builds the vault's core and `vector vault`; WP A44 builds the Vault API; the desktop's backup and Settings → Memory → Backup are A45. `vault` is listed only after the legal read; until it is listed, only the free GitHub backend works.

- **Encryption (P3).** A random vault key stays on the computer (`<data>/vault/vault.json` for the CLI, `safeStorage` on the desktop) and gives, by HKDF, the chunk, manifest, object-id and chunker keys (`packages/core/src/vault/crypto.ts`). Each file is cut into content-defined chunks before compression (`chunker.ts`, 16/64/256 KiB, cut points keyed by the vault), each chunk is brotli-compressed and sealed with AES-256-GCM, with the header, the vault id and the chunk's id as associated data, and named by an HMAC of its plaintext, so a chunk an earlier version holds is never sent again (`format.ts`). A version's manifest lists its files, their chunks and `minReader`; a reader below `minReader` says "update Vector" before it opens anything. Formats are in `@vectordevai/schema/vault`.
- **Recovery code.** 26 base32 symbols and a checksum, shown once; scrypt (N = 2^17) of it wraps the vault key, and the store keeps only the wrapped key (`recovery.ts`). A typo is caught by the checksum; another code opens nothing. Once the code is lost, only a computer that still holds the vault key can restore; Vector cannot.
- **Restore.** Through the brain's own writes (`BrainExport.restore`, trusted only for a vault backup), never a copy of brain.db: what was in use comes back in use, what waited for review waits again, pins stay, in batches of 500 entries or 2 MB; an entry already in memory is left alone.
- **`vector vault backup|status|restore|versions|forget`.** `--github owner/repo` backs up to a private repository the person owns, over their own git, free on every plan (`github.ts`): the repository is checked private before every push, holds only the vault, and keeps the newest 7 versions. Without `--github`, the CLI uses Brain Vault on Vector when the status lists `vault` for the plan (`remote.ts`). Vector Local blocks the `brain-vault` source.
- **The desktop (A45).** Settings → Memory → Backup, on the desktop only. The person chooses a private GitHub repository they own (free on every plan, `packages/desktop/src/main/vault-github.ts`: the desktop's own git with the person's git credentials, the privacy check before every push, 7 versions, a warning once the vault takes more than 1 GB of the repository) or, while the status lists `vault` with storage, Brain Vault on Vector. Back up now creates the vault on first use and shows its recovery code once; the nightly backup (`vault-backup.ts`) runs once a day in the small hours while the app is open, or after a day and a half without one, and never creates a vault. The vault key is sealed with the key the OS credential store holds (`vault-secrets.ts`, safeStorage); without a secure store the desktop makes no vault. Memory is read from the app's engine (`GET /memory/backup`) and restored through it (`POST /memory/restore`, `BrainExport.restore` trusted for a vault), both owner-only routes. A version restores with this computer's key, or with the recovery code on another computer, which then backs up to that vault. The desktop's vault key is its own: the CLI keeps its key in its own file, so using one vault from both means restoring it in the CLI with the recovery code. Vector Local blocks the `brain-vault` source and decides git's pushes as `git-remote` before git starts.
- **The Vault API (A44).** `/api/vault/{setup, uploads, commit, snapshots, snapshots/:id}` and `DELETE /api/vault`, in the shapes of `@vectordevai/schema/vault`, with only a Vector account token (`vct_`), never a run token. Records live in Supabase (`docs/vector/owner-actions/sql/brain-vault.sql`, one invoker function called with the service role) and the encrypted objects in the R2 bucket `vector-vault` at `<mode>/<account>/<vault>/{objects,versions}/<id>`, where `<account>` is an HMAC of the account id under `VECTOR_VAULT_ACCOUNT_SALT`; neither names a Vector account. The quota is a server gate: an uploads request reserves the bytes of every object the store does not hold yet in one transaction that locks the vault, refuses the whole request with 402 `VAULT_QUOTA` when it does not fit, and only then signs a PUT for each missing object that carries its exact size and lives 900 seconds. A commit HEADs each object not yet confirmed and the manifest; a missing or resized one is deleted and answered 409 `VAULT_SIZE_MISMATCH`. Writes need `vault` listed and a plan that includes it, active or renewing within the grace; paused, ended and frozen answer 409 `VAULT_READ_ONLY` and still restore. Reading, forgetting a version and deleting the vault need only the sign-in. The quota is the plan's `vault.gb` in decimal gigabytes; besides it a vault holds at most 60 versions and 2 million objects, and four backups may run at once. The `vault` provisioner keeps §4.4: frozen holds the vault (nothing deleted), an ended plan's vault is read-only for 30 days from an emailed notice and then deleted, and account deletion erases it at once, the wrapped key first. The daily cleanup (`/api/vault/cleanup`, 03:40 UTC) deletes lapsed vaults, sweeps uploads that never committed an hour after their last request, prunes versions older than the plan's version days (the newest is always kept), and deletes from storage the objects no version names. Status shows `meters.vault {usedBytes, quotaBytes}` while `vault` is listed. `vault` is ready to list with `VECTOR_VAULT_ENABLED=true`, the store, the bucket and the notice email; owner steps are in `docs/vector/owner-actions/brain-vault.md`.

## Using Codium in Vector

- **Tokens.** Chat accepts the desktop's sign-in token, a `cli` token minted by the new CLI's code exchange, and run tokens (`vrt_` for GitHub runs, `vht_` for hosted runs). A token pasted from `vectordev.ai/auth/cli` gets 401 `CODIUM_SIGN_IN_REQUIRED` at chat and still works for free models and status (`MODEL_PLAN_REQUIRE_MARKED_TOKENS`, default true). Run tokens are refused everywhere except chat, `/models` and their own service.
- **Old clients.** Below `MODEL_PLANS_MIN_CLIENT` (unset: the compiled-in 1.99.113), `/models` answers `enabled:false` and chat answers 426 `CODIUM_UPDATE_REQUIRED`.
- **The catalog Vector sees** (`GET /api/model-plans/models`) reads only the snapshot and the runtime model switches. New clients get every served model with its lab, weight, role and, for a model above the plan, `locked: {plan, name}`, plus the synthetic **Codium Auto** entry after the default model. Old clients get only the unlocked models in the four-field shape. Choosing a locked model offers Change plan.
- **Choosing Codium.** Vector never moves a person to Codium by itself: not for a new session, a Vectorscope review, a swarm, an editor connected to Vector, or a run where Codium is the only provider. Inside Codium, once the person chose it, Vector may pick another model of their tier: titles and helpers use the plan's smaller models, Codium Auto picks a model for each message by its size, and a swarm may route tasks to the plan's other models. Long-context entries and fast lanes are manual only and are never picked automatically.
- **Admission** (`api/_lib/model-plan-admit.ts`) is one Lua script and one store round trip: the account's requests at once, the global set whose last share (`MODEL_PLAN_PRIORITY_RESERVE`) is kept for Max and Ultra, the month's available pool, the daily share, the Brain helpers' share and a run's ceiling, then one hold per request with one deadline. The per-minute limit is checked before. Each request holds a fixed reservation per model until it settles; an answer the provider never priced, or a refusal after the request was dispatched, is charged at that full reservation, because it may still be billed.
- **What the gateway forwards.** Text and tools through the gateway, with token usage but without the provider's charge, its name or fingerprint. Clients stamp each Codium step as Codium and store no tokens or cost for it.

## Status and estimates

`GET /api/model-plans/status` (account or desktop token, cached 30 seconds, cleared by reconcile) answers shares rounded to 0.01, public counts and timestamps only: the plan, `left`, the state and reason, the action, a scheduled downgrade, today's share when the tier has a daily limit, `listed`, public entitlements, meters, `empty` (below the cheapest unlocked request) and `low` (under 10% left). A paused plan answers `{active: true, access: false, …}`. Clients decode new fields one at a time, so an unknown value never fails the whole status.

`POST /api/model-plans/estimate` answers bands ("under 1%" to "more than your month"), with inputs clamped and rounded to steps 1.5x apart, so it cannot reveal the pool (P2).

## Switches

Runtime switches live in the store (`api/_lib/codium-switches.ts`), take effect within 30 seconds, need no redeploy and are written to an audit log. The owner page sets them.

- `sales`: off pauses checkout and upgrades. Renewals and already-paid upgrades continue (M12).
- `codium`: off makes the gateway refuse Codium. After `CODIUM_CODIUM_OFF_PAUSE_MINUTES` (60) off, active subscriptions get `pause_collection=void`, lifted when the switch returns.
- `cloudAgents`, `hosted` (`on`, `no-new`, `stop`), `ops`, `remote`, `vault`, `push`: one per service.
- `perks-off` and `models-off` take a single perk or model off the pages and the gateway.

Never set `MODEL_PLANS_ENABLED` back to false while anyone is subscribed: it stops the service for paying people. Use `sales` and `codium` instead. Funding, alerts and the owner page are described in [owner-actions/codium-owner-guards.md](owner-actions/codium-owner-guards.md).

`bun scripts/setup-model-plans.ts` from `packages/web` is a dry run by default and makes no network call. With `--apply` and the owner's full `sk_` setup key (never the deployed `rk_` runtime key) it creates or reuses the four monthly products and prices (lookup keys `vector-models-{10,50,100,200}-monthly-v1`, `tax_behavior=exclusive`, statement descriptor `VECTORDEV CODIUM`), the single no-change portal, and the webhook subscribed to exactly the 20 events; it archives the legacy top-up prices and deactivates an old plan-change portal. `bun scripts/codium-economics.ts` prints private planning figures for the owner's terminal only.

Crons (`CRON_SECRET`): outbox every minute, replay and funding every 10 minutes, the risk sweep hourly, the full sweep daily at 04:23 UTC, the Brain Vault cleanup daily at 03:40 UTC (A44), and the ops domain job daily at 04:10 UTC (A47: weekly re-verification and Worker updates that failed). The other hosted and ops schedules are added by the work packages that build their routes.
