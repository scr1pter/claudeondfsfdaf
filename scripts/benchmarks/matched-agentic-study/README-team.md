# Matched native-team runner: review before any funded execution

`paired_runner.py` is a separate native-team instrument. Import and default CLI
execution do not read controller credentials or receipts, contact a gateway,
start a browser or coding runtime, or call a model. It reuses the explicitly
selected public `agentic-study/runner.py` composition helpers and its unchanged
functional evaluator checks. The single-agent runner and its controls are not
modified. This branch is an instrument for review, not authorization to fund it.

The fixed development replication set is WorkflowRunner, EvidenceWorkbench,
DeliveryOutbox, in that order. Both arms use the same frozen seed and TASK.md.
Runtime orders are Vector/Codex, Codex/Vector, Codex/Vector. All three tasks had
already been qualified; this is not a new held-out study. A budget stop leaves
the fixed set incomplete/not met. Report every failed, stopped and not-run arm;
do not pool a favorable selected subset or claim a speed/cost win from it.

The product source proposed by the coordinating review is the separate clean
`vector-tokenomics-scale` worktree at
`479303cf229badc0fa2c770f27d7d845dfa4fa68`. The runner does not edit that tree.
An execution must explicitly provide the reviewed source hash again. Product
readiness evidence and remaining baseline TaskTool variance are separate from
the paired-runner controls; this document does not claim every product test is
green.

## Frozen team profile

Each arm has one lead and exactly three lifetime native child slots:
`backend_worker`, `frontend_worker`, `team_judge`. Follow-ups can reuse those
identities. Replacements, extra roles, depth-two agents, cross-arm ancestry,
unrecognized helpers, and model/profile drift fail closed. Native autonomous
identity counts are separate from request counts and helper-purpose counts.
The native registry checks real SQLite ancestry before forwarding inference.
The fresh runtime home must contain exactly one persisted root matching the
first request. That root is validated and durably audited before forwarding;
the runner never infers ownership from a root CLI footer.

Every inference uses Sol `gpt-6.1-sol`, High effort, summary `auto`, verbosity
`low`, 1,050,000 context and 32,000 output ceiling. Workers, judge, same-session
repairs, retries and helpers all consume the same metered scope. Unobserved
helper producers remain unavailable; no helper label exempts a native identity
from admission. The role instructions come from one `PROFILE` object and are
rendered into both native configurations with the same meaning. The team lead
delegates nonoverlapping backend/frontend file ownership, waits for both, runs
the fixed judge, corrects material issues, and personally verifies final UI/API.

The common browser client, capabilities, origin and runtime binaries are frozen
and identical for both arms. Coding runtimes get the common client endpoint and
its local browser token; browser libraries and raw browser connection details
are not provided to them. This is an owned runtime/profile policy and bounded
posthoc audit, not an operating-system sandbox. Do not claim protection against
arbitrary malicious local code. Images, verification and quality are preserved.

## Funding and closure

The existing $48 study total and cumulative $20 `foundry-vector`/$20
`foundry-codex` caps remain unchanged. The historical minimum is 889 requests /
$20.3038291. All earlier charges stay in the original ledger and actors. There
is no reset, reclassification, cap expansion, new actor, force-unseal or blanket
disarm operation. Each arm has a $3 soft stop, 300 provider requests, two-hour
execution bound and at most one formal repair in the same lead session.

Before each arm, read settled global and actor reservation headroom. The
preregistered conservative admission requires $5.73: the unchanged meter's
full-image 1.05M input + 32K output reservation. If either headroom is smaller,
the arm is **not run**, before setup or scoped funding admission. This does not
guarantee completion; the witness checks the actual conservative reservation
again before every request. Never remove vision or reduce quality to fit.

Only `OwnedSupervisor` receives the actual scoped meter token. The CLI sees a
separate random witness alias, which cannot authenticate to the real meter or
control it. Controller credentials and the funded token are never written into
CLI configuration. The durable witness audit is fsynced before forwarding;
audit failure latches and stops the arm. Scoped closure disarms only the owned
token, drains accepted handlers and requests, and reconciles the complete
receipt multiset by batch hash, sequence and normalized request hash. Native
root/worker/judge/helper charges are all retained, including failed requests.
Known controller totals are preserved if receipt joining or closure is unknown;
do not add those totals to reconciled usage a second time.

A failed terminal, contradictory terminal, unknown closure, native protocol
error, failed execution, audit failure or quality ambiguity blocks the next arm.
A recognized known-usage `max_output_tokens` incomplete response may continue
within the current arm under the unchanged limits; it requires manual review
at closure even after a later completion. The runtime monitor watches the
fatal `arm.failure` latch, not that nonfatal observation. There is no automatic
retry of uncertain mutation or automatic next task.

## Plans and private execution inputs

Required explicit paths are `--vector-root`, `--common-runner-root`,
`--task-root`, `--browser-driver-root`, `--bun`, `--node`, `--codex-bin`,
`--chrome`, `--playwright-module` and a new `--out` directory outside all input
trees. `--task-root` contains the three task directories named above. Runtime
tool paths are supplied by the coordinating review; do not discover user
credentials or running apps. A plan freezes source cleanliness/revision, all
three task manifests, shared role semantics, both instrument directories,
browser-driver files, exact runtime paths, executable hashes, the Playwright
package hash, study limits and order. It can be written using `--write-plan`.
No credential/config or receipt file is read while planning.

Task command contracts must invoke an explicit frozen Python/Bun/Node tool and
a directly named script inside the task manifest. External code/file operands
are accepted only for the designated frozen common-browser dependencies.
Unbound absolute/relative helpers, interpreter `-m`/`-c` or inline JavaScript,
module loaders and compound flag/file escapes are rejected before an arm can
open. Runtime app/out placeholders are data operands, not evaluator code.
This binds the three qualified public commands without claiming a universal
analysis of arbitrary imports or hashing the trusted host standard library.

An eventual, separately reviewed invocation adds `--run --reviewed-plan FILE
--expected-plan-sha SHA256 --expected-source COMMIT`, plus explicit private
`--controller-config FILE --receipt-jsonl FILE`. The plan file contains the
plan object printed under `plan`, not the surrounding display wrapper. SHA256
means the canonical JSON digest printed as `planSha256`. All freezes are
rechecked before admission and every invocation. Only after those checks does
the runner read the existing controller's `localToken`. It never loads a real
provider key. The receipt reader is read-only and only used after explicit run.

One invocation executes at most one fixed task pair. Index 2 requires the
frozen successful-closure summary of index 1 through `--previous-summary`;
index 3 requires both summaries in order. Source, task, profile, binary and
instrument freezes must be identical across the fixed set. A predecessor with
manual review, unknown settlement or an unrun arm cannot open the next pair.
Functional product failures stay recorded even when closure permits completing
the other arm. Nothing schedules or automatically launches another pair.

Every output is private: runtime homes, native IDs, rollouts, SQLite extracts,
normalized tool commands, support data, browser images, source snapshots,
receipts/accounting metadata, controller/config paths and local capabilities.
Never commit them. Public reports should contain only counts, enum/flag
metadata, hashes, relationships and reviewed aggregate costs. The runner
prints no raw prompt or credential on errors.

## Native telemetry and quality gates

The runner positively queries its owned Windows Job Object for zero active
processes before descendant collection. It reuses the existing owned-process
primitives; there is no PID/name-wide cleanup. Root CLI stdout is not accepted
as descendant coverage. The registry exports every owned descendant, including
refused attempted sessions, from native SQLite/rollout state and hashes it.
The audit normalizes terminal calls from all those native transcripts and runs
the unchanged common browser audit for each. Unknown or unfinished commands,
unrecognized schemas, absent execution telemetry and policy ambiguities remain
manual review, even when the independent functional evaluator passes.

The quality gate retains each native turn's chronology and outcome. The first
successful completion from each worker must precede the original judge
creation. Later completions from those same worker identities require a
subsequent review turn from that same judge identity; final lead browser/API
commands must follow the latest successful judge completion. This allows a
formal same-lead repair with worker and judge follow-ups without creating any
additional autonomous identities. Ordering uses nondecreasing native timestamps
normalized to seconds, reports equal timestamps, and is not strict causal
proof. A later fatal, cancelled, pending or unknown native phase cannot be
hidden by an earlier completion. A recoverable historical native error followed
by a valid completion can clear that phase while its error observation, raw
transcript and all charges remain retained. An ordinary failed verification
command is not itself a native session fatal outcome.

The gate separately checks post-judge lead browser/API command evidence. Static command
recognition is deliberately bounded. A legitimate verification hidden inside
an unrecognized helper script needs review rather than a false pass. Explicit
owned DATA_DIR support data and scripts are retained and counted; an executed
support script outside authored source keeps the common audit's conservative
manual-review disposition. No blanket trust of a DATA_DIR path is inferred.

The independent functional verifier is the existing frozen task evaluator,
with every original API/browser group, expected check count, exit-code rule and
protected-source check. Its one-agent repair prelude alone is replaced with the
fixed native-team continuation prelude; failed-check observations are unchanged.
No fake provider completion or unchanged real task seed establishes a product
pass. Efficiency/success conclusions require review of the whole fixed set.

## Free controls already safe to run

From this directory:

```powershell
python -m unittest test_paired_runner -v
```

These controls use only temporary Python objects/files and synthetic SQLite.
They start no HTTP server, coding runtime, browser or application and read no
controller config, private real runtime, receipt ledger or provider key. They
exercise the actual Supervisor/arm admission/settlement code through injected
callbacks. Synthetic evaluator outcomes are labeled fixtures, never benchmark
results. Existing witness suites that start loopback servers need their own
reviewed free-control authorization; the command above does not run them.
