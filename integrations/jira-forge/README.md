# Vector for Jira — source template and owner gates

This is a manifest-only Forge remote connector. There is no Forge code, package manifest or dependency install. The all-zero app id in `manifest.yml` is deliberately unregistered. The owner must register the real Forge app, replace that id and configure its matching full application ARI in `VECTOR_JIRA_FORGE_APP_ID`. This build registers or deploys nothing and grants no platform permissions.

The connector uses A2A 1.0 JSON-RPC, with non-streaming `SendMessage`, `GetTask` and `CancelTask` at `https://vectordev.ai/api/jira/a2a`. The manifest references an endpoint key, which resolves to the fixed remote and `/a2a` route. Its separate `preUninstall` endpoint uses `/uninstall`. The declared icon is a local static asset. Native task/context ids are opaque server-generated UUIDs, scoped to the signed requester and installation. A terminal task stays terminal; a later task gets a new id.

## Identity and least privilege

Every native call verifies an RS256 Forge Invocation Token against the pinned commercial Atlassian JWKS. Audience and `app.id` must both match the configured app. Cloud id, installation ARI, API base, endpoint key and expiry are validated; each `jti` is consumed until expiry. A token cannot be replayed against another body. No key URL or context URL from a payload is fetched. Isolated Cloud claims are unsupported and hold rather than selecting a dynamic host.

Paid work, links, polling and cancellation require the token's signed `principal`. An initial body's `userAccountId` must equal it. The current Forge Remote documentation labels `principal` as available to UI modules; its availability for these remote agent calls is therefore a real native qualification gate. The server never infers identity from a body, reporter, display name, Rovo text or user-token payload. Pre-uninstall intentionally permits no requester, while requiring its own signed endpoint/cloud/installation proof.

The exact scopes are `read:jira-work`, `read:jira-user`, `read:app-user-token`, and `read:app-system-token`. The additional `read:jira-user` differs from the original three-scope spec: the documented `/rest/api/3/myself` read requires it to prove that the app-user token belongs to the signed person. The coordinator approved this minimum read scope for the source template. No write, administration or email scope is requested. Actual new app consent is an owner go-live action.

Native user proof requires exact account id, active account, `accountType: atlassian` and explicit `guest: false`; missing flags hold. Context is fetched only through the invoking user's `x-forge-oauth-user` token against the verified cloud's fixed Jira API gateway. Tokens stay within that invocation, are never stored or included in a job, and never reach a model. The requested system token is ignored for context reads. A site connect code is issued only after the same person's native identity and `ADMINISTER` permission check; the existing account authority redeems it once while signed in.

## Tasks and data

`AUTOMATION` cannot spend runs. Initial Rovo coding chat is refused; private `link <code>` uses the existing one-time account link flow. A plain assignment uses the fixed task line. An own, unedited native comment can supply a task only after author and exact body proof. Workflow/manual text may contain mutable space instructions and relevant context, so it asks for the person's explicit prompt in the existing conversation. Summaries, descriptions, reporters, other comments and wrapper text stay untrusted context. ADF extraction keeps bounded text and line breaks and never follows links or media.

Repository questions contain exact opaque options from the project's current mapping. A reply must belong to the same verified person/context and current authorization, and must still match a stored offered value and immutable repository id. Names and model guesses are not selection authority. An original prompt awaiting input is encrypted under a separate key with a hard expiry of at most fifty minutes, within the two-hour contract; it is not embedded in two-day task metadata. Metadata contains bounded ids, fixed states and sealed rendered output. Installation/account indexes are bounded, expire within the two-day retention window and let static erasure code find tasks without scanning. Task/draft writes atomically fence the exact installation, link and task records so stale writers cannot restore erased data.

The server responds within its fifty-second bound, below Jira's fifty-five-second budget, then processes admitted requests after the response. The laptop queue remains capped at ten minutes, a run at thirty-five minutes and the whole task at fifty minutes. The fifty-minute fallback distinguishes a still-running computer from waiting work and never claims the computer stopped. No paid inference or remote workspace is added by this connector.

Native artifacts use the shared-place output policy: fixed outcome and allowed link only. Private summaries require the injected idempotent `privateResult({account, jid, text})` account/job surface. A missing surface holds the encrypted terminal outbox instead of publishing or dropping private text. New exact-P2-head hosted Redis tests must qualify the task/draft and resource admission transactions; local fake results and older P1c CI cannot substitute for that proof.

The manifest truthfully declares remote `compute` and `storage`, with `inScopeEUD: true`, because bounded platform text is encrypted temporarily on Vector's backend. This is not a data-residency, compliance or Runs on Atlassian claim. Owner privacy/security review and actual deployment qualification remain required.

## Owner qualification

Read the current direct-distribution and remote-agent requirements before registration. Current public guides describe direct installation without an early-access notice, but this build does not qualify Free/Standard/Premium/Enterprise, HIPAA or FedRAMP availability. Verify native signed-principal presence, explicit guest membership flags, token scopes, callback payloads, polling/stop/deadline behavior, source-only manifest validation, uninstall delivery and the private account surface on a dedicated site. Also qualify the prerequisite laptop worktree, runner, relay, signing keys and model constraints. Do not deploy this template with the placeholder app id.

Marketplace registration, partner verification, listing assets, security contact, legal approval and actual app consent are owner actions. Current cloud security-bugfix deadlines are ten days for critical, four weeks for high, twelve for medium and twenty-five for low severity; the owner must maintain an operational response process. TLS/HSTS and actual production retention were not measured by this source build.
