# Vector for Linear — owner activation gates

The VE-12 sources implement the dormant native adapter. This directory registers no app and contains no SDK dependency. Local loopback fixtures are software evidence; they do not qualify a live Linear workspace.

The owner must supply the existing `VECTOR_LINEAR_CLIENT_ID`, `VECTOR_LINEAR_CLIENT_SECRET` and `VECTOR_LINEAR_WEBHOOK_SECRET` configuration and explicitly enable `linear` after the independent phase review and hosted checks. No credentials belong in this repository. The native callback is `https://vectordev.ai/api/linear/oauth`; webhook delivery is `https://vectordev.ai/api/linear/webhook`. A callback GET redirects to the fixed same-origin account page fragment. Only its authenticated POST with the original single-use state may finish the install or person link.

The OAuth app uses `actor=app` and exactly `read`, `write`, `app:assignable`, `app:mentionable`. Person linking uses `actor=user`, scope `read`; its credentials are discarded after the native viewer and organization are proved. App credentials are a sealed rotating access/refresh pair. Refresh preserves the installation authorization revision; reinstall/reconnect changes it. Old queued jobs hold after a changed authorization.

Current public documentation requires an integration-directory submission to distribute an agent to other workspaces. The older spec's unlisted authorize-link release assumption is unqualified. Directory assets, privacy/support text, native app registration, reviewer access and distribution approval are owner work in the later surfaces/go-live phase.

A delegation alone may identify a responsible human selected by automation. It receives a native request for that person's own prompt and admits no paid job. Immutable creator-authored prompt activities establish task text. Other authors cannot cancel or select a repository for that sponsor. Titles, descriptions, comments, guidance and prompt context remain untrusted data. The adapter never calls Linear's inference-backed repository suggestions. Opaque native selection values prove the current mapped team, immutable repository identity and our own preceding elicitation; missing bounded history holds instead of guessing.

Native requests require current authorization before each effect. Activity delivery uses a stable supplied UUID and reconciles that exact object after an uncertain response. A stop prevents subsequent issue/plan actions and permits only its final response. Rate limits and Retry-After persist between invocations. Signed revocation and team-access controls carry no native authorization generation. A canonical signed semantic receipt, excluding the unsigned delivery header and send timestamp, pins the current generation and prevents replay against a reconnect. Access-token 401s remain renewable and never prove terminal grant revocation. The current public documentation does not define a sufficient terminal refresh-error contract; viewer success also cannot attribute an old team removal to a new grant. These ambiguous controls therefore hold affected work without deleting tokens, links, maps or bodies. Reconnect creates a fresh revision and clears the old hold. Native permission/grant revalidation beyond reconnect remains an owner qualification gate.

All native session results use the shared-place policy because a response may become an issue comment. Only the fixed outcome and allowed link appear there. The injected `LinearDeps.privateResult({account, jid, text})` surface must deliver privately and idempotently by account plus job id. Until the later owner surface is connected, the terminal outbox retains its sealed private summary; it never publishes or drops it to finish a task.

Before activation, qualify the actual native payload/author fields, app viewer membership, first-thought latency, stop handling, whole-plan replacement, lost activity-create recovery, refreshed/lost refresh responses, token revocation and changed-installation holds against a dedicated owner workspace. Also qualify the prerequisite safe laptop placement, signing/relay/runner capabilities, permitted models and private result surface. Fresh exact-P2-head hosted Redis checks must cover the new installation/quota and native-session admission fences. Earlier P1c CI is evidence only for that older head.

All native admission, task metadata and effects require the trusted account-deletion authority adapter; an absent adapter fails closed. Fresh review and exact-P2-head hosted Redis proof must qualify the new account/link/install/hold fences and opaque installation epochs. Permanent minimal closure markers prevent erased account data from being recreated by delayed writes.

Disconnect uses the same durable pending/confirmed/uncertain revocation protocol. A concurrent local eraser cannot reopen the grant while its captured refresh-token revoke is in flight. The default transport checks exact captured closing authority immediately before the request, and only HTTP200 revocation acknowledgement confirms this operation; 400/401 and ambiguous transport results do not prove a dead grant. Uncertain state keeps a token-free closing barrier, exposing `review-native-revocation` instead of blind transport retry. Local account erasure remains available without active account authority. Process-death/native reconciliation and the provider's behavior for an already delivered request remain actual P4/live qualification gates; no final preflight is claimed to cancel an in-flight provider operation.
